## 1. 실행

### 개발 중

```bash
cd backend && ./gradlew bootRun     # http://localhost:8080
cd frontend && npm install && npm run dev   # http://localhost:5173
```

Vite가 `/api`를 8080으로 넘깁니다. 백엔드 포트를 바꿨다면 `VITE_API_TARGET`으로 지정합니다.

### 설치본

```bash
packaging/desktop/jpackage/build-desktop.sh
```

프론트를 빌드해 백엔드 정적 리소스로 넣고 OS별 설치 파일을 만듭니다. 실행하면 창 없이 서버가 뜨고
브라우저가 열립니다. 포트를 바꾸려면 `~/.project-flow/application.properties`에 `server.port=8090`

## 2. 화면과 순서

메뉴는 설계서 §2.2의 구조를 그대로 씁니다.

```text
프로젝트 | WBS | Agile | 간트 차트 | RACI | RAID | Dashboard
                 ├─ Backlog                              ├─ 요약
                 ├─ Sprint                               └─ 진척
                 └─ Board
```

- **Agile**을 누르면 Backlog로 가고, 그 아래 줄에 Backlog · Sprint · Board가 펼쳐집니다.
- **진척**은 Dashboard 안의 탭입니다. 요약이 숫자를 보여 주고, 진척이 그 숫자의 근거(가중치·기준선·
  스냅샷)를 입력하는 곳입니다. **체크포인트만 예외로 WBS 화면의 항목 편집 폼에서 입력**합니다 —
  진척 탭의 체크포인트 목록은 읽기 전용이고, 편집은 "WBS에서 편집" 링크로 안내합니다.

프로젝트 선택은 모든 화면이 공유하므로 한 번 고르면 화면을 옮겨도 유지됩니다.

처음 시작할 때의 순서는 이렇습니다.

```
프로젝트 만들기
      │
      ▼
WBS 구성 ──────────────► 단계는 Summary, 최하위 작업은 Work Package
      │                   Work Package마다 실행 방식(Waterfall/Agile/Hybrid)과 가중치
      ▼
Backlog 작성 ──────────► Story·Bug를 Work Package에 귀속
      │
      ▼
Sprint 계획·시작 ──────► 항목 배정 → 시작 (동시에 하나만)
      │
      ▼
Board에서 실행 ────────► TODO → IN_PROGRESS → REVIEW → DONE
      │
      ▼
진척 자동 집계 ────────► WBS·간트·대시보드가 같은 숫자를 봅니다
```

### 2.1 WBS — 범위를 정한다

- **Summary**는 단계, **Work Package**는 최하위 관리 단위입니다. Work Package에는 하위를 둘 수
  없습니다 — 하위가 필요하면 구분을 Summary로 바꾸세요.
- **실행 방식은 Work Package에만** 지정합니다. 미지정으로 두면 예전처럼 입력한 진행률을 그대로
  씁니다(`수동 입력`).
- **실행 방식을 Waterfall·Hybrid로 바꾸면 같은 편집 폼에 체크포인트 목록이 나타납니다.** 여기서
  추가·승인·삭제합니다 — Dashboard까지 오갈 필요가 없습니다. 항목을 먼저 저장해야(기존 항목
  편집일 때만) 나타나고, 추가·승인·삭제는 폼의 [저장]과 무관하게 그 자리에서 바로 반영됩니다.
- **가중치**는 형제 사이의 비중입니다. 비워 두면 "정하지 않음"이고 0이 아닙니다. 한 가지 안에서
  아무도 가중치가 없으면 예전처럼 하위 개수로 평균 냅니다(`하위 평균`).
- **실적·예상 종료**는 편집 폼에서 직접 넣습니다. Sprint가 끝났다고 자동으로 채워지지 않습니다.

### 2.2 Backlog — 실행할 일을 적는다

- Epic > Story/Bug > Task 계층입니다. **귀속은 상속**되므로 Story의 Work Package를 바꾸면 그 Task도
  따라갑니다.
- **집계 대상은 Story·Bug뿐**입니다. Epic이나 Task를 함께 세면 같은 일을 두 번 셉니다.
- Story Point는 팀의 추정, 진척 가중치는 Work Package 안에서의 비중입니다 — **다른 값이니 더하지
  마세요.**
- 다 쓴 항목은 삭제 대신 **보관**하세요. 보관해도 마지막 상태가 남습니다.

### 2.3 Sprint·Board — 담고, 실행한다

**Sprint** 화면은 계획을 다룹니다 — Sprint 만들기, 항목 배정, 시작, 종료(이월 포함).
**Board** 화면은 실행을 다룹니다 — 카드 옮기기, 차단 표시, 배정 제거. 두 화면은 고른 Sprint를
공유하므로 Sprint에서 고른 것이 Board에서 열립니다.

- **실행 중인 Sprint는 하나**입니다(단일 팀 전제).
- 완료로 옮길 때 **확인 대화상자**가 뜹니다. 시스템에 Definition of Done이 없으므로 "확인했다"는
  사실을 사람이 밝혀야 합니다.
- **차단**은 상태와 별개입니다. 칸은 그대로 두고 표시만 하며, 차단된 항목은 완료할 수 없습니다.
  차단 카드에는 관련 RAID 항목과 소유자가 함께 뜹니다.
- **종료할 때 미완료를 다음 Sprint로 이월**할 수 있습니다. 원 Sprint에는 "이월"로, 다음 Sprint에는
  완료로 남아 실적이 두 번 세어지지 않습니다.

### 2.4 진척 (Dashboard 탭) — 숫자의 근거를 본다

| 실행 방식 | 진척 계산 |
|---|---|
| Agile | 완료 Story·Bug ÷ 전체 Story·Bug |
| Waterfall | 승인된 체크포인트 가중치 ÷ 전체 체크포인트 가중치 |
| Hybrid | Agile × α + Waterfall × (1−α). α는 Work Package의 "Agile 비율(%)" |
| 미지정 | 입력한 진행률 그대로 |
| 상위(Summary) | 하위 가중치 평균. 가중치가 하나도 없으면 하위 개수 평균 |

- **분모가 없으면 "산정 전"**입니다. 0%가 아니고, 화면도 막대를 그리지 않습니다.
- **Waterfall·Hybrid의 분모(체크포인트)는 여기서 편집하지 않습니다.** 목록은 읽기 전용으로만
  보이고, 추가·승인·삭제는 WBS 화면의 항목 편집 폼에서 합니다(§2.1). "WBS에서 편집" 링크를 누르면
  그 항목이 열린 WBS 화면으로 이동합니다.
- **인수 상태는 진척과 별개**입니다. 실행이 100%여도 인수가 남았으면 완료로 보지 않습니다.
- **기준선(Baseline)을 승인**해야 계획 대비 편차가 나옵니다. 승인은 명시적 행위이고, 자동으로
  일어나는 경로는 없습니다.
- **스냅샷**으로 그 시점의 보고 숫자를 남길 수 있습니다. 이후 범위가 바뀌어도 스냅샷은 그대로입니다.

### 2.5 간트 — 세 가지 일정을 함께 본다

한 행에 위에서부터 **기준 일정(회색 얇은 선) · 현재 계획(굵은 막대) · 실적(완료색 얇은 선)**이
쌓입니다. 예상 종료는 오른쪽 삼각 표식이고, 기준 종료일을 넘기면 경고색이 됩니다.

- **기준선을 승인하지 않았으면 "기준 일정 미등록"**이라고 적습니다. 현재 계획을 기준선인 것처럼
  그리지 않습니다.
- **Sprint는 업무 행 위의 별도 레인**입니다. 업무 행을 클릭하면 관련 Sprint가, 레인을 클릭하면
  관련 업무가 강조됩니다.
- 기준 초과 배너의 링크를 누르면 **WBS의 해당 행**으로 이동합니다.

### 2.6 RACI — 책임을 정한다

- **구성원은 프로젝트 화면에서 추가·수정·삭제합니다**(행의 "구성원" 버튼). RACI 화면은 그 목록을
  매트릭스의 열로 읽기만 하고, 구성원이 하나도 없으면 프로젝트 화면으로 가라는 안내만 보여줍니다.
- 단계(Summary)에 지정한 역할은 **그 아래 Work Package에 상속**됩니다. 점선·흐린 글자가 상속된
  것이고, 그 행에서는 지울 수 없습니다.
- 하위에서 같은 역할에 다른 사람을 지정하면 **재정의**입니다. 상위의 글자는 취소선으로 남습니다.
- 누락 경고는 상속까지 본 뒤 **최하위 행에만** 나옵니다. 책임자 중복은 **그 글자를 실제로 가진
  행에** 표시되며, 자동으로 지우지 않습니다.
- **Backlog 담당자는 RACI 역할이 아닙니다.** 행 머리에 참고로 보일 뿐이고, 담당자를 바꿔도 A는
  움직이지 않습니다.

### 2.7 RAID — 위험과 이슈를 관리한다

- 한 항목을 **WBS 업무·Sprint·Backlog 여러 곳에** 연결할 수 있습니다. 같은 위험을 여러 개로 복사하지
  마세요 — 닫아야 할 것이 여러 개가 됩니다.
- **연결 대상을 삭제하면 연결만 끊기고 항목은 남습니다.** 보관은 연결에 영향을 주지 않습니다.
- 노출도는 확률 × 영향으로 자동 계산합니다. 기한 초과는 서버 기준일로 판정하며, 종결된 항목은
  기한이 지나도 초과가 아닙니다.

### 2.8 Dashboard — 한 화면에서 본다

**요약** 탭은 다른 화면의 숫자를 모아 보여줄 뿐 **자기 계산은 하지 않습니다.** 그래서 WBS·간트·
Dashboard의 진척은 항상 같습니다. **진척** 탭(§2.4)이 그 숫자의 근거를 입력하는 곳이고, 여기서
기준선을 승인하면 요약으로 돌아올 때 갱신됩니다.

- 카드의 숫자는 대부분 **눌러서 원인 항목으로 이동**합니다.
- **"데이터 누락"** 카드는 숫자가 답하지 못하는 부분을 알려 줍니다 — 실행 방식 미지정, 가중치 없음,
  산정 불가, 미연결 Backlog. 임의로 채우지 않습니다.
- **완료 Story Point 추세**는 종료된 Sprint만 그립니다. 진행 중인 것은 아직 움직이는 숫자라 옆에
  따로 적습니다.

## 3. 공유 — 내보내기와 가져오기

프로젝트 화면의 행마다 셀렉트가 있습니다.

| 고르는 것 | 결과 |
|---|---|
| 전체 (JSON) | 프로젝트 하나를 파일 하나로. **다시 읽어들이기 위한 것** |
| WBS / RACI / RAID (CSV) | Excel에서 읽기 위한 것. 판정값과 라벨 포함 |

- 가져오기는 **항상 새 프로젝트를 만듭니다.** 기존 프로젝트에 병합하지 않습니다.
- 파일 형식 버전은 **6**입니다. 그보다 높은 파일은 거부하고, 낮은 파일(1~5)은 읽습니다.
- CSV에는 UTF-8 BOM이 붙어 Windows Excel에서 한글이 깨지지 않습니다.

## 5. 알려진 제한 사항

### 5.1 구조

- **팀이 하나입니다.** 팀 테이블이 없어 실행 중인 Sprint도 하나뿐입니다. 팀을 도입하려면 `teams` +
  `sprints.team_id`를 추가하고 "활성 Sprint 하나" 규칙을 팀 단위로 바꿔야 하며, 속도 추세도 팀별로
  나뉘어야 합니다(**팀 간 포인트를 합산하면 안 됩니다**).
- **로그인이 없습니다.** 구성원은 프로젝트 안의 이름일 뿐이고, 변경자·승인자는 입력한 문자열입니다.
  RACI는 표시용이지 권한이 아닙니다.
- **데스크톱 설치본은 각자 로컬 H2 파일**을 씁니다. 공유 서버가 없으므로 프로젝트를 넘기는 방법은
  파일뿐입니다.

### 5.2 일정

- 선후행 관계는 **FS(Finish-to-Start) 한 종류**입니다. SS/FF/SF는 지원하지 않습니다.
- **영업일·휴일 달력이 없습니다.** 주말에도 일정이 흐르고, 지연 일수와 기대 진행률이 달력일 기준입니다.
- 일정 재계산은 **뒤로만 밀어냅니다.** 여유가 생겨도 앞으로 당기지 않습니다.
- **마일스톤 개념이 없습니다.** 대시보드는 계획 종료일과 예상 종료일을 말할 뿐입니다.

### 5.3 진척

- **실적 날짜는 손으로 넣습니다.** Board에서 완료해도 WBS의 실제 완료일은 채워지지 않습니다
  (Sprint 종료와 산출물 완료는 다른 사실이기 때문입니다).
- **기준선은 최신 하나만 봅니다.** 여러 버전을 나란히 비교하는 화면은 없습니다.
- **Waterfall 체크포인트가 없으면 산정 전**입니다. 체크포인트를 먼저 등록해야 숫자가 나옵니다.
- 진척률 변경 이력(요구사항 8.2)은 `change_logs`에 자리는 있지만 **화면이 없습니다.**

### 5.4 RAID·RACI

- `raid_links.target_id`에는 **외래 키가 없습니다.** 애플리케이션이 유일한 방어선이므로, 새 삭제
  경로를 만들면 `RaidService.detachTargets`를 함께 불러야 합니다.
- **RACI 상속에 예외를 둘 수 없습니다.** "이 업무만 단계의 책임자를 따르지 않음"은 그 행에 다른
  사람을 지정해야 표현됩니다. 빈 재정의는 표현할 수 없습니다.

### 5.5 검증하지 않은 것

- **PostgreSQL(`server` 프로필)에서의 V20·V21 마이그레이션.** H2로만 확인했습니다.
- **Docker 이미지 빌드와 실행.** Dockerfile은 있으나 검증하지 않았습니다.
- **브라우저에서의 시각 확인은 일부만** 했습니다. 메뉴 구조, Dashboard의 두 탭과 탭 전환 시 갱신,
  Board, Sprint는 실제로 열어 확인했습니다. WBS·Backlog·간트·RACI·RAID 화면과 다크 모드,
  좁은 화면은 타입 검사·빌드까지만 확인했습니다.
- **대량 데이터에서의 성능.** 대시보드는 여섯 개 조회를 한 요청에서 합치므로, 항목 수가 크게 늘면
  가장 먼저 느려질 곳입니다.

## 6. 운영 적용 전에 필요한 일

1. **PostgreSQL에서 마이그레이션 전체를 한 번 돌려 보기.** 특히 V18(이력 표 흡수)과 V21(RAID 컬럼
   이전)은 데이터를 옮기는 마이그레이션이라 실 DB에서 확인해야 합니다.
2. **백업 절차 정하기.** 데스크톱은 `~/.project-flow/data`, 서버는 PostgreSQL입니다. 내보내기 JSON은
   백업이 아니라 공유 수단입니다(판정값이 빠져 있습니다).
3. **동시 편집 정책.** 지금은 마지막 저장이 이깁니다. 여러 사람이 같은 프로젝트를 편집하면 조용히
   덮어씁니다.
4. **로그인·권한이 필요한지 결정.** 필요하다면 RACI를 권한 체계로 확장할지, 별도로 둘지를 먼저
   정해야 합니다(이번 범위에서 제외했습니다).
5. **팀 도입 여부 결정.** 위 5.1의 변경이 함께 필요합니다.
