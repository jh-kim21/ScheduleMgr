## 1. 요약

대시보드를 만들고 지시서의 통합 시나리오 7개를 실제 서버에서 끝까지 밟았다.

- **대시보드는 아무것도 계산하지 않는다.** 진척·일정·실행·책임·위험을 각 서비스에서 읽어 배치할
  뿐이다. "WBS, 간트, Dashboard 진척이 일치한다"는 완료 기준을 보증하는 유일한 방법이고, 실측으로
  확인했다.
- **한 요청, 한 기준일.** 여섯 개 payload를 서버가 한 번에 모아 하나의 `referenceDate`와 함께
  돌려준다. 브라우저가 여섯 번 부르면 카드마다 다른 "오늘"이 될 수 있다.
- **미산정을 0으로 대체하지 않는다.** 헤드라인 숫자가 `null`이면 "산정 전"이라 적고, 그 숫자가
  무엇에 대해 침묵하는지(`notEstimableCount`)를 함께 말한다.
- **데이터 누락을 따로 보고한다.** 실행 방식 미지정·가중치 없음·산정 불가·미연결 Backlog를 세어
  각각 원인 화면으로 보낸다. 임의로 채우지 않는다.
- **속도 추세는 종료된 Sprint만** 그린다. 진행 중인 것은 아직 움직이는 숫자라 옆에 따로 둔다.
  단일 팀이므로 계열은 하나이고, 팀이 생기면 나뉘어야 한다(합산 금지).
- 검증: 백엔드 **197건**, 프론트엔드 **95건**, 실 서버 통합 시나리오 **47항목** 전부 통과.
- **기능 변경은 대시보드 신설뿐이다.** 통합 검증에서 제품 결함은 나오지 않았고, 보완이 필요한
  곳도 없었다.

## 2. 변경 내용

### 2.1 백엔드

| 파일 | 역할 |
|---|---|
| `application/dto/DashboardResponse.java` | 한 화면 분량의 payload |
| `application/DashboardService.java` | 여섯 서비스의 응답을 읽어 배치 |
| `presentation/DashboardController.java` | `GET /api/projects/{projectId}/dashboard` |

**마이그레이션은 없다.** 대시보드가 필요로 하는 것은 이미 저장돼 있다.

`DashboardService`가 하는 일은 딱 두 가지다.

1. **읽기** — `ProgressService`, `GanttService`, `SprintService`, `BacklogService`,
   `RaciService`, `RaidService`를 각각 한 번씩 부른다.
2. **고르기** — 한 화면에 올릴 만큼만 추린다(카드당 5건). 추리더라도 **id를 모두 남겨** 숫자에서
   원인 항목으로 갈 수 있게 한다.

산술은 하지 않는다. 진척은 `ProgressResponse.project()`를 **그대로** 싣고, 지연·임계·기준 초과는
간트가 판정한 값을 세기만 하며, 책임 공백은 `RaciValidator`가 이미 상속까지 반영해 낸 목록을 종류별로
셀 뿐이다.

### 2.2 프론트엔드

| 파일 | 역할 |
|---|---|
| `api/dashboardApi.ts` | payload 타입 |
| `features/dashboard/useDashboard.ts` | 모듈 스코프 상태 + 캐시 |
| `views/DashboardView.vue` | 카드 배치 |
| `router/index.ts`, `App.vue` | `/dashboard` 라우트와 메뉴 |
| `stores/scheduleCache.ts` | `dashboardCacheKeyFor` — 세 리비전 + 로컬 날짜 |

**대시보드 캐시 키에는 모든 것이 들어간다.** 여섯 화면의 데이터를 읽으므로 어느 화면의 편집도 카드를
움직일 수 있다. 로컬 날짜는 지연·기한 초과가 날짜 기준이라 필요하다(표시하는 기준일은 언제나 서버의
`referenceDate`).

**읽기 전용 화면이다.** 대시보드에는 변경 API가 없다 — 각 숫자는 그것을 소유한 화면에서 바꾼다.
수동 새로고침 버튼만 두었다.

### 2.3 카드 구성

| 카드 | 내용 | 이동 |
|---|---|---|
| 진척 | 실제·계획·편차, Work Package 수와 산정 전 수, 실행 방식 분포 | 진척 |
| 일정 | 계획 기간·예상 종료, 지연/지연 위험/임계 건수, 지연 상위 5건 | 간트 · 각 행은 WBS |
| 기준 일정 | 승인 버전·항목 수, 기준 초과 목록, 범위 변화 | 진척 · 각 행은 WBS |
| 실행 | 진행 중 Sprint의 Goal·완료·포인트, 차단 항목과 관련 RAID·담당자 | Sprint · RAID |
| 추세 | 종료 Sprint의 완료 Story Point 막대 | Sprint |
| 책임 | 책임자 없음/담당자 없음/책임자 중복 건수 | RACI |
| 위험·이슈 | 기한 초과·노출도 높음·열린 이슈 | RAID |
| 인수 대기 | 실행 100%이지만 승인이 남은 업무 | WBS |
| 데이터 누락 | 종류별 건수 | 원인 화면 |

## 3. 검증

### 3.1 자동 테스트와 빌드

```
cd backend  && ./gradlew test        # 197건 통과
cd backend  && ./gradlew build       # 성공 (테스트 포함)
cd frontend && npm test -- --run     # 95건 통과
cd frontend && npm run build         # vue-tsc + vite 빌드 성공
```

`DashboardService`에는 단위 테스트를 두지 않았다. 여섯 서비스를 조합하는 클래스라 단위 테스트는
스무 개 남짓한 가짜 리포지토리를 요구하면서, 정작 검증해야 할 것("실제 화면들과 같은 숫자인가")은
확인하지 못한다. 그 질문에 답하는 것은 아래 §3.2의 시나리오이고, 조합의 재료가 되는 규칙들은 이미
각자의 단위 테스트가 지키고 있다.

### 3.2 통합 시나리오 (47항목, 실 서버)

빈 H2 파일에 V1~V21을 처음부터 적용한 뒤 실제 API로 지시서의 시나리오 일곱 개를 밟았다. 스크립트는
`scratchpad/verify7.py`, 결과 **47/47 통과**. Step 6의 검증(34항목)이 남긴 데이터를 그대로 두고
돌려, 회귀 확인이 실제 기존 데이터에 대해 이뤄지게 했다.

| 지시서 시나리오 | 확인한 것 |
|---|---|
| 생성 → WBS → 실행 방식 → Backlog → Sprint → Board → 진척 | Board에서 Story 하나를 완료하자 Agile Work Package가 50%가 되고, **WBS·간트·대시보드가 같은 값과 같은 기준일**을 보고 |
| 미완료 이월 → 다음 Sprint 완료 → 과거 실적 보존 | S1은 완료분 5포인트·이월 1건으로 고정, S2가 이월분을 완료로 셈. **합계 2건 — 중복 없음** |
| Hybrid 개발 완료 → 인수 대기 → 승인 후 완료 | α=60으로 Agile 100 × 0.6 + 승인 100 × 0.4 = 100%, 인수 대기로 표시, 승인 후 해제 |
| 지연 → 관련 Backlog·RAID 원인 → 책임자 | 차단 카드에 관련 Issue와 소유자(PM)가 함께, 지연 행은 WBS id를 동반, 책임 공백은 상속 반영해 0 |
| 범위·가중치 변경 → 현재 진척 갱신 → 기준 보존 | 기준선 버전 불변, 범위 변화(추가 1·가중치 변경 1) 보고, 편차는 기준선 범위에서만, 스냅샷 저장 |
| 프로젝트 변경 → 화면 필터·범위 갱신 | 선택 store와 캐시 키가 프로젝트를 포함하므로 화면 전환·프로젝트 전환이 각각 새로 읽음 |
| 기존 데이터 회귀 + 내보내기·가져오기 | Step 6이 만든 프로젝트 조회·수정·대시보드 정상, 왕복 후 진척·기준선·Sprint 실적 모두 보존 |

| 완료 기준 | 결과 |
|---|---|
| 같은 프로젝트·범위·기준일의 WBS·간트·Dashboard 진척 일치 | ✅ 실측 |
| 빈 데이터 표시 | ✅ 빈 프로젝트에서 진척 `null`(산정 전), 기준선 없음, Sprint 없음, 누락 없음 |
| 미산정 표시 | ✅ 분모 없는 Agile은 `null`·`NOT_ESTIMABLE`, 대시보드가 건수와 `incomplete`를 함께 보고 |
| 오류 상태 | ✅ 없는 프로젝트는 404 |
| 숫자 → 원인 항목 이동 | ✅ 지연·기준 초과·인수 대기는 WBS id, 데이터 누락은 종류별 목적지, 차단은 RAID |
| 기존 메뉴 정상 | ✅ 회귀 시나리오에서 확인 |

### 3.3 검증 중 고친 것

**제품 결함은 없었다.** 첫 실행에서 11항목이 실패했는데 모두 검증 스크립트 쪽 문제였다.

- 완료 확인 필드 이름을 `completionConfirmed`로 잘못 보냈다(실제는 `acceptanceConfirmed`). Board
  이동과 Backlog 생성이 400으로 거부되어 그 뒤의 시나리오가 줄줄이 실패했다. **API는 옳게 거부했다** —
  Definition of Done 확인 없이 완료로 넘어가지 않는 것이 Step 4의 규칙이다.
- Step 6 검증 스크립트에서도 4항목이 스크립트 버그였다(대상 종류가 다른 id를 그대로 비교, POST가
  201을 돌려주는데 200만 허용, Backlog 없는 Agile이 산정 전인 것을 실패로 판정).

### 3.4 실행하지 않은 검증

- **브라우저에서의 시각 확인.** 이 시점에는 타입 검사와 빌드까지만 했고 값은 API 레벨 47항목으로
  확인했다. (§5-1의 후속 변경 때 Dashboard 두 탭과 Board·Sprint·메뉴는 실제로 열어 확인했다.
  추세 막대와 좁은 화면은 여전히 눈으로 보지 않았다.)
- **PostgreSQL에서의 마이그레이션.** H2로만 돌렸다. V18·V21은 데이터를 옮기는 마이그레이션이라
  운영 적용 전에 실 DB에서 한 번 돌려 봐야 한다(운영 안내 §6).
- **대량 데이터에서의 성능.** 대시보드가 여섯 조회를 한 요청에 합치므로 가장 먼저 느려질 곳이다.
- **Docker 이미지 빌드.** 이번 범위 밖(지시서 "운영 배포" 제외).

## 4. 결정과 근거

| 결정 | 대안 | 왜 이쪽인가 |
|---|---|---|
| 서버가 한 번에 합쳐 준다 | 브라우저가 여섯 API를 부른다 | 기준일이 하나여야 카드끼리 어긋나지 않는다. 왕복도 하나로 준다 |
| 대시보드가 계산하지 않는다 | 필요한 값만 골라 다시 계산 | 완료 기준이 "세 화면이 일치한다"이다. 자체 산술은 네 번째 의견이 된다 |
| 카드당 5건만 싣는다 | 전부 싣는다 | 대시보드는 "어디를 볼지" 정하는 화면이다. 전체는 각 화면에 있고, id를 남겨 이동을 보장한다 |
| 추세에 진행 중 Sprint를 넣지 않는다 | 함께 그린다 | Sprint 중간에 보면 매번 하락으로 읽힌다. 옆에 따로 적어 값은 보이게 했다 |
| 데이터 누락을 별도 카드로 | 숫자 옆 각주 | 누락은 그 자체로 할 일이다. 각주로 두면 헤드라인만 읽고 지나간다 |
| 읽기 전용 | 대시보드에서 바로 수정 | 같은 값을 고치는 경로가 둘이면 검증 규칙도 두 벌이 된다. 원인 화면으로 보낸다 |
| `DashboardService` 단위 테스트 없음 | 가짜 6종을 세워 테스트 | 조합만 하는 클래스다. 가짜로는 "실제와 같은 숫자인가"를 물을 수 없어 통합 시나리오로 대신했다 |
| 마일스톤 대신 계획·예상 종료일 | 마일스톤 엔티티 신설 | 이 코드베이스에 마일스톤 개념이 없다. 새 개념을 대시보드가 도입하는 것은 지시서 범위 밖이다 |

| Step | 내용 | 상태 |

| 1 | 현황 분석·격차 정리 | 완료 (문서) |

| 3 | Product Backlog와 Work Package 귀속 | 완료 |
| 4 | Sprint · Board · 이월 · 완료 확인 | 완료 |
| 5 | 가중치·완료 기준·Baseline·변경 이력 + 공통 진척 집계 | 완료 |
| 6 | 간트(기준/계획/실적) · RACI 상속 · RAID 복수 연결 | 완료 |

설계 문서 대비 **의도적으로 구현하지 않은 것**:

- **팀(Team)** — 사용자가 단일 팀으로 결정했다. 도입 시 필요한 변경은 운영 안내 §5.1에 적었다.
- **로그인·권한** — 지시서가 "RACI 기반 권한 체계 전면 개편"을 범위에서 제외했다.
- **알림·외부 도구 연동** — 지시서 범위 제외.
- **진척률 변경 이력 화면** — `change_logs`에 자리는 있으나 화면이 없다(요구사항 8.2).

## 5-1. 보고서 작성 뒤의 후속 변경 — 메뉴 구조 정정

이 보고서를 쓴 뒤, 화면 구조가 설계서 §2.2와 어긋나 있다는 지적을 받고 바로잡았다. Step 7까지
기능은 다 만들었지만 **메뉴 배치를 설계서대로 하지 않은 것**이 남아 있었다.

| | 고치기 전 | 고친 뒤 (설계서 §2.2) |
|---|---|---|
| Agile 묶음 | 없음 — Backlog·Sprint가 최상위에 평평하게 | `Agile` 아래 Backlog · Sprint · Board |
| Board | Sprint 화면에 끼워 넣음 | 독립 라우트 `/board`. Sprint 화면은 계획만 다루고 링크 |
| Dashboard | 두 번째, 라벨 "대시보드" | 맨 끝, 라벨 `Dashboard` |
| 진척 | 최상위 메뉴 | `Dashboard`의 탭 (`/dashboard?tab=progress`) |

- **진척을 Dashboard 탭으로 넣은 근거**: 요약은 읽기 전용 집계이고 진척은 그 숫자의 *근거를 입력*
  하는 곳이라 한 화면의 두 면이다. 이렇게 해야 최상위 메뉴가 설계서의 일곱 개로 떨어진다.
  "Dashboard는 읽기 전용"이라는 규칙은 `DashboardService`와 `/dashboard` API에 대한 것이지 화면이
  다른 컴포넌트를 품지 못한다는 뜻이 아니다 — 진척 탭은 기존 진척 API를 그대로 쓰므로 변경 경로가
  늘지 않는다.
- `ProgressView.vue` → `features/progress/ProgressPanel.vue`로 옮겼다(껍데기만 벗김).
  예전 `/progress`는 진척 탭으로 리다이렉트하므로 기존 링크가 살아 있다.
- **탭 전환 시 요약을 다시 읽는다.** 탭은 같은 컴포넌트 안이라 마운트가 다시 일어나지 않는데,
  진척 탭에서 기준선을 승인하면 요약이 낡는다. `useProgress`의 모든 변경이 `markWbsChanged()`를
  부르고 대시보드 캐시 키에 WBS 리비전이 들어 있어, 요약으로 돌아올 때 `ensureLoaded`가 다시 읽는다.

검증: 프론트엔드 95건·빌드 통과에 더해 **브라우저에서 직접 확인**했다 — 메뉴 일곱 개와 Agile 하위 줄,
Board 화면, Sprint의 계획 전용 화면, Dashboard의 두 탭, 그리고 진척 탭에서 기준선을 v2로 승인한 뒤
요약 탭이 v2로 갱신되는 것까지.

## 6. 남은 문제

- **`raid_links.target_id`에 외래 키가 없다.** 새 삭제 경로를 만들 때 `detachTargets`를 함께 부르지
  않으면 등록부에 이름 없는 줄이 남는다.
- **실적 날짜 입력 경로가 WBS 편집 폼뿐이다.** Board에서 완료할 때 실제 완료일을 묻는 것이
  자연스럽지만, Step 6 지시서가 자동 복사를 금지했고 "묻기"는 범위 밖이라 넣지 않았다.
- **기준선은 최신 하나만 본다.** 여러 버전 비교 화면이 없다.
- **동시 편집은 마지막 저장이 이긴다.** 낙관적 잠금이 없다.
- **대시보드가 여섯 조회를 한 트랜잭션에서 한다.** 항목이 많아지면 가장 먼저 느려진다. 지금은
  캐시(세 리비전 + 날짜)로 재조회를 줄이는 수준이다.

운영 적용 전에 필요한 일은 [운영 안내 §6](Hybrid_PM_Operation_Guide.md#6-운영-적용-전에-필요한-일)에
정리했다.
