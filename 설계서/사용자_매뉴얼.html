1. 시작하기

한 줄 요약: 앱을 띄우고, 메뉴 구조를 익히고, 모든 화면에 공통으로 적용되는 규칙 몇 가지를 알아 둡니다.

1.1 실행

설치본

실행하면 창이 뜨지 않고 서버가 백그라운드로 올라온 뒤 브라우저가 자동으로 열립니다. 창이 없는 것이 정상입니다. 브라우저가 안 열리면 직접 http://localhost:8080 으로 들어가세요.

포트를 바꾸려면 ~/.project-flow/application.properties 에 한 줄이면 됩니다.

server.port=8090

브라우저도 바뀐 포트로 열립니다. 이 파일은 데이터와 같은 폴더에 있어 재설치·업그레이드해도 남습니다.

개발 중

cd backend  && ./gradlew bootRun    # http://localhost:8080
cd frontend && npm run dev          # http://localhost:5173

프론트엔드가 /api 요청을 8080으로 넘깁니다. 백엔드 포트를 바꿨다면 VITE_API_TARGET 으로 알려 주세요.

데이터는 어디에 있나

데스크톱 설치본 ~/.project-flow/data (로컬 H2 파일)

설치본은 각자의 PC에 데이터를 둡니다. 공유 서버가 없으므로 다른 사람에게 프로젝트를 넘기는 방법은 파일뿐입니다(9장 참고).

1.2 메뉴 구조

프로젝트 | WBS | Agile | 간트 차트 | RACI | RAID | Dashboard
                 ├─ Backlog                              ├─ 요약
                 ├─ Sprint                               └─ 진척
                 └─ Board
  • Agile 은 자기 화면이 없는 묶음입니다. 누르면 Backlog 로 가고, 그 아래에 Backlog · Sprint · Board 줄이 나타납니다. 이 줄은 Agile 화면 세 개 안에 있을 때만 보입니다.
  • 진척 은 Dashboard 안의 탭입니다. 요약이 숫자를 보여 주고, 진척이 그 숫자의 근거를 입력하는 곳이라 한 화면의 두 면으로 두었습니다.
  • 오른쪽 위 시스템 설정 버튼은 화면 테마를 바꿉니다(시스템 설정 → 라이트 → 다크 순환).

각 화면이 하는 일은 이렇습니다.

1.3 모든 화면에 공통인 것

프로젝트 선택은 하나입니다

화면마다 왼쪽 위에 프로젝트 셀렉트가 있고, 모든 화면이 같은 선택을 공유합니다. 한 번 고르면 메뉴를 옮겨도 유지되고, 바꾸면 모든 화면이 그 프로젝트로 따라옵니다.

기준일은 서버가 정합니다

지연·기한 초과 같은 판정의 "오늘"입니다. 화면 상단에 기준일 2026-09-09 처럼 적혀 있습니다.

브라우저 시계를 쓰지 않는 이유는, 한 응답 안의 행들이 서로 다른 "오늘"로 판정되거나 오래 열어 둔 탭에서 차트의 오늘 선과 배지가 어긋나는 것을 막기 위해서입니다. 탭을 밤새 열어 둬도 다음 날 자동으로 갱신됩니다.

추가·수정은 전부 대화상자입니다

  • 폼이 화면에 붙박이로 있지 않고 대화상자로 뜹니다. 표를 아래로 밀어내지 않기 위해서입니다.
  • 저장이 거부되면 대화상자가 닫히지 않습니다. 그 안에 이유가 표시되고 입력값은 그대로 남습니다. 다시 입력할 필요가 없습니다.
  • 닫기는 × 버튼, 취소 버튼, Esc 키 모두 됩니다.

표는 가로로 스크롤합니다

셀 내용을 줄바꿈하지 않습니다. 행 높이가 들쭉날쭉해지면 훑어 읽기 어렵기 때문입니다. 화면보다 넓으면 표 안에서 좌우로 스크롤하세요. 설명·비고처럼 긴 칸은 잘라서 보여주고, 마우스를 올리면 전체가 뜹니다.

저장은 즉시 반영됩니다

"전체 저장" 버튼은 없습니다. 대화상자에서 저장하거나 카드를 옮기면 그 순간 서버에 반영됩니다.

화면끼리 숫자가 다르면 안 됩니다

진척은 한 곳에서만 계산해 WBS·간트·Dashboard 가 같은 값을 읽습니다. 세 화면의 진척이 다르게 보인다면 그건 캐시이거나 결함입니다 — 화면을 다시 들어가 보고, 그래도 다르면 알려 주세요.

1.5 이 도구의 세 가지 원칙

매뉴얼 전체에서 반복되는 태도입니다. 이것만 알아도 화면이 왜 그렇게 동작하는지 대부분 설명됩니다.

1. 산정 전은 0%가 아닙니다. 분모가 없으면(Story 가 없는 Agile Work Package, 체크포인트가 없는 Waterfall) 숫자를 만들어 내지 않고 "산정 전"이라고 적습니다. 착수 전 프로젝트가 "0% 진행"으로 보이면 정말 0%인 것과 구별할 수 없기 때문입니다.

2. 만족할 수 없는 구조는 거부하고, 계획이 안 맞는 것은 표시합니다. 순환 선후행처럼 유효한 답이 아예 없는 것은 등록 자체를 막습니다. 반면 최종 책임자가 둘이거나 일정이 선행보다 앞서는 것은 저장은 되고 경고만 뜹니다 — 인수인계 중에 반드시 지나가는 상태이고, 막으면 "지우고 다시 넣기"를 강요하게 됩니다.

3. 파생 값은 저장하지 않습니다. WBS 코드, Summary 의 일정·진척, 지연 판정, 노출도는 모두 볼 때 계산합니다. 저장해 두면 항목을 옮기거나 날짜가 바뀌는 순간 낡은 값이 되기 때문입니다. 그래서 화면을 새로 열면 항상 지금 기준의 숫자가 나옵니다.

2. 프로젝트

모든 화면의 출발점. 프로젝트를 만들고 고르고, 파일로 주고받는 곳입니다.

시작일 · 종료일 계획의 테두리입니다

프로젝트의 시작일·종료일은 어디에도 쓰이지 않습니다. 간트와 Dashboard의 "계획 기간"은 이 두 날짜가 아니라 WBS 항목들의 실제 날짜 범위 (가장 이른 시작일 ~ 가장 늦은 종료일)입니다. 둘이 어긋나 있어도 경고하지 않으므로, 프로젝트 기간을 적어 두었다고 일정이 그 안에 갇히지는 않습니다.

프로젝트 선택은 앱 전체가 공유합니다

여기서 고른 프로젝트가 곧 WBS·Agile·간트·RACI·RAID·Dashboard가 보는 프로젝트입니다. 각 화면 왼쪽 위의 셀렉트는 같은 값을 가리키는 창구가 여럿일 뿐입니다. 그래서 탭을 옮겨도 선택이 첫 프로젝트로 되돌아가지 않습니다.

선택한 프로젝트를 삭제하면 선택이 자동으로 비워집니다 — 없는 프로젝트를 가리킨 채로 다른 화면에 들어가면 그 화면이 빈 채로 오류를 내기 때문입니다.

저장이 거부되면

대화상자가 닫히지 않고 그 안에 이유가 뜹니다. 입력값도 그대로 남습니다. 화면 본문에 오류를 적으면 대화상자 뒤에 가려서 "조용히 실패한 것처럼" 보이기 때문에, 저장 성공 여부를 대화상자가 직접 말하도록 되어 있습니다.

2.2 프로젝트 삭제가 함께 지우는 것

삭제는 되돌릴 수 없고, 확인창 한 번이 전부입니다. 프로젝트에 딸린 모든 것이 데이터베이스 연쇄 삭제(ON DELETE CASCADE)로 함께 사라집니다.

WBS 화면의 "연결 Backlog가 있으면 삭제 거부" 같은 안전장치가 여기에는 없습니다. WBS 항목 하나를 지울 때는 실행 기록이 딸려 나가는 것을 막지만, 프로젝트 삭제는 "이 프로젝트를 통째로 없앤다"는 뜻이므로 막을 이유가 없습니다. 대신 그만큼 되돌릴 수도 없으니, 지우기 전에 전체 JSON으로 내보내 두세요.

2.3 주의할 점

  • 프로젝트 상태는 표시용입니다. "완료"로 바꿔도 지연 판정이 멈추거나 Sprint가 닫히거나 진척 계산이 얼어붙지 않습니다. 상태에 따른 규칙(요구사항 4.3)은 아직 구현되지 않았습니다.
  • 프로젝트 이름에 유일성 제약이 없습니다. 같은 이름을 두 번 만들 수 있고, 그러면 모든 화면의 프로젝트 셀렉트에서 구분할 수 없습니다. 가져오기만은 이 사정을 알고 (가져옴)을 붙입니다.
  • 동시 편집은 마지막 저장이 이깁니다. 두 사람이 같은 프로젝트를 고쳐도 경고가 없습니다.
  • 삭제 확인창에 무엇이 함께 지워지는지 적혀 있지 않습니다. "이름" 프로젝트를 삭제할까요? 한 줄뿐이므로, 위 표를 기억해 두는 쪽이 안전합니다.

3. WBS

한 줄 요약: 프로젝트의 범위를 계층으로 정의하고, 그 계층을 다른 모든 화면이 쓸 수 있는 뼈대로 만드는 화면입니다. 여기서 만든 항목이 간트의 막대, Backlog의 귀속 대상, RACI의 행, RAID의 연결 대상, 진척 집계의 단위가 됩니다.

3.4 이 화면의 규칙

거부되는 동작과 그 이유입니다. 대부분은 화면이 먼저 막고, 서버가 최종 방어선입니다.

"하위" 버튼이 비활성입니다

그 항목이 Work Package이기 때문입니다. 마우스를 올리면 이유가 뜹니다 — Work Package에는 하위 항목을 둘 수 없습니다. 수정에서 구분을 Summary로 바꾸세요.

Work Package는 최하위 관리 단위라는 선언입니다. 여기에 Backlog가 붙고 가중치가 매겨집니다. 자식이 하나 생겼다고 조용히 상위 항목으로 바뀌면, 붙어 있던 실행 방식과 Backlog 귀속이 말없이 고아가 됩니다. 그래서 구분을 바꾸는 것은 사람이 하는 명시적인 행위여야 합니다.

같은 이유로, 드래그해서 Work Package 안쪽(행 가운데)에 놓는 것도 불가능합니다. 위/아래 가장자리에 놓아 형제로 만드는 것은 됩니다 — 그건 그 Work Package의 부모 아래로 들어가는 것이지 그 안으로 들어가는 것이 아니기 때문입니다.

파일 가져오기의 상위 항목 선택도 같은 규칙을 따릅니다. 그래서 그 목록에는 Work Package가 아예 나오지 않습니다 — 골라서 거부당하는 것보다 애초에 고를 수 없는 편이 낫기 때문입니다.

구분에서 Work Package를 고를 수 없습니다

하위가 있는 항목이기 때문입니다. 하위를 먼저 다른 곳으로 옮기거나 지워야 합니다. (서버도 같은 이유로 거부합니다: 하위 항목이 있는 항목은 Work Package로 바꿀 수 없습니다.)

Summary로 바꾸려는데 거부됩니다

메시지: 연결된 Backlog 항목이 3건 있어 Summary로 바꿀 수 없습니다 (로그인 화면, 목록 화면, … 등). 다른 Work Package로 옮기거나 보관하세요.

Summary는 하위를 집계하는 자리라, 여기에 Story가 직접 붙어 있으면 그 무게가 두 번 셉니다 — Summary 자신의 집계에서 한 번, 하위 집계에서 또 한 번. 그래서 살아 있는 Backlog가 붙은 Work Package는 Summary가 될 수 없습니다.

보관된 Backlog는 막지 않습니다. 보관은 "이건 접어둔다"는 명시적인 표시이기 때문입니다.

실행 방식 셀렉트가 비활성입니다

구분이 Summary이기 때문입니다. 실행 방식은 최하위 Work Package에 지정합니다.

이때 이전에 지정했던 값은 지워지지 않고 보관됩니다. 표에 보관 Agile 칩으로 보이고, 구분을 Work Package로 되돌리면 그대로 살아납니다. 그래서 이 규칙은 "Summary는 실행 방식이 null이어야 한다"가 아니라 "Summary의 실행 방식은 바꿀 수 없다"로 되어 있습니다 — 폼이 보관값을 그대로 돌려보내도 통과해야 하기 때문입니다.

드래그해도 놓이지 않습니다

  • 자기 자신 위에 — 무의미합니다.
  • 자기 하위 어딘가에 — 순환이 됩니다. 위/아래 가장자리도 마찬가지로 막힙니다(그 자리의 새 부모가 결국 자기 자신의 하위이기 때문입니다).
  • Work Package 안쪽에 — 위 규칙.

서버도 같은 것들을 거부합니다: 항목을 자기 자신의 하위로 이동할 수 없습니다. / 항목을 자신의 하위 항목 아래로 이동할 수 없습니다.

삭제가 거부됩니다

메시지: 연결된 Backlog 항목이 2건 있어 삭제할 수 없습니다 (…). 다른 Work Package로 옮기거나 보관하세요.

삭제 대상은 그 항목 하나가 아니라 그 아래 전부입니다. 판정도 그 범위 전체를 보고 합니다 — 지우려는 단계 어딘가에 살아 있는 Backlog가 하나라도 있으면 거부됩니다.

이 가드가 없으면 상위 하나를 지우는 것으로 실행 기록이 조용히 사라집니다. 보관된 항목만 남았다면 사유를 남기고 연결을 끊은 뒤 삭제가 진행됩니다.

Backlog를 고쳐도 WBS는 다시 읽습니다 — 트리가 연결 Backlog 수를 싣고 있기 때문입니다.

3.6 실무 예시

예시 1 — 새 프로젝트의 뼈대를 세운다

"차세대 포털 구축"의 WBS를 3단계로 잡고 싶다.

목표하는 모습:

1  요구 분석            (Summary)
   1.1  현행 조사       (Work Package · Waterfall)
   1.2  요구사항 정의   (Work Package · Waterfall)
2  설계·개발            (Summary)
   2.1  화면 설계       (Work Package · Hybrid, α 40)
   2.2  API 개발        (Work Package · Agile)

순서가 중요합니다.

  1. ＋ 최상위 항목 추가 → 업무명 요구 분석 → 추가. 새 항목이라 구분은 Work Package입니다.
  2. 방금 만든 1 요구 분석 행의 하위 버튼을 누르려니 비활성입니다. → 수정을 눌러 구분을 Summary로 바꾸고 저장합니다.
  3. 이제 하위 버튼이 살아납니다. 1.1 현행 조사, 1.2 요구사항 정의를 차례로 추가합니다.
  4. 각 하위를 수정해서 실행 방식 Waterfall, 시작일·종료일을 넣습니다.
  5. 2 설계·개발도 같은 순서로 만듭니다. 2.1 화면 설계는 실행 방식을 Hybrid로 고른 뒤 Hybrid 비중 α에 40을 넣습니다 — 비우면 그 행이 산정 전이 됩니다.

함정 — 새 항목을 만들 때 실행 방식을 먼저 고르고 나서 구분을 Summary로 바꾸면 추가가 거부됩니다(실행 방식 셀렉트가 비활성이라 되돌릴 수도 없습니다). 구분을 Summary로 바꿀 계획이라면 실행 방식은 미지정으로 둔 채 만드세요. 이미 그 상태가 됐다면 구분을 잠시 Work Package로 되돌려 실행 방식을 미지정으로 바꾼 뒤 다시 Summary로 고칩니다.

확인: 1 요구 분석 행의 실행 방식 칸이 Waterfall 2로, 2 설계·개발 행이 Agile 1 · Hybrid 1로 보이면 제대로 된 것입니다.

예시 2 — 이미 만들어 둔 Work Package를 쪼개고 싶다

2.2 API 개발이 너무 커서 인증 API와 주문 API로 나누려 한다. 그런데 2.2에는 이미 Story가 5건 붙어 있다.

  1. 2.2 API 개발의 하위 버튼 → 비활성입니다(Work Package라서).
  2. 수정 → 구분을 Summary로 → 저장 → 거부됩니다: 연결된 Backlog 항목이 5건 있어 Summary로 바꿀 수 없습니다 (…). 다른 Work Package로 옮기거나 보관하세요.
  3. 먼저 하위 두 개를 만들 자리를 확보합니다. 하지만 2번이 막혀 있으니 순서를 바꿉니다. - 2 설계·개발 아래에 하위 버튼으로 인증 API, 주문 API를 새로 만듭니다 (2.3, 2.4가 됩니다). - Backlog 화면으로 가서 5건의 귀속 Work Package를 2.3 또는 2.4로 옮깁니다. (Epic이나 Story의 하위 Task는 상위에서 상속되므로 상위만 옮기면 따라옵니다.)
  4. 이제 2.2 API 개발을 수정 → 구분 Summary → 저장 (통과합니다).
  5. 2.3, 2.4 행을 각각 2.2 행의 가운데로 드래그해 하위로 넣습니다. → 코드가 2.2.1, 2.2.2로 다시 매겨집니다.

왜 이렇게 도는가: Summary는 하위를 집계하는 자리라 Story를 직접 붙들고 있을 수 없고, 시스템은 "어느 하위로 옮길지"를 대신 정해 주지 않기 때문입니다.

예시 3 — 단계 하나를 통째로 지우려는데 거부된다

3 파일럿 단계를 없애기로 했다.

  1. 3 파일럿 행의 삭제 → 확인창에 하위 항목도 모두 함께 삭제됩니다.가 붙습니다 → 확인.
  2. 표 위에 붉은 글씨: 연결된 Backlog 항목이 2건 있어 삭제할 수 없습니다 (파일럿 배포 스크립트, 파일럿 피드백 반영). 다른 Work Package로 옮기거나 보관하세요.
  3. 두 건을 어떻게 할지 정합니다. - 일이 살아 있다 → Backlog 화면에서 다른 Work Package로 귀속을 옮깁니다. - 끝났거나 접는다 → Backlog 화면에서 보관합니다. (진행 중인 Sprint에 배정돼 있으면 보관도 거부되니, Sprint에서 먼저 제거해야 합니다.)
  4. 다시 삭제하면 진행됩니다. 이때 RAID 항목은 지워지지 않고 연결만 끊깁니다 — RAID 화면에서 그 항목의 연결 대상이 (없음)으로 바뀝니다.

대안: 정말 지우기보다 그 가지의 계획을 남겨 두고 싶다면, 삭제 대신 최상위 드롭존으로 끌어내려 다른 단계 밖으로 빼 두는 방법도 있습니다. 코드만 뒤로 밀릴 뿐 기록은 그대로 남습니다.

예시 4 — 이미 있는 Excel 계획표를 그대로 올린다

컨설팅사에서 받은 Excel WBS가 있고, 들여쓰기로 단계를 표현해 두었다.

레벨  업무명           시작일        종료일        진행률
1     요구 분석
2       현행 조사       2026-01-05   2026-01-12
2       요구사항 정의   2026-01-13   2026-01-30
1     설계
  1. 이 표를 레벨·업무명·시작일·종료일·진행률 순서의 CSV(또는 xlsx)로 정리합니다. 진행률 칸은 비워 둡니다 — 아직 아무도 시작 안 했습니다.
  2. ＋ 파일에서 가져오기 → 파일 선택 → 상위 항목은 (최상위) (이미 있는 프로젝트의 맨 위 단계로 붙일 것이므로) → 가져오기.
  3. 결과: 1 요구 분석(Summary, 바로 다음 행이 한 단계 깊으므로), 그 아래 1.1 현행 조사· 1.2 요구사항 정의(둘 다 진행률 0), 그리고 2 설계(Work Package, 하위가 없으므로)가 기존 항목들 뒤에 새 최상위로 붙습니다.
  4. 각 Work Package를 수정해 실행 방식을 지정합니다 — 파일은 이름·기간·진행률만 옮겼을 뿐, Agile/Waterfall 여부는 이 화면에서 사람이 정합니다.

같은 파일을 이미 있는 2 설계·개발(Summary) 아래에 끼워 넣고 싶다면, 3번에서 상위 항목을 2 설계·개발로 고르기만 하면 됩니다 — 나머지는 같습니다.

3.7 주의할 점

수정하면 실적·예상 종료가 지워집니다

가장 조심해야 할 것입니다. WBS 항목에는 실제 시작일·실제 완료일·예상 종료일이 저장될 수 있고 간트가 그것을 그리지만, 이 편집 폼에는 그 세 칸이 없습니다. 그래서 이 화면에서 항목을 수정·저장하면 그 값들이 비워집니다.

  • 지금 그 값이 들어 있는 경우는 가져오기(JSON)로 들여온 프로젝트뿐입니다.
  • 가져온 프로젝트의 실적을 보존해야 한다면 그 항목을 이 화면에서 수정하지 마세요.
  • 꼭 고쳐야 한다면 먼저 프로젝트를 JSON으로 내보내 두세요.

파일로 가져온 항목도 실행 방식·가중치는 비어 있습니다

파일 가져오기는 업무명·시작일·종료일·진행률만 받습니다. 그래서 가져온 직후에는 모든 항목이 실행 방식 미지정이고 진척은 입력한 진행률 그대로(수동 입력)입니다. Agile·Waterfall· Hybrid로 계산하고 싶다면 항목마다 수정을 열어 실행 방식을 지정하세요.

지연 배지와 진척 숫자는 서로 다른 값을 봅니다

한 행에서 진척 칸은 Agile 100%인데 배지는 지연 일 수 있습니다. 모순이 아니라, 두 표시가 다른 값을 보기 때문입니다.

표시 근거
진척 칸 공통 집계 결과(완료 Story 비율, 승인된 체크포인트 비율 등)
지연 배지 편집 폼에 직접 입력한 진행률

실행 방식이 미지정인 항목에서는 둘이 같은 값이라 차이가 없습니다. Agile·Waterfall·Hybrid로 전환한 항목에서만 갈라집니다. 지연 배지를 실제와 맞추려면 진행률 칸도 함께 갱신해야 합니다.

하위가 있는 항목을 저장하면 집계된 일정이 자기 값이 됩니다

시작일·종료일·진행률 칸이 비활성이어도 화면에 보이는 집계값이 그대로 저장됩니다. 평소에는 표시가 달라지지 않지만(어차피 하위에서 다시 계산하므로), 나중에 그 항목의 하위를 전부 지우면 그때 복사된 값이 그 항목 자신의 일정으로 남습니다. 원래 넣어 뒀던 값이 아닐 수 있으니 확인하세요.

WBS 코드는 언제든 바뀝니다

1.2.1은 트리에서의 위치일 뿐이라, 앞의 형제를 하나 추가하거나 지우면 달라집니다. 회의록·이메일에 코드를 박아 두지 마세요. 코드는 "지금 화면에서 찾는 법"이고, 항목의 정체성은 이름입니다.

산정 전은 0%가 아닙니다

막대가 없고 산정 전이라고 적힌 것은 아직 셀 근거가 없다는 뜻입니다. 착수 전 프로젝트가 "0% 진행"으로 보이지 않게 하려는 구분입니다. 흔한 원인:

  • Agile인데 집계 대상 Story·Bug가 없다
  • Waterfall인데 승인 체크포인트가 없다
  • Hybrid인데 α가 비어 있다
  • 하위가 없는 Summary다 (전환은 했는데 아직 자식을 안 만든 상태)

가중치를 비우는 것과 0은 다릅니다

  • 비움 = "아직 안 정했다". 형제 중 아무도 안 정했으면 예전 방식(하위 개수 평균)이 유지됩니다.
  • 0 = "이 가지는 진척에 기여하지 않는다".
  • 형제 중 일부만 넣으면 안 넣은 쪽이 평균에서 빠지고 부모에 불완전이 붙습니다. 넣으려면 형제 전체에 넣으세요.

배너 숫자와 배지 개수가 다릅니다

배너는 leaf만 세고, 배지는 Summary 행에도 붙습니다. 지연된 leaf 하나가 3단계 아래에 있으면 배지는 네 개(자신 + 조상 3), 배너는 1건입니다. 의도된 것입니다 — 접어 둔 상태에서 안쪽 지연을 놓치지 않으려고 배지는 위로 올리고, 건수는 중복되지 않게 leaf로 셉니다.

종료일 당일은 아직 지연이 아닙니다

날짜가 하루 지나야 지연이 됩니다. 그리고 진행률 100%는 종료일이 지났어도 완료로 봅니다 — 실제 완료일을 이 화면에서 기록할 수 없어 "지연 완료"를 구분할 근거가 없기 때문입니다.

영업일 개념이 없습니다

시작일~종료일은 달력일이고 주말·공휴일도 그대로 흘러갑니다. 기대 진행률도 달력일 기준의 직선입니다.

동시 편집은 마지막 저장이 이깁니다

두 사람이 같은 항목을 열어 두고 각자 저장하면, 나중 저장이 앞의 것을 조용히 덮어씁니다. 경고는 없습니다.

4. Agile — Backlog · Sprint · Board

한 줄 요약 — 세 화면은 하나의 흐름입니다. Backlog에 적고 → Sprint에 담고 → Board에서 옮깁니다. Backlog는 "무슨 일을 하는가", Sprint는 "이번 2주에 무엇을 하기로 했는가", Board는 "그 일이 지금 어디까지 왔는가"에 답합니다.

4.1 세 화면의 역할 분담

상단 메뉴에서 Agile을 누르면 Backlog로 이동하고, 그 아래에 Backlog · Sprint · Board 줄이 펼쳐집니다. Agile은 자기 화면이 없는 묶음 이름입니다.

화면 다루는 것 다루지 않는 것
Backlog (/backlog) 항목을 만들고, 유형·계층·귀속 Work Package·담당·추정을 정한다. 보관·삭제 어느 Sprint에 넣을지
Sprint (/sprint) Sprint 만들기, 항목 배정, 시작, 종료(이월 포함) 카드 옮기기, 차단
Board (/board) 카드를 네 칸 사이로 옮기기, 차단 표시, 배정 제거 Sprint 자체의 생성·시작·종료

세 화면이 나뉜 이유는 성격이 다르기 때문입니다. Backlog와 Sprint는 계획을 다루므로 표와 폼이 어울리고, Board는 실행을 다루므로 카드와 드래그가 어울립니다. Sprint 화면과 Board 화면은 고른 Sprint를 공유합니다 — Sprint 목록에서 고른 것이 Board를 열면 그대로 열려 있습니다.

프로젝트 선택은 모든 화면이 공유합니다. 화면을 옮겨도 유지됩니다.

한 항목은 세 화면에서 같은 것을 가리킵니다. Board의 카드는 별도의 데이터가 아니라 Backlog 항목입니다. 그래서 Board에서 카드를 "검토"로 옮기면 Backlog 표의 상태 열도 함께 바뀝니다.

4.2 Backlog

실행할 일을 적는 목록입니다. WBS가 범위(무엇을 만드는가)라면 Backlog는 실행(그것을 어떤 일로 쪼개 하는가)입니다. 그래서 모든 항목은 WBS의 최하위 Work Package에 귀속됩니다.

4.2.1 화면 구성 (표 열·필터·버튼)

맨 위에 프로젝트 셀렉트가 있고, 불러오는 동안 불러오는 중…이 옆에 뜹니다.

상단 안내와 배너

상황에 따라 아래가 표 위에 나타납니다. 배너의 건수는 필터를 무시하고 프로젝트 전체를 셉니다 — "미연결 3건"은 프로젝트에 대한 사실이라, 필터 때문에 숫자가 줄면 문제가 작아 보이기 때문입니다.

표시 나오는 조건
실행 방식을 지정할 Work Package가 없습니다… WBS에 Work Package가 하나도 없음. WBS 화면 링크가 붙습니다
미연결 N건 귀속 Work Package가 없는 비보관 항목 수
연결을 고쳐야 하는 항목 N건 + 제목 나열 귀속 대상이 Summary가 되었거나 사라진 비보관 항목
Sprint에 넣을 수 없는 Story·Bug가 N건 있습니다 위 문제 때문에 배정이 막힌 Story·Bug 수
… 에 귀속된 항목만 보고 있습니다. Work Package 필터가 걸려 있을 때

필터 (표 바로 위)

필터 값
Work Package 전체 / WBS 코드 + 이름 (Work Package만 나옵니다. Summary는 목록에 없습니다)
유형 전체 / Epic / Story / Bug / Task
상태 전체 / 할 일 / 진행 중 / 검토 / 완료
연결 연결 여부 전체 / 연결됨 / 미연결
보관 보관 제외(기본) / 보관만 / 보관 포함

기본값에서 하나라도 달라지면 오른쪽에 필터 해제 버튼이 나타납니다. 필터는 화면을 떠나도 유지됩니다 — 떠날 때의 시야로 돌아오는 것이 상태를 기억하는 이유입니다.

보관은 기본으로 감춥니다. 접어둔 항목이 섞이면 열린 일이 실제보다 많아 보입니다.

WBS 화면의 연결 Backlog 셀을 눌러 오면 그 Work Package로 필터가 자동으로 걸리고, 이때만 보관 포함으로 바뀝니다. WBS에서 "보관 2"를 보고 눌렀는데 빈 목록이 나오면 안 되기 때문입니다. 주소창의 조건은 곧바로 지워지므로, 이후 필터를 손으로 바꿔도 되돌아가지 않습니다.

표 열

유형 · 제목 · 귀속 Work Package · 담당 · SP · 가중치 · 상태 · (수정 / 보관·복구 / 삭제)

  • 정렬은 우선순위(높음 → 보통 → 낮음) 다음 등록 순이고, 가족이 한 덩어리로 붙습니다 — Epic 다음에 그 Story들, 각 Story 다음에 그 Task들. 제목 칸의 들여쓰기가 계층을 나타냅니다.
  • 순서를 손으로 바꾸는 기능은 없습니다. 위로 올리고 싶으면 우선순위를 높이세요.
  • 귀속 Work Package 칸은 링크입니다. 누르면 WBS 화면에서 그 항목이 펼쳐지고 강조됩니다.
  • 필터에 걸리지 않았지만 하위를 설명하려고 남긴 조상 행은 흐리게 표시됩니다. Task 하나만 검색되어도 그 Story가 무엇인지 보이게 하려는 것입니다.
  • 제목 칸에는 칩과 표시가 여러 개 붙습니다 — 4.2.5 참조.
  • 수용 조건이 있으면 제목 아래 작은 글씨로 함께 보입니다.

＋ 항목 추가 버튼은 필터 줄 오른쪽 끝에 있습니다.

＋ 항목 추가(또는 행의 수정)를 누르면 대화상자가 뜹니다.

폼이 상황에 따라 덧붙이는 안내:

  • 상위를 골랐을 때 — 하위 항목의 귀속은 상위 항목을 따릅니다. 귀속을 바꾸려면 상위 항목을 옮기세요.
  • Task인데 상위가 없을 때 — Task는 Story 또는 Bug의 하위여야 합니다.
  • Epic·Task를 고를 때 — …은(는) 진척 집계에 별도로 가산되지 않습니다.
  • 귀속 Work Package의 실행 방식이 Agile·Hybrid가 아닐 때 — 실행 방식을 바꾸라는 안내. 막지는 않습니다(초안 단계에서는 정상적인 순서입니다).

Story Point와 진척 가중치는 다른 값입니다. 포인트는 팀의 추정(속도 추세의 재료), 가중치는 진척 계산에서 이 항목이 차지하는 비중입니다. 같은 단위가 아니므로 더하거나 바꿔 쓰면 안 됩니다.

집계 대상은 Story와 Bug뿐입니다. Epic은 묶음이고 Task는 실행 상세라, Epic을 그 안의 Story와 함께 세면 같은 일을 두 번 세게 됩니다. 그래서 Epic·Task 행에는 집계 제외 칩이 붙고, 이 둘은 Sprint에 배정할 수도 없습니다.

저장할 때의 동작

  • 추가한 뒤에는 대화상자가 열린 채 남습니다. 여러 건을 연달아 적는 것이 흔하고, 아래 표에 새 행이 나타나는 것이 이미 확인 신호입니다. 수정한 뒤에는 닫힙니다.
  • 저장이 거부되면 닫히지 않고 대화상자 안에 이유가 표시되며 입력값은 그대로 남습니다.
  • 상태를 완료로 바꾸려면 확인 체크박스를 켜야 저장 버튼이 활성됩니다. 이미 완료인 항목을 다시 저장할 때는 묻지 않습니다 — 제목만 고쳐도 매번 체크하게 만들지 않으려는 것입니다.
  • Esc로 닫을 수 있고, 열리면 첫 입력 칸에 커서가 갑니다.

4.2.3 계층과 귀속 규칙

계층은 두 단만

Epic ── Story ── Task
   └── Bug  ── Task
  • Epic은 다른 항목의 하위가 될 수 없습니다.
  • Story·Bug의 상위는 Epic뿐이고, Task의 상위는 Story 또는 Bug뿐입니다.
  • Task는 상위 없이 존재할 수 없습니다. Work Package에 직접 붙일 수 없습니다.
  • 이미 하위를 가진 항목의 유형을 바꿔서 그 하위가 갈 곳이 없어지면 거부됩니다. (예: Task를 달고 있는 Story를 Epic으로 바꾸려는 경우)
  • 자기 자신 또는 자기 하위를 상위로 지정하면 거부됩니다.

Epic·Story·Bug는 계층 노드가 아닙니다. WBS처럼 1.2.1 같은 코드를 만들지 않고, 들여쓰기는 화면 표시일 뿐입니다.

귀속은 상속됩니다 — 검증이 아니라 불가능

  • 상위가 있는 항목의 귀속 Work Package는 언제나 상위 것입니다. 폼에서 그 셀렉트가 잠기는 이유입니다.
  • 상위를 다른 Work Package로 옮기면 하위 전체가 따라갑니다. 그래서 Story를 다른 Epic 아래로 옮기는 순간, 그 Story와 Task들의 귀속이 조용히 새 Epic의 것으로 바뀝니다 — 잠긴 셀렉트에 바뀐 값이 보이니 저장 전에 확인하세요.
  • 귀속은 최하위 Work Package에만 됩니다. Summary를 지정하면 거부됩니다(셀렉트에 나오지도 않습니다).
  • 요청이 상위와 다른 Work Package를 지정하면 조용히 고치지 않고 거부합니다 — "Task를 다른 Work Package로 옮겼다"고 착각하면 안 되기 때문입니다.

4.2.4 보관과 삭제

다 쓴 항목은 삭제 대신 보관하세요.

보관 삭제
남는 것 항목 전체(마지막 상태 포함) 아무것도
되돌리기 복구 버튼 불가
표에서 기본 필터에서 감춰짐, 제목에 취소선 + 보관 칩 사라짐
진척 집계 빠짐 빠짐
Sprint 배정 배정 대상에서 제외 —
  • 보관해도 상태는 그대로입니다. 어느 상태에서 접었는지가 기록의 일부이기 때문입니다.
  • 열려 있는 Sprint(계획 중 또는 실행 중)에 배정된 항목은 보관·삭제가 모두 거부됩니다. 버튼이 비활성되고 툴팁에 어느 Sprint인지 나옵니다. Sprint에서 제거(Board 화면)한 뒤 다시 시도하세요. 그대로 지우면 그 Sprint의 배정 기록까지 사라지기 때문입니다.
  • 하위 항목이 있으면 삭제할 수 없습니다. 툴팁에 몇 건인지 나옵니다. 하위를 먼저 옮기거나 지우세요. (보관은 하위가 있어도 됩니다.)
  • 삭제에는 확인 대화상자가 없습니다. 누르면 바로 지워집니다.
  • 항목을 지우면 그 항목에 걸려 있던 RAID 연결만 끊기고 RAID 항목 자체는 남습니다.

WBS 쪽에서 오는 제약 — 살아 있는 Backlog가 붙어 있는 WBS 항목은 삭제되지 않습니다. 반대로 보관된 항목만 남아 있으면 연결을 끊고 지웁니다. 그래서 "WBS 항목을 지우고 싶은데 Backlog가 붙어 있다"의 답은 보관입니다.

4.2.5 경고 표시가 뜻하는 것

제목 칸에 칩으로 붙습니다. 경고 칩은 한 번에 하나만 보이고, 나쁜 것부터 우선합니다 — 아예 쓸 수 없는 연결이 실행 방식만 바꾸면 되는 것보다 급하기 때문입니다.

칩 뜻 무엇을 해야 하나
연결 끊김 귀속 id는 있는데 그 WBS 항목을 찾을 수 없다 수정에서 Work Package를 다시 고릅니다
Summary 연결 귀속 대상이 나중에 Summary로 바뀌었다 최하위 Work Package로 다시 연결합니다
미연결 귀속 Work Package가 없다 초안이면 정상. Sprint에 넣기 전에는 연결해야 합니다
실행 방식 확인 귀속 Work Package의 실행 방식이 Waterfall이거나 미지정 WBS에서 Agile 또는 Hybrid로 바꿉니다. 배정은 막히지 않습니다

경고가 아닌 다른 칩들:

칩 뜻
보관 접어둔 항목. 제목에 취소선
(Sprint 이름) 그 열린 Sprint에 배정되어 있다. 보관·삭제가 막히는 이유
차단 Board에서 차단 표시된 상태. 마우스를 올리면 사유가 보입니다

높음 / 보통 / 낮음 우선순위. 높음은 붉게 표시됩니다

앞의 셋(연결 끊김·Summary 연결·미연결)이 있으면 Sprint에 배정할 수 없습니다. 실행 방식 확인은 경고일 뿐 배정을 막지 않습니다 — 고쳐야 할 상태이지 깨진 상태는 아닙니다.

4.3 Sprint

계획을 다루는 화면입니다. 만들고, 담고, 시작하고, 종료합니다.

4.3.1 화면 구성

툴바 — 프로젝트 셀렉트 · 단일 팀 배지(마우스를 올리면 이유가 뜹니다) · ＋ Sprint 추가

Sprint 목록 — 한 줄에 하나씩, 시작일이 늦은 것부터 나옵니다. 지금 계획하거나 돌리고 있는 것이 맨 위에 있게 하려는 것입니다.

Sprint 3   실행 중   2026-09-01 ~ 2026-09-12      4/9건 · 21/40 SP · 차단 1
부분 뜻
상태 계획 / 실행 중 / 종료
4/9건 완료 항목 / 배정 항목
21/40 SP 완료 Story Point / 배정 Story Point
차단 N 차단된 항목 수 (0이면 표시 안 함, 열린 Sprint에서만 의미 있음)
이월 N 이월된 항목 수 (0이면 표시 안 함, 종료된 Sprint에서만 채워짐)

고른 Sprint의 상세가 목록 아래에 펼쳐집니다.

  • 이름 + 상태 배지
  • 기간. 실행 중이면 N일 남음 / 오늘 종료 / 종료일 N일 경과가 붙습니다(종료일 포함 계산)
  • 종료된 것이면 종료 YYYY-MM-DD
  • 목표: … 또는 Sprint Goal이 비어 있습니다.
  • 오른쪽에 버튼들 — 시작 / 종료 / 수정 / 삭제 (상태에 따라 나타나는 것이 다릅니다)
  • 항목 배정 줄 (종료된 Sprint에는 없습니다)
  • 맨 아래 이 Sprint 의 Board 열기 링크

추가·수정 대화상자의 필드는 이름 · 시작일 · 종료일 · Sprint Goal 넷뿐입니다. 종료일이 시작일보다 앞서면 저장 버튼이 비활성되고 그 자리에서 알려 줍니다.

4.3.2 계획 → 배정 → 시작 → 종료 흐름

① ＋ Sprint 추가        이름·기간·목표          → 상태: 계획
② 항목 배정             셀렉트에서 골라 [배정]   → 여러 번 반복
③ [시작]                                        → 상태: 실행 중
④ Board에서 실행        카드 이동·차단
⑤ [종료] + 이월 선택                            → 상태: 종료 (되돌릴 수 없음)

② 배정 — 항목 배정 셀렉트에는 유형 · 제목 (N SP) 형태로 나옵니다. 항목을 고르면 배정 버튼이 활성됩니다. 고를 것이 없으면 셀렉트에 배정할 수 있는 항목이 없습니다라고 적힙니다.

셀렉트에 나오는 것은 완료 가능한 Story·Bug이면서 다른 열린 Sprint에 들어 있지 않은 것뿐입니다. 구체적으로 아래를 모두 만족해야 합니다.

  • 유형이 Story 또는 Bug (Epic·Task는 불가)
  • 보관되지 않음
  • 귀속 Work Package가 있고, 그것이 Summary가 아니고, 사라지지도 않았음
  • 계획 중이든 실행 중이든 다른 Sprint에 살아 있는 배정이 없음

③ 시작 — 시작하는 순간 배정된 항목들의 Story Point가 그 시점 값으로 각인됩니다. 계획 중에는 추정이 계속 바뀌므로, 기억할 값은 팀이 실제로 약속한 숫자이기 때문입니다. 이 값이 종료된 Sprint의 계획 SP가 됩니다.

⑤ 종료 — 대화상자가 뜨고 아래를 알려 줍니다.

  • 완료된 항목은 이 Sprint의 실적으로 기록되고, 미완료 항목 N건은 이월로 남습니다
  • 항목의 상태는 바뀌지 않습니다 — 종료는 Sprint의 진술이고, 일이 아직 검토에 있는지는 항목의 사정입니다. 이 분리가 이월을 가능하게 합니다
  • 미완료 항목을 옮길 Sprint를 고를 수 있습니다(다음 절)

종료는 되돌릴 수 없습니다. 종료된 Sprint는 수정·삭제·배정 변경·Board 이동이 모두 막히고, 그 숫자는 이후 무슨 일이 있어도 움직이지 않습니다.

4.3.3 이월 (실적이 두 번 세어지지 않는 이유 포함)

종료 대화상자의 미완료 항목을 옮길 Sprint 셀렉트에는 지금은 옮기지 않음과 아직 종료되지 않은 다른 Sprint들이 나옵니다. 옮길 곳이 하나도 없으면 옮길 Sprint가 없습니다. 나중에 새 Sprint를 만들어 배정할 수 있습니다.라고 적힙니다.

⚠️ 셀렉트의 기본값은 지금은 옮기지 않음이 아니라 목록의 첫 Sprint입니다. 확인하지 않고 종료를 누르면 미완료 항목이 그 Sprint로 넘어갑니다. 옮기고 싶지 않다면 직접 골라야 합니다.

종료할 때 각 항목에 찍히는 결과

결과 배지 언제
완료 종료 시점에 상태가 완료였다
이월 종료 시점에 완료가 아니었다
제외 Sprint가 끝나기 전에 Board에서 제거했다

왜 두 번 세어지지 않나

한 배정 행은 한 Sprint의 한 항목에 대한 기록이고, 종료할 때 그 행에 결과가 한 번 찍힙니다. 이월은 원래 행을 고치는 것이 아니라 다음 Sprint에 새 행을 만드는 것입니다.

Sprint 3 : [Story A] → 종료 시 미완료 → 결과 "이월"   (완료 실적 0)
Sprint 4 : [Story A] 새 배정 행 → 여기서 완료 → 결과 "완료"  (완료 실적 1)

그래서 Story A의 완료 실적은 Sprint 4에만 쌓입니다. Dashboard의 속도 추세에서도 한 번만 셉니다.

종료된 Sprint의 숫자는 그 뒤에 무슨 일이 있어도 변하지 않습니다. 항목을 나중에 재오픈하거나 다른 Sprint에서 완료해도 마찬가지입니다 — 종료된 Sprint는 자기가 찍어 둔 결과만 말하고, 계획 SP도 시작 시점에 각인한 값을 씁니다.

4.3.4 이 화면의 규칙 (왜 버튼이 비활성인가)

버튼 언제 보이나 언제 비활성인가 / 왜
시작 상태가 계획일 때만 이미 실행 중인 Sprint가 있으면 비활성. 툴팁: 이미 실행 중인 Sprint가 있습니다 (단일 팀)
종료 상태가 실행 중일 때만 항상 활성
수정 종료가 아닐 때 항상 활성. 종료된 Sprint는 버튼 자체가 사라집니다(결과는 이력이므로)
삭제 상태가 계획일 때만 배정된 항목이 하나라도 있으면 비활성. 툴팁: 배정된 항목이 있어 삭제할 수 없습니다
배정 종료가 아닐 때 항목을 고르지 않으면 비활성

그 밖에 서버가 거부하는 것들 — 거부되면 화면 위쪽에 빨간 글씨로 이유가 나옵니다.

  • 같은 이름의 Sprint를 두 개 만들 수 없습니다.
  • 종료일이 시작일보다 앞설 수 없습니다.
  • 실행 중인 Sprint는 삭제할 수 없습니다 — 먼저 종료해야 합니다. 종료된 것은 이력이라 지울 수 없습니다.
  • 종료된 Sprint에는 배정·제거·Board 이동이 되지 않습니다.
  • 한 항목은 열린 Sprint 하나에만 들어갑니다. 계획 중인 다음 Sprint에 미리 넣어 두는 것도 막습니다 — 지금 하는 일을 다음 계획에도 세면 계획이 두 배가 됩니다.
  • 자기 자신으로는 이월할 수 없고, 종료된 Sprint로도 이월할 수 없습니다.

왜 실행 중 Sprint가 하나뿐인가 — 이 앱은 한 프로젝트에 한 팀을 전제합니다. 팀이 하나면 동시에 도는 Sprint도 하나이고, 이 규칙이 "한 항목이 두 Sprint에서 동시에 세어지는 일"을 원천적으로 막아 줍니다. 툴바의 단일 팀 배지가 그 전제를 표시합니다.

4.4 Board

실행을 다루는 화면입니다. 카드를 네 칸 사이로 옮깁니다.

4.4.1 화면 구성 (네 칸과 카드에 보이는 것)

툴바 — 프로젝트 셀렉트 · Sprint 셀렉트. Sprint 셀렉트에는 이름 (상태) 형태로 모든 Sprint가 나옵니다(계획·실행 중·종료 전부). 처음 들어오면 실행 중인 Sprint가 기본으로 열리고, 없으면 목록의 첫 번째가 열립니다. Sprint 화면에서 고른 것이 그대로 열립니다.

헤더 — 이름 + 상태 배지, 기간(실행 중이면 남은 기간), 목표: …, 오른쪽에 Sprint 계획으로 링크.

  • 계획 상태이면 아직 시작하지 않은 Sprint 입니다. 카드를 옮길 수는 있지만, 실적은 시작한 뒤부터 의미가 있습니다.
  • Sprint가 하나도 없으면 Sprint 화면으로 가는 안내가 나옵니다.

네 칸 — 할 일 · 진행 중 · 검토 · 완료. 칸 머리에 그 칸의 카드 수가 적히고, 비어 있으면 없음이라고 표시됩니다. (화면이 좁으면 두 칸씩 두 줄로 접힙니다.)

카드에 실제로 보이는 것

위에서부터 순서대로입니다. 해당 값이 없으면 그 줄은 나오지 않습니다.

위치 내용

머리 오른쪽 Story Point (없으면 표시 안 함)

종료된 Sprint의 Board는 읽기 전용입니다. 카드를 끌 수 없고 차단·제거 버튼도 사라집니다. 대신 아래에 이 Sprint에서 제외된 항목 N건 — 제목들 이 표시됩니다 — 왜 빠졌는지가 이력이기 때문입니다. (열린 Sprint에서는 제거된 항목이 아예 보이지 않습니다.)

제거는 배정만 뺍니다. Backlog 항목 자체는 그대로 남고, 그 Sprint의 기록에는 제외로 남습니다.

4.4.2 카드 옮기기와 완료 확인

드래그해서 다른 칸에 놓습니다. 놓을 수 있는 칸은 테두리가 강조됩니다. 카드를 옮기는 다른 방법(버튼·메뉴)은 없습니다.

완료 칸으로 옮길 때만 확인 대화상자가 뜹니다.

완료 처리
  <카드 제목>
  수용 조건: …            ← 없으면 "등록된 수용 조건이 없습니다."
  완료되지 않은 하위가 N건 있습니다. 그래도 완료로 처리할 수 있습니다.   ← 하위가 남았을 때만
  수용 조건과 완료 기준(Definition of Done)을 확인했습니까?
  [확인하고 완료]  [취소]
  • 왜 묻는가 — 시스템에 Definition of Done이 저장되어 있지 않습니다. 그러니 기준을 충족했다는 것은 누르는 사람만 증명할 수 있습니다.
  • 하위 Task를 다 끝내도 Story가 자동으로 완료되지 않습니다. 대신 남은 하위 수를 카드와 이 대화상자에 실어 사람이 판단하게 합니다. 하위가 남아 있어도 완료할 수 있습니다 — 불필요해진 Task가 남는 것은 정상입니다.
  • 완료에서 다른 칸으로 빼는 것(재오픈)은 묻지 않습니다. 이때 완료 시각만 지워지고, 이미 종료된 Sprint에 찍힌 완료 결과는 그대로 남습니다. 그 상태가 되면 카드에 지난 Sprint에서 완료로 기록된 항목입니다 (지금은 미완료).가 붙습니다 — 지금의 상태와 과거의 실적은 다른 사실이기 때문입니다.
  • Backlog 편집 폼에서 상태를 완료로 바꿀 때도 같은 확인을 요구합니다. 한쪽만 막으면 절차가 장식이 되기 때문입니다.
  • 계획 상태의 Sprint에서도 카드를 옮길 수는 있습니다(안내문이 뜹니다).

4.4.3 차단

카드 바닥의 차단 버튼을 누르면 사유를 적는 작은 대화상자가 뜹니다(예: 외부 API 응답 대기). 사유는 비워 둘 수 있습니다.

  • 차단은 칸(상태)과 별개입니다. 카드는 있던 칸에 그대로 있고, 테두리가 붉어지며 사유가 카드에 적힙니다. 상태를 한 칸 늘리지 않은 이유는 "차단"이 할 일 → 진행 중 → 검토 → 완료의 중간에 끼어들면 흐름이 깨지기 때문입니다.
  • 차단된 항목은 완료할 수 없습니다. 먼저 차단 해제를 누르세요.
  • 차단된 카드에만 관련 RAID가 펼쳐집니다. 그 Backlog 항목에 직접 연결된 것과, 그 항목이 귀속된 Work Package에 연결된 것을 함께 보여 주고, 종결된 RAID는 제외합니다 — 이미 닫힌 것은 아무것도 막고 있지 않기 때문입니다. 열려 있는 모든 카드에 위험 목록을 달면 보드가 읽히지 않으므로 차단된 카드에만 폅니다.
  • 차단은 Board를 통해서만 켜고 끕니다. Backlog 표에서는 차단 칩으로 보이기만 하고 해제할 수 없습니다. (여기서 오는 함정은 발견한 결함 참조.)

4.5 실무 예시

가상의 프로젝트 "사내 예약 시스템" 으로 2주 Sprint 한 사이클을 처음부터 끝까지 따라갑니다.

준비 — WBS와 실행 방식 (Agile 화면 이전)

WBS에 이렇게 만들어 두었다고 합시다.

1   요구 분석            (Summary)
2   예약 기능            (Summary)
2.1   예약 등록 화면      (Work Package · 실행 방식: Agile)
2.2   예약 조회 API       (Work Package · 실행 방식: Agile)
3   배포                 (Work Package · 실행 방식: Waterfall)

구성원도 미리 등록합니다(RACI 화면 아래쪽) — 김PL, 이개발, 박QA. 담당자 셀렉트는 여기서 등록한 사람만 보여 줍니다.

1일차 — Backlog 작성

Backlog 화면에서 ＋ 항목 추가로 다음을 만듭니다.

유형 제목 상위 귀속 담당 SP
Epic 예약 흐름 — 2.1 예약 등록 화면 — —
Story 사용자가 날짜를 골라 예약한다 예약 흐름 (상속: 2.1) 이개발 5
Story 예약 확인 메일을 받는다 예약 흐름 (상속: 2.1) 이개발 3
Task 메일 템플릿 작성 예약 확인 메일을… (상속: 2.1) 박QA —
Bug 중복 예약이 저장된다 — 2.2 예약 조회 API 이개발 2
Story 관리자가 예약을 취소한다 — (미연결) — 8

여기서 일어나는 일:

  • Epic을 상위로 고르는 순간 귀속 셀렉트가 잠기고 2.1 예약 등록 화면이 자동으로 들어갑니다.
  • Task는 상위를 고르지 않으면 저장되지 않습니다.
  • 마지막 Story는 아직 어디에 붙일지 몰라 미연결로 뒀습니다. 화면 위에 미연결 1건 배너가 뜨고, 행에 미연결 칩이 붙으며, Sprint에 넣을 수 없는 Story·Bug가 1건 이라고 알려 줍니다.
  • Epic 행과 Task 행에는 집계 제외 칩이 붙습니다.
  • 표는 높음 → 보통 → 낮음 순으로 정렬되고, Epic 밑에 그 Story들이, Story 밑에 Task가 붙어 나옵니다.

미연결 Story를 정리합니다. 수정을 눌러 귀속을 2.2 예약 조회 API로 지정하면 배너가 사라집니다.

2일차 — Sprint 계획과 시작

Sprint 화면 → ＋ Sprint 추가

이름        Sprint 1
시작일      2026-09-14
종료일      2026-09-25
Goal        예약 등록과 확인 메일까지 끝낸다

목록에서 Sprint 1을 고르고 항목 배정 셀렉트를 엽니다. 여기 나오는 것은 Story 3건과 Bug 1건뿐입니다 — Epic과 Task는 목록에 아예 없습니다.

세 건을 배정합니다(5 + 3 + 2 = 10 SP). 이제 목록 줄이 이렇게 보입니다.

Sprint 1   계획   2026-09-14 ~ 2026-09-25    0/3건 · 0/10 SP

Backlog 화면으로 돌아가 보면 그 세 행에 Sprint 1 칩이 붙어 있고, 보관·삭제 버튼이 비활성되어 있습니다.

시작을 누릅니다. 이 순간 10 SP가 각인됩니다. 상태가 실행 중이 되고, 다른 Sprint의 시작 버튼은 이미 실행 중인 Sprint가 있습니다 (단일 팀) 툴팁과 함께 비활성됩니다.

3~9일차 — Board에서 실행

Board 화면을 엽니다(Sprint 1이 이미 열려 있습니다). 헤더에 9일 남음이 보입니다.

  • 사용자가 날짜를 골라 예약한다 카드를 할 일 → 진행 중으로 끕니다. 확인 없이 바로 옮겨 집니다.
  • 며칠 뒤 진행 중 → 검토 → 완료로 옮깁니다. 완료로 놓는 순간 대화상자가 뜨고, 등록해 둔 수용 조건이 그대로 보입니다. 확인하고 완료를 누릅니다.
  • 예약 확인 메일을 받는다를 완료로 옮기려 하자 대화상자에 완료되지 않은 하위가 1건 있습니다. 그래도 완료로 처리할 수 있습니다. 가 함께 뜹니다 (Task 메일 템플릿 작성이 남아 있습니다). 그 Task가 실제로는 필요 없어졌다고 판단하여 그대로 완료합니다.

7일차 — 차단이 생기다

중복 예약이 저장된다 Bug가 외부 DB 팀의 응답을 기다리게 됐습니다.

  1. 카드의 차단을 누르고 사유에 DB팀 유니크 제약 검토 대기라고 적습니다.
  2. 카드가 붉은 테두리로 바뀌고 사유가 카드에 적힙니다. 칸은 진행 중 그대로입니다.
  3. RAID 화면에서 이슈 DB 유니크 제약 미확정을 등록하고, 연결 대상으로 이 Bug(또는 귀속 Work Package 2.2)를 지정합니다.
  4. Board로 돌아오면 차단 카드 아래에 그 이슈가 소유자와 함께 표시됩니다 — "왜 막혔나"의 답이 카드 옆에 있습니다.
  5. Sprint 목록 줄에도 · 차단 1이 붙습니다.

이 상태에서 카드를 완료로 끌면 확인 대화상자를 지나 서버가 거부하고, 화면 맨 위에 차단된 항목은 완료할 수 없습니다. 차단을 먼저 해제하세요.가 뜹니다. 보드 아래쪽을 보고 있었다면 메시지를 놓치기 쉬우니, 완료 전에 차단 해제부터 누르세요.

10일차 — Sprint 종료와 이월

Bug는 끝내 풀리지 않았습니다. 종료 전에 다음 Sprint를 먼저 만들어 둡니다.

Sprint 2   2026-09-28 ~ 2026-10-09   Goal: 예약 취소와 중복 예약 결함

Sprint 1을 고르고 종료를 누릅니다.

Sprint 종료
  Sprint 1
  완료된 항목은 이 Sprint의 실적으로 기록되고, 미완료 항목(1건)은 이월로 남습니다.
  항목의 상태는 바뀌지 않습니다.

  미완료 항목을 옮길 Sprint  [ Sprint 2 (계획) ▾ ]    ← 기본값이 이미 Sprint 2입니다
  [종료]  [취소]

종료 후 결과:

Sprint 1   종료   2026-09-14 ~ 2026-09-25    2/3건 · 8/10 SP · 이월 1
Sprint 2   계획   2026-09-28 ~ 2026-10-09    0/2건 · 0/10 SP
  • Sprint 1의 Board는 읽기 전용이 됩니다. Bug 카드에 이월 배지가 붙습니다.
  • Bug는 Sprint 2에 새 배정으로 들어가 있습니다. 상태는 여전히 진행 중이고 차단도 그대로 입니다 — 종료는 항목의 상태를 건드리지 않습니다.
  • 아직 배정하지 않은 관리자가 예약을 취소한다(8 SP)를 Sprint 2에 추가 배정합니다.

다음 사이클 — 실적이 두 번 세어지지 않는지 확인

Sprint 2를 시작하고, DB팀 회신이 와서 Bug 카드의 차단 해제 후 완료로 옮깁니다. Sprint 2를 종료하면:

Sprint 1   종료   2/3건 ·  8/10 SP · 이월 1      ← 그대로. 절대 움직이지 않습니다
Sprint 2   종료   2/2건 · 10/10 SP

Bug의 완료 실적은 Sprint 2에만 쌓였습니다. Dashboard의 완료 Story Point 추세도 8 → 10으로 그려지고, 같은 일을 두 번 세지 않습니다.

뒷정리

  • 다 쓴 Epic이나 더 안 할 Story는 삭제하지 말고 보관하세요. 마지막 상태가 남고, 나중에 보관만 필터로 다시 볼 수 있습니다.
  • WBS에서 2.1 예약 등록 화면을 지우려 하면 거부됩니다. 붙어 있는 Backlog를 다른 Work Package로 옮기거나 보관한 뒤에 다시 시도하세요.

4.6 주의할 점

계획과 실행이 섞이지 않게

  • Story Point와 진척 가중치를 같은 것으로 쓰지 마세요. 하나는 팀의 추정(속도의 재료), 하나는 진척 계산에서의 비중입니다. 더하거나 바꿔 쓰면 두 숫자가 모두 의미를 잃습니다.
  • Epic·Task는 진척에도, Sprint에도 들어가지 않습니다. 실행의 단위는 Story와 Bug입니다.
  • 차단은 상태가 아닙니다. 차단해도 카드는 그 칸에 남습니다. "지금 어느 단계인가"와 "지금 막혀 있는가"는 다른 질문입니다.
  • 보관도 상태가 아닙니다. 보관해도 마지막 상태가 남습니다.

되돌릴 수 없는 것

  • Sprint 종료는 되돌릴 수 없습니다. 종료 전에 이월 대상을 반드시 확인하세요 — 셀렉트의 기본값이 지금은 옮기지 않음이 아닙니다.
  • Backlog 항목 삭제에는 확인 대화상자가 없습니다. 지우기 전에 보관을 먼저 고려하세요.
  • 이월할 Sprint가 필요하면 종료하기 전에 만들어 두는 편이 편합니다(나중에 배정해도 되지만, 종료 대화상자에서 한 번에 끝내는 것이 흔한 흐름입니다).

WBS 항목이 삭제되지 않는다 살아 있는 Backlog가 붙어 있습니다. 옮기거나 보관하세요
다른 화면의 숫자가 낡아 보인다 화면마다 캐시가 있습니다. 그 화면으로 다시 들어가면 갱신됩니다

Agile 밖으로 이어지는 것

  • Board에서 완료해도 WBS의 실제 완료일은 채워지지 않습니다. Sprint가 끝난 것과 산출물이 완료된 것은 다른 사실이고, 한 Sprint가 여러 Work Package에 걸칠 수 있기 때문입니다.
  • 간트의 Sprint 레인은 Sprint당 한 줄입니다. 여러 Work Package에 걸쳐도 반복해 그리지 않습니다.
  • Backlog 담당자는 RACI 역할이 아닙니다. RACI 화면 행 머리에 참고로 보이지만, 담당자를 바꿔도 그 업무의 A·R은 움직이지 않습니다.
  • 귀속 Work Package의 실행 방식이 Agile 또는 Hybrid여야 Story·Bug의 완료가 진척으로 올라갑니다. 실행 방식 확인 칩이 보이면 WBS에서 먼저 바꾸세요.

5. 간트 차트

WBS에 입력한 일정을 시간축에 펼쳐 놓고, 계획이 스스로 모순되는지(선후행 위반) 와 계획 대비 현실이 밀렸는지(지연) 를 한 화면에서 구분해 보는 곳입니다.

간트 화면은 읽는 화면입니다. 일정을 고치는 곳은 WBS이고, 여기서 직접 바꿀 수 있는 것은 선후행 관계와 일정 재계산 두 가지뿐입니다. 나머지는 전부 서버가 판정해 내려준 결과를 그리는 것입니다.

화면 맨 위에는 프로젝트 선택 드롭다운, 오른쪽에 임계 경로 강조 체크박스와 일정 재계산 버튼이 있습니다. 체크박스는 임계 경로로 판정된 업무가 하나라도 있을 때만 나타납니다 — 강조할 것이 없는데 체크박스만 있으면 켜도 아무 일이 없어 고장처럼 보이기 때문입니다.

차트가 그려지지 않는 두 경우는 각각 다른 문구로 알려 줍니다.

상황 화면 문구
WBS 항목이 하나도 없음 WBS 항목이 없습니다. WBS 화면에서 업무를 먼저 등록해 주세요.
항목은 있으나 날짜가 하나도 없음 일정이 입력된 항목이 없습니다. WBS 화면에서 시작일과 종료일을 입력하면 차트가 표시됩니다.

5.1 차트 읽는 법

화면의 구성

차트는 좌우 두 칸입니다.

  • 왼쪽(업무 칸, 고정 폭) — 머리글은 업무. 그 아래에 Sprint 이름 줄(있을 때)이 오고, 이어서 WBS 순서 그대로 업무 행이 늘어섭니다. 각 행은 WBS 코드 · 업무명 · 상태 배지이고, 업무명은 계층 깊이만큼 들여쓰기됩니다. 하위가 있는 항목(Summary)은 굵은 글씨입니다.
  • 오른쪽(타임라인, 가로 스크롤) — 위에 축(월 띠 + 일 칸), 그 아래 Sprint 레인, 그 아래 업무 막대.

날짜 축

  • 위 줄은 월입니다. 차트 범위가 한 해 안이면 9월, 해를 넘기면 2026.09처럼 적습니다.
  • 아래 줄은 일입니다. 날짜 칸은 항상 다 그리지만 숫자는 칸이 넓을 때만 적습니다. 칸 폭은 전체 기간에 따라 자동으로 줄어듭니다 — 약 60일 이하면 26px, 120일 이하면 16px, 그보다 길면 8px이고, 8px일 때는 날짜 숫자가 아예 사라집니다. 몇 년짜리 계획이 화면 몇 킬로미터로 늘어나지 않게 하려는 것이고, 숫자가 사라진 자리를 메우는 것이 툴팁입니다(§5.7).
  • 차트 양 끝에 3일씩 여백을 둡니다. 첫 막대가 테두리에 딱 붙지 않게 하려는 것입니다.

한 행에 쌓인 세 가지 일정

이 화면의 핵심입니다. 행을 셋으로 늘리지 않고 한 행 안에 위에서부터 세 줄을 쌓습니다. 행을 셋으로 늘리면 접어둔 WBS의 이점이 사라지고, 같은 업무의 세 일정을 눈으로 잇기가 오히려 어려워지기 때문입니다.

위치 표시 무엇인가 어디서 오는가
행의 위쪽 얇은 회색 막대 (높이 4px, 반투명) 기준 일정 (Baseline) — 승인 당시 약속한 일정 Dashboard → 진척 탭에서 승인한 기준선
행의 가운데 굵은 막대 (높이 16px, Summary는 8px) 현재 계획 — 지금 WBS에 들어 있는 시작일~종료일 WBS 화면
행의 아래쪽 얇은 초록 막대 (높이 4px) 실적 — 실제로 언제 시작해 언제 끝났는가 저장된 실적 값 (§5.9 참고)
막대 오른쪽 바깥 작은 삼각 표식 ▶ 예상 종료 — 지금 시점에서 다시 예측한 종료일 저장된 예상 종료 값 (§5.9 참고)

세 줄이 서로 어긋난 만큼이 그대로 "약속 대비 계획이 밀린 양"과 "계획 대비 실제가 밀린 양"입니다.

  • 기준 일정 막대는 기준선이 승인된 경우에만 그립니다. 없으면 아예 안 그리고 범례에 기준 일정 미등록이라고 적습니다. 현재 계획을 기준선 자리에 복사해 그리지 않습니다 — 그렇게 하면 두 줄이 영원히 겹쳐서 계획이 아무리 밀려도 초과를 볼 수 없게 됩니다.
  • 실적 막대는 종료 실적이 없으면 기준일까지 열어 두고, 반투명(60%)으로 그립니다. "시작은 했고 아직 안 끝났다"를 흐린 끝으로 말하는 것입니다.
  • 예상 종료 표식은 현재 계획의 종료일과 다를 때만 나타납니다. 같으면 표식이 계획 막대 끝에 겹쳐 아무 정보도 주지 못합니다. 이 표식이 기준 종료일을 넘겼으면 빨간색, 아니면 회색입니다.

막대의 색과 외곽선

채움 색은 지연 상태, 점선 외곽선은 선후행 위반, 실선 외곽선은 임계 경로입니다. 이 셋은 서로 다른 것을 말하므로 표현 수단도 겹치지 않게 나눠 두었습니다.

계획 막대는 상태 색의 옅은 배경(32% 투명, Summary는 50%)이고, 그 위에 진행률만큼 같은 색의 진한 채움이 덮입니다. 그래서 "이 업무의 상태"와 "얼마나 찼는지"를 한 막대에서 같이 읽습니다.

각 행 오른쪽 끝에 알약 모양 배지가 붙습니다. 문구는 일정 미정 / 시작 전 / 정상 / 지연 위험 / 지연 5일 / 완료 여섯 가지이고, 지연일 때만 경과 일수가 함께 붙습니다. 배지에 마우스를 올리면 왜 그 판정인지 한 줄로 설명합니다.

지연 위험 기대 진행률 25%, 실제 0% (25%p 부족)

지연은 이렇게 판정됩니다

지연은 입력값이 아니라 계산값입니다. 어디에도 지연 일수를 손으로 적는 칸이 없습니다. 순서대로 이 규칙을 적용합니다.

  1. 진행률이 100%면 무조건 완료 입니다. 종료일이 지났어도 그렇습니다 — 실제 완료일을 기록하지 않으므로 "지연 완료"를 구분할 근거가 없습니다.
  2. 시작일이나 종료일이 비어 있으면 일정 미정. 막대도 그리지 않습니다.
  3. 기준일이 시작일보다 이전이면 시작 전.
  4. 기준일이 종료일보다 이후이면 지연. 경과 일수 = 종료일부터 기준일까지의 날수. 종료일 당일은 아직 지연이 아닙니다 — 그날이 지나야 지연입니다.
  5. 그 밖에는 기대 진행률과 비교합니다. 기대 진행률 = 경과일 ÷ 계획일 × 100 (양끝 포함, 소수점 반올림, 100 상한). 예: 9월 7일~9월 18일(12일) 업무를 9월 9일에 보면 경과 3일 → 기대 25%. 실제 진행률이 기대보다 낮으면 지연 위험, 같거나 높으면 정상입니다.

기대 진행률은 계획 기간에 대한 단순 선형입니다. 공수 산정도, 실제 착수일도 없는 상태에서 이보다 정교한 가중치를 둘 근거가 없고, 선형이라야 사용자가 값을 미리 예측할 수 있습니다.

기준일은 서버가 정합니다. 응답에 referenceDate를 함께 실어 보내고, 범례 오른쪽 끝과 차트의 빨간 점선이 모두 그 날짜를 씁니다. 브라우저 시계를 쓰면 한 응답 안의 행들이 서로 다른 "오늘"로 판정되거나, 밤새 열어둔 탭에서 오늘 선과 배지가 어긋납니다.

Summary 행에도 배지가 붙습니다. 접어둔 상태에서 하위의 지연을 놓치면 안 되기 때문입니다. 다만 상단 배너의 건수는 leaf(최하위 업무)만 셉니다 — Summary는 하위의 지연을 이미 반영하고 있어 같이 세면 한 건이 레벨 수만큼 중복 집계됩니다. 그래서 "지연 2건"인데 배지는 4개 보이는 것이 정상입니다.

5.2 상단 배너와 경고

차트 위에 최대 여섯 종류의 안내 줄이 순서대로 쌓입니다. 조건에 맞는 것만 나타납니다.

6 인수 대기 (흐린 글씨) 실행이 100%인데 인수가 남은 항목이 있을 때 실행이 끝났지만 인수가 남은 업무가 1건 있습니다 — 2.1 화면 설계.
7 선후행 위반 (보라) 선행보다 먼저 시작하는 업무가 있을 때 선행 업무보다 먼저 시작하는 업무가 1개 있습니다 — 3.1 통합 테스트. 일정 재계산으로 자동 조정할 수 있습니다.
8 임계 경로 (중립색) 임계 경로 업무가 있을 때 임계 경로 3개 업무 · 2026-08-24 ~ 2026-09-30 (38일) — 2.3 … → 3.1 … → 3.2 …. 아래 줄에 이 업무들은 여유가 없어, 하루 밀리면 프로젝트 종료일도 하루 밀립니다. 와 다음으로 촉박한 업무는 2.2 서버 개발 (여유 2일)입니다.

색을 세 갈래로 나눈 이유가 있습니다.

  • 주황은 "계획 대비 현실이 밀렸다"(지연),
  • 보라는 "계획이 스스로 모순된다"(선후행 위반·기준 초과),
  • 중립색은 "판단에 필요한 정보"(임계 경로)입니다.

지연과 위반은 대응 방법이 완전히 다르기 때문에(전자는 일을 당기거나 일정을 늦추는 것, 후자는 관계를 고치거나 재계산하는 것) 배너 색으로 먼저 구분해 둡니다.

기준 일정 미등록 배너는 "고장"이 아닙니다. 기준선을 승인하지 않은 프로젝트에서는 정상 상태이고, 이 상태에서는 기준 대비 초과도 판정하지 않습니다(비교 대상이 없으므로).

5.3 Sprint 레인

Sprint를 쓰는 프로젝트라면 업무 행들 위에 별도의 얇은 줄로 Sprint 기간이 표시됩니다. 왼쪽 칸에는 Sprint 이름과 상태(계획 / 실행 중 / 종료)가 적히고, 오른쪽에 기간 막대가 그려집니다.

  • Sprint 하나에 줄 하나입니다. 한 Sprint가 세 개의 Work Package를 건드려도 세 번 그리지 않습니다. 반복해 그리면 존재하지 않는 세 벌의 일정과 진척을 만들어 내게 됩니다.
  • 막대 색은 상태에 따라 진하기가 다릅니다 — 실행 중이 가장 진하고, 계획이 그다음, 종료는 회색으로 물러납니다.
  • Sprint 막대에 마우스를 올리면 브라우저 기본 툴팁으로 Sprint 3 · 2026-09-01 ~ 2026-09-14 · 완료 5/8 처럼 이름·기간·완료 건수가 나옵니다.
  • Sprint 이름(마우스 올림)에는 Sprint 목표가, 목표가 없으면 이름이 표시됩니다.

양방향 강조 — 클릭해서 관계 보기

이 레인의 쓸모는 "이 업무를 지금 어느 Sprint가 하고 있는가"를 눈으로 잇는 것입니다.

  • 업무 행을 클릭 → 그 업무를 다루는 Sprint 레인만 남고 나머지는 흐려집니다.
  • Sprint 이름이나 막대를 클릭 → 그 Sprint가 손대는 업무 행만 남고 나머지가 흐려집니다.
  • 같은 것을 다시 클릭하면 해제됩니다. 다른 쪽을 클릭하면 이전 선택은 자동으로 풀립니다.
  • 업무 행은 키보드로도 됩니다 — Tab으로 이동해 Enter 또는 Space.

이 연결은 강조 전용입니다. Sprint에서 어떤 값도 파생되지 않습니다. 특히 Sprint 종료일을 업무의 실제 종료일로 복사하지 않습니다 — Sprint가 끝난 것과 그 Work Package의 산출물이 완료된 것은 다른 사실이고, 한 Sprint가 여러 Work Package에 걸칠 수 있습니다.

Sprint 레인이 없는 프로젝트에서는 이 줄 자체가 나타나지 않습니다.

5.4 선후행 관계

차트 아래 선후행 관계 절에서 관리합니다.

지원하는 관계는 FS 하나뿐

FS(Finish-to-Start, 선행이 끝나야 후행이 시작) 한 종류만 지원합니다. 그래서 관계를 등록할 때 종류를 고르는 칸이 없습니다. SS/FF/SF가 필요하면 저장 구조부터 바꿔야 합니다.

등록

머리말 오른쪽 ＋ 관계 추가 를 누르면 대화상자가 열립니다. WBS 항목이 2개 미만이면 버튼이 비활성입니다(관계를 맺을 상대가 없으므로).

칸 설명
선행 업무 먼저 끝나야 하는 업무
후행 업무 그 뒤에 시작하는 업무
대기(일) 선행이 끝나고 며칠 더 기다린 뒤에 시작할 수 있는가

대화상자 안에 이 설명이 함께 적혀 있습니다.

선행 업무가 끝난 뒤 대기 일수만큼 지나서 후행 업무를 시작할 수 있습니다 (대기 0 = 바로 다음 날). 이 값은 계획상 간격이며, 실제 지연은 오늘 날짜와 진행률로 자동 판정됩니다.

대기(일)은 지연이 아닙니다. 콘크리트 양생이나 승인 대기처럼 계획에 원래 들어 있는 기다림입니다. 예전 화면에서 이 칸을 "지연(일)"이라고 적었다가 실제 지연 판정과 혼동을 일으켜 바꾼 것이니, 이 구분은 유지해 주세요.

계산은 이렇습니다: 후행의 가장 이른 시작일 = 선행 종료일 + 대기일 + 1일. 대기 0이면 선행이 끝난 바로 다음 날부터 시작할 수 있습니다. 같은 후행에 선행이 여럿이면 그중 가장 늦은 날짜가 적용됩니다.

목록·수정·삭제

등록된 관계는 1.2 요구사항 확정 → 2.1 화면 설계 형태로 한 줄씩 나열됩니다. 대기가 0보다 크면 뒤에 대기 2일 배지가 붙습니다. 하나도 없으면 등록된 선후행 관계가 없습니다. 라고 적습니다.

  • 수정 — 그 행이 그 자리에서 편집 폼으로 바뀝니다. 선행·후행·대기를 모두 바꿀 수 있습니다. 저장이 서버에 받아들여지면 행이 다시 읽기 모드로 돌아가고, 거부되면 입력값을 그대로 둔 채 오류가 표시됩니다.
  • 삭제 — 확인 없이 즉시 삭제합니다.

관계를 추가·수정·삭제해도 WBS 항목의 날짜는 하나도 바뀌지 않습니다. 관계는 "이런 순서여야 한다"는 제약을 등록하는 것뿐이고, 날짜를 실제로 옮기는 것은 일정 재계산뿐입니다.

거부되는 조합과 그 이유

조합 화면에 나오는 메시지 왜 거부하는가
같은 업무를 선행·후행 양쪽에 같은 항목을 선행/후행으로 지정할 수 없습니다. 자기가 끝나야 자기가 시작할 수 있다는 뜻이 됨
이미 있는 조합 이미 등록된 선후행 관계입니다. 같은 제약이 둘이면 화살표만 겹쳐 그려지고 얻는 것이 없음
순환이 생기는 조합 (A→B가 있는데 B→A) 선후행 관계에 순환이 생깁니다. 순환이 있으면 만족하는 일정이 아예 존재하지 않습니다. 차트도 재계산도 의미가 없어지므로 등록 자체를 막습니다
상위·하위 관계인 두 항목 사이 상위·하위 관계인 항목끼리는 선후행 관계를 걸 수 없습니다. Summary 일정은 하위 항목에서 계산되므로 만족할 수 있는 일정이 없습니다. Summary 일정은 하위에서 계산되는 파생 값이라, 하위를 뒤로 밀면 상위 종료일도 같은 만큼 밀려 위반이 영원히 남습니다

위반은 막지 않고 표시합니다. 날짜 자체는 자유롭게 입력할 수 있고, 제약을 어긴 계획도 저장됩니다. 계획을 세우는 도중에는 반드시 어긋난 상태를 지나가기 때문입니다. 대신 그 행에 점선 외곽선과 빨간 눈금이 붙고 배너가 뜹니다 — 언제 고칠지는 사용자가 정합니다. 반면 순환과 상위·하위 조합은 "만족할 수 있는 일정이 없는" 경우라서 등록 자체를 거부합니다.

선후행 관계는 Summary 항목에도 걸 수 있습니다(서로 상위·하위 관계만 아니면). 이때 판정은 집계된 일정으로 하고, 재계산 시에는 그 아래 leaf 전체를 같은 일수만큼 밉니다.

주의 — WBS 이동은 막지 않습니다. 형제였던 두 항목에 관계를 걸어 둔 뒤 한쪽을 다른 쪽 하위로 옮기면, 등록 시점엔 없던 "상위·하위 관계 사이의 선후행"이 만들어집니다. 이 상태로 재계산을 누르면 §5.5의 오류 메시지가 나옵니다.

5.5 일정 재계산

오른쪽 위 일정 재계산 버튼입니다. 누르면 먼저 확인창이 뜹니다.

선후행 관계를 만족하도록 일정을 뒤로 밀어냅니다. 진행할까요?

하는 일

  • 위반 중인 후행 업무를, 가장 이른 시작일까지 뒤로 밀어냅니다. 밀린 만큼 종료일도 함께 이동하므로 기간(일수)은 유지됩니다.
  • Summary가 위반이면 그 아래 leaf 전체를 같은 일수만큼 밉니다. Summary의 날짜는 파생 값이라 직접 옮길 수 없기 때문입니다.
  • 한 번 밀면 그 뒤 업무가 다시 위반이 될 수 있으므로, 더 이상 위반이 없을 때까지 반복합니다.
  • 끝나면 몇 개 항목이 움직였는지 알려 줍니다. (3개 항목의 일정을 뒤로 이동했습니다. / 모든 선후행 관계가 이미 충족되어 변경된 일정이 없습니다.)
  • WBS 날짜를 실제로 바꾸므로 WBS 화면도 다음에 열 때 새로 읽습니다.

하지 않는 일

  • 앞으로 당기지 않습니다. 선행이 일찍 끝나 여유가 생겨도 후행을 앞당기지 않습니다. 뒤로만 미는 규칙이라야 반복이 반드시 끝난다는 보장이 서고, 무엇보다 사람이 의도적으로 남겨 둔 간격(휴가, 검토 기간, 버퍼)을 시스템이 말없이 지워 버리면 안 됩니다.
  • 자동으로 실행되지 않습니다. 위반 배너가 떠 있어도 누르기 전에는 아무 일도 일어나지 않습니다. 언제 밀지는 계획을 세우는 사람이 정할 일입니다.
  • 날짜가 없는 항목은 건드리지 않습니다. 제약 판정에도 참여하지 않고 이동 대상도 아닙니다.
  • 진행률·실적·기준선을 바꾸지 않습니다. 오직 시작일·종료일만 움직입니다.
  • 되돌리기가 없습니다. 밀린 날짜를 원래대로 되돌리려면 WBS에서 손으로 고쳐야 합니다.

재계산이 거부되는 경우

상위·하위 관계인 항목끼리 선후행 관계가 걸려 있으면(§5.4의 마지막 주의 참고) 재계산이 아예 거부되고, 문제되는 관계의 WBS 코드를 이름과 함께 알려 줍니다.

상위·하위 관계인 항목끼리 걸린 선후행 관계가 있어 재계산할 수 없습니다: 2 설계·개발 → 2.3 근태 단말 연동. 해당 선후행 관계를 삭제한 뒤 다시 시도하세요.

이 경우 해당 관계를 삭제하고 다시 시도하면 됩니다.

5.6 임계 경로와 여유(float)

임계 경로는 "여기가 하루 밀리면 프로젝트 종료일도 하루 밀리는" 업무들의 사슬입니다. 서버가 간트를 조회할 때마다 계산해 각 업무의 여유(float) 와 각 관계의 임계 여부를 함께 내려 줍니다.

켜고 끄기

툴바의 임계 경로 강조 체크박스입니다. 임계 경로 업무가 하나라도 있을 때만 나타나고, 기본은 켜져 있습니다. 화면을 옮겨 다녀도 껐던 상태가 유지됩니다.

켜면 이렇게 바뀝니다.

  • 임계 업무의 막대에 진한 실선 외곽선이 붙고, 임계 관계의 화살표가 굵어집니다.
  • 임계 업무 행의 왼쪽 끝에 굵은 세로 표시가 붙고 WBS 코드가 진해집니다.
  • 나머지 막대와 화살표는 반투명(40%)으로 물러납니다.

새로운 색을 쓰지 않습니다. 채움 색은 이미 지연 상태가, 점선 외곽선은 이미 선후행 위반이 쓰고 있어서 색 계열을 하나 더 얹으면 서로 헷갈립니다. 대신 배경과 대비가 가장 큰 중립색의 실선과 굵기로만 구분합니다.

두 가지 예외가 있습니다.

  • Summary 막대는 흐리게 처리하지 않습니다. 일정이 하위에서 계산되는 구조 표시라서, 임계인 자식 바로 위에서 Summary가 흐려지면 잘못 읽힙니다.
  • 위반 중인 임계 막대는 점선 외곽선을 유지합니다. 위반 표시를 임계 실선으로 덮어 가리지 않습니다.

여유(float) 읽는 법

막대에 마우스를 올리면 툴팁의 여유 줄에 나옵니다. 네 가지 문구뿐입니다.

문구 뜻
여유 3일 3일까지는 밀려도 프로젝트 종료일이 움직이지 않음
여유 없음 (임계 경로) 여유 0일. 하루만 밀려도 종료일이 밀림
제약보다 2일 늦음 (임계 경로) 여유가 음수. 계획이 이미 제약을 어기고 있다는 뜻(= 그 행의 선후행 위반)
선후행 관계 없음 이 업무는 어떤 관계에도 참여하지 않음

선후행 관계 없음과 여유 없음은 정반대입니다. 전자는 "사슬 위에 있지 않아 판정 대상이 아니다"이고, 후자는 "사슬 위에 있는데 줄 여유가 하나도 없다"입니다. 임계 경로는 사슬에 대한 이야기이므로 아무 관계도 없는 업무는 애초에 답할 질문이 아닙니다. 화면에서 두 값을 다른 말로 쓰는 이유입니다.

계산 방식에서 알아둘 것

  • 전진 패스는 입력한 날짜 그대로입니다. 즉 "가장 빠른 종료일"을 다시 계산하지 않고 계획 종료일을 그대로 씁니다. 그래서 사용자가 일부러 남겨 둔 간격이 실제 여유로 잡힙니다. "이 업무가 밀리면 종료일이 밀리는가"라는 실무 질문에 답하려면 아무도 입력하지 않은 이상적 일정이 아니라 입력된 계획을 봐야 하기 때문입니다.
  • 대기(일)은 여유가 아닙니다. 계획상 대기이므로 후속 판정의 기준선에 포함됩니다. 대기만큼 정확히 떨어져 붙어 있으면 여유는 0입니다.
  • 여유가 음수면 계획이 이미 모순입니다. 줄 여유가 없으므로 임계 경로로 봅니다.
  • 관계에 참여하고 날짜가 둘 다 있는 업무만 판정 대상입니다. Summary도 관계가 걸려 있으면 집계된 일정으로 참여하고, 걸려 있지 않으면 선후행 관계 없음입니다.
  • 관계가 하나도 없으면 임계 경로 자체가 없어, 배너도 체크박스도 나타나지 않습니다.

5.7 툴팁으로 볼 수 있는 것

차트 위 아무 데나 마우스를 올리면 툴팁이 뜹니다. 막대 위가 아니어도 됩니다 — 오히려 빈 곳에서 가장 많이 쓰입니다.

항상 나오는 것 — 날짜

첫 줄에 2026-09-09 (수) 처럼 커서 아래 날짜와 요일이 나오고, 같은 순간 차트에는 그 날짜 칸이 연한 파란색으로 칠해집니다. 그 날이 기준일이면 뒤에 기준일 알약이 붙습니다.

이 기능이 있는 이유는 축이 날짜 칸은 다 그리지만 숫자는 일부만 적고, 하루 폭이 좁아지면 아예 적지 않기 때문입니다. 긴 프로젝트에서 "여기가 며칠이지?"에 답하는 유일한 수단입니다.

툴팁 동작에서 알아둘 것

  • 막대에는 브라우저 기본 툴팁을 달지 않았습니다. 커스텀 툴팁과 이중으로 떠서 겹치기 때문입니다. 접근성 정보(스크린 리더용 이름)는 따로 유지됩니다. (예외적으로 Sprint 막대에는 기본 툴팁이 있습니다 — §5.3)
  • 툴팁은 화면 가장자리에 가까우면 커서 반대쪽으로 뒤집혀 잘리지 않습니다.
  • 툴팁은 마우스 이벤트를 받지 않으므로, 툴팁 위로 커서를 옮겨 내용을 클릭·복사할 수는 없습니다.
  • 차트 밖으로 커서가 나가면 즉시 사라집니다.

5.8 실무 예시

가상의 프로젝트 「사내 근태 시스템 구축」 으로 두 상황을 따라가 봅니다. 기준일은 2026-09-09 (수) 입니다.

계획은 이렇습니다.

코드 업무 계획 진행률
1 요건 정의 (Summary) 07-01 ~ 07-24 100%
1.1 현행 조사 07-01 ~ 07-10 100%
1.2 요구사항 확정 07-13 ~ 07-24 100%
2 설계·개발 (Summary) 07-27 ~ 09-04 —
2.1 화면 설계 07-27 ~ 08-07 100%
2.2 서버 개발 08-10 ~ 09-04 70%
2.3 근태 단말 연동 08-24 ~ 09-04 30%
3 검증 (Summary) 09-07 ~ 09-30 —
3.1 통합 테스트 09-07 ~ 09-18 0%
3.2 사용자 인수 테스트 09-19 ~ 09-30 0%

선후행 관계는 네 개입니다. 1.2 → 2.1 (대기 0), 2.2 → 3.1 (대기 0), 2.3 → 3.1 (대기 2), 3.1 → 3.2 (대기 0).

2.3 → 3.1의 대기 2일은 단말 납품사에서 검수 결과를 받는 데 걸리는 시간입니다 — 우리 일이 아니라 계획에 원래 들어 있는 기다림이라 지연이 아니라 대기로 적었습니다.

시나리오 A — 지연이 생겼을 때 원인을 찾아 대응하기

① 화면을 열면 배너가 이렇게 뜹니다.

지연 2건 (최대 5일) — 2.2 서버 개발, 2.3 근태 단말 연동. 지연 위험 1건 — 3.1 통합 테스트 (25%p 부족).

임계 경로 3개 업무 · 2026-08-24 ~ 2026-09-30 (38일) — 2.3 근태 단말 연동 → 3.1 통합 테스트 → 3.2 사용자 인수 테스트. 이 업무들은 여유가 없어, 하루 밀리면 프로젝트 종료일도 하루 밀립니다. 다음으로 촉박한 업무는 2.2 서버 개발 (여유 2일)입니다.

② 숫자를 확인합니다.

  • 2.2와 2.3은 종료일이 09-04인데 오늘이 09-09입니다. 종료일을 지났고 100%가 아니므로 지연 5일 — 배지에 지연 5일이라고 적힙니다.
  • 3.1은 아직 기간 안(09-07~09-18)입니다. 12일 중 3일이 지났으니 기대 25%인데 실제 0%라 지연 위험입니다. 막대 안에 25% 지점에 세로 눈금이 찍혀 있고, 진한 채움이 하나도 없어 그 간격이 그대로 보입니다.
  • Summary인 2 설계·개발과 3 검증 행에도 배지가 붙어 있습니다. 하지만 배너의 "지연 2건"에는 세지 않습니다 — 그 지연은 이미 하위에서 세고 있기 때문입니다.

③ 어느 것부터 손대야 하는지 판단합니다.

지연 일수만 보면 2.2와 2.3이 똑같이 5일입니다. 여기서 임계 경로가 답을 갈라 줍니다. 막대에 마우스를 올려 툴팁의 여유 줄을 봅니다.

  • 2.3 근태 단말 연동 → 여유 없음 (임계 경로)
  • 2.2 서버 개발 → 여유 2일

같은 5일 지연이지만 2.3이 밀리면 프로젝트 종료일이 그대로 밀리고, 2.2는 이틀까지는 버팁니다. 게다가 2.3 뒤에는 대기 2일이 붙어 있어, 2.3이 하루 늦으면 3.1의 시작 가능일도 하루 밀립니다. 2.3에 먼저 인력을 붙이는 것이 맞습니다.

임계 경로 강조를 켜면 2.3 → 3.1 → 3.2 사슬만 진하게 남고 나머지가 흐려져, 이 판단을 회의 자리에서 그대로 보여 줄 수 있습니다.

④ Sprint를 확인합니다.

2.3 근태 단말 연동 행을 클릭하면 위쪽 Sprint 레인에서 관련 Sprint만 남습니다. 예를 들어 Sprint 5 · 실행 중 하나가 남고 툴팁에 완료 3/9라고 나오면, 이 Work Package의 지연이 곧 그 Sprint의 남은 6건이라는 뜻입니다. 어디를 볼지가 정해졌으므로 Board 화면으로 넘어가 막힌 카드를 찾습니다.

⑤ 대응합니다. 화면에서 할 수 있는 일은 아래 세 갈래입니다.

  • 일을 당긴다 — Board에서 카드를 처리해 진행률이 오르면, 다음에 간트를 열 때 배지가 지연 → 지연 위험 → 정상 순으로 자연스럽게 바뀝니다. 여기서 상태를 손으로 바꾸는 칸은 없습니다.
  • 계획을 고친다 — WBS에서 2.3의 종료일을 실제 가능한 날짜로 옮깁니다. 그러면 시나리오 B로 넘어갑니다.
  • 원인을 기록한다 — 단말 납품 지연처럼 프로젝트 밖에서 온 원인이라면 RAID에 DEPENDENCY 항목으로 남기고 2.3에 연결해 둡니다. 다음 주에 같은 질문을 다시 받지 않으려면 이 기록이 필요합니다.

시나리오 B — 기준 일정을 넘길 것 같을 때

계속해서, 납품사와 협의한 결과 2.3을 09-14까지 미뤄야 한다고 합시다. 이 프로젝트는 착수 시점에 기준선 v1을 승인해 두었습니다.

① WBS에서 2.3의 종료일을 09-04 → 09-14로 고칩니다.

② 간트를 열면 배너가 두 개 늘어납니다.

기준 종료일 초과 1건 — 예상 종료가 승인된 기준 일정을 넘겼습니다. 2.3 근태 단말 연동 (10일)

선행 업무보다 먼저 시작하는 업무가 1개 있습니다 — 3.1 통합 테스트. 일정 재계산으로 자동 조정할 수 있습니다.

③ 차트에서 무슨 일이 일어났는지 봅니다.

  • 2.3 행에서 위쪽 회색 기준 막대는 09-04에서 끝나 있는데 가운데 계획 막대는 09-14까지 늘어나 있습니다. 두 막대의 어긋난 길이가 곧 10일입니다. 기준 막대를 현재 계획으로 덮어쓰지 않기 때문에 이 어긋남이 보입니다.
  • 3.1의 계획 시작일은 여전히 09-07인데, 이제 가장 이른 시작일은 09-14 + 대기 2일 + 1일 = 09-17 입니다. 그래서 3.1 막대에 보라 점선 외곽선이 생기고, 막대 왼쪽 앞 09-17 위치에 굵은 세로 눈금이 찍힙니다. 3.1로 들어오는 화살표는 왼쪽으로 되감기는 모양이 됩니다.
  • 3.1 막대에 마우스를 올리면 툴팁에 가장 이른 시작 2026-09-17이 경고색으로 나옵니다. 3.1 자신의 여유는 여전히 여유 없음 (임계 경로)입니다 — 여유는 뒤쪽 제약에서 계산되고, 3.1이 어긴 것은 앞쪽 제약이기 때문입니다.
  • 음수 여유는 2.3 쪽에 나타납니다. 2.3 툴팁의 여유가 제약보다 10일 늦음 (임계 경로)으로 바뀝니다 — 뒤 일정을 그대로 두려면 2.3이 09-04에 끝났어야 하는데 09-14로 계획했다는 뜻입니다. 여유가 음수라는 것은 곧 그 계획이 이미 모순이라는 신호입니다.
  • 범례 줄에도 기준 종료일 초과 1건이 빨간 글씨로 붙습니다.

④ 두 가지를 결정합니다.

  • 뒤 일정을 밀 것인가 — 일정 재계산을 누르면 확인창 뒤에 3.1이 09-17~09-28로, 이어서 3.2가 09-29~10-10으로 밀리고 2개 항목의 일정을 뒤로 이동했습니다. 라고 나옵니다. 기간(각 12일)은 유지됩니다. 되돌리기가 없으니 누르기 전에 확정하세요.
  • 약속을 다시 할 것인가 — 종료일 자체를 못 미루는 상황이라면 재계산 대신 범위를 줄이거나 병렬화를 검토해야 합니다. 이때 기준선을 새로 승인하지 마세요. 새 기준선을 승인하면 초과가 사라져 "약속을 지켰다"처럼 보이지만, 실제로 바뀐 것은 약속뿐입니다. 기준선은 계획을 고칠 때마다가 아니라 이해관계자와 다시 합의했을 때만 승인합니다.

⑤ 재계산 후 다시 확인합니다.

  • 위반 배너가 사라집니다. 3.1의 점선 외곽선과 09-17 눈금도 사라집니다.
  • 기준 종료일 초과는 오히려 늘어납니다 — 이제 3.1과 3.2도 기준선의 종료일을 넘겼기 때문입니다. 배너는 초과 일수가 큰 순서로 나열하므로, 목록 맨 앞이 가장 크게 어긋난 업무입니다. 링크를 누르면 WBS 화면의 그 행이 펼쳐지고 강조되어 바로 고칠 수 있습니다.
  • 이 상태가 바로 이 화면이 존재하는 이유입니다. 선후행 위반(계획의 모순)은 해소했지만 기준 대비 초과(약속과의 차이)는 남았다 — 둘은 다른 문제이고, 두 번째는 시스템이 해결해 줄 수 없습니다.

5.9 주의할 점

판정에 관한 것

  • 기준일은 언제나 서버 시각입니다. 범례 오른쪽 끝의 기준일 …이 그 값이고, 화면의 모든 배지·배너·오늘 선이 이 하나를 씁니다. 브라우저 시계와 다를 수 있습니다.
  • 종료일 당일은 아직 지연이 아닙니다. 그날이 지나야 지연이 됩니다.
  • 진행률 100%는 종료일이 지났어도 완료 입니다. 실제 완료일을 기록하지 않아 "지연 완료"를 구분할 근거가 없습니다.
  • 배너의 건수는 leaf만, 배지는 Summary에도 붙습니다. 숫자와 눈에 보이는 배지 개수가 다른 것이 정상입니다.
  • 영업일·휴일 달력이 없습니다. 주말에도 일정이 흘러가고, 지연 일수와 기대 진행률 모두 달력일 기준입니다. 주말은 음영으로만 구분합니다. 긴 연휴가 낀 구간의 기대 진행률은 실제보다 높게 나옵니다.
  • 기대 진행률은 단순 선형입니다. 앞이 무겁거나 뒤가 무거운 업무에는 잘 맞지 않을 수 있습니다. 판단의 출발점으로만 쓰세요.

입력에 관한 것

  • 실적(실제 시작·완료)과 예상 종료를 입력할 화면이 없습니다. 차트와 툴팁은 이 값들을 그릴 수 있지만, 값을 넣는 경로는 현재 가져오기(import) 뿐입니다. 직접 만든 프로젝트에서는 실적 막대와 예상 종료 표식이 나타나지 않는 것이 정상입니다. 이때 기준 대비 초과 판정은 예상 종료 대신 현재 계획의 종료일로 이루어집니다 — 예측을 적지 않았다는 것이 "늦지 않는다"는 뜻은 아니기 때문입니다.
  • 일정은 WBS에서만 고칩니다. 차트에서 막대를 끌어 옮기는 기능은 없습니다.
  • 선후행 관계는 FS 한 종류뿐입니다. SS/FF/SF는 지원하지 않습니다.
  • 대기(일)은 지연이 아니라 계획상 대기입니다. 여기에 실제 지연 일수를 적지 마세요 — 적으면 계획 자체가 늘어난 것으로 취급되어 지연이 사라진 것처럼 보입니다.

동작에 관한 것

  • 일정 재계산은 되돌릴 수 없습니다. 뒤로만 밀고 앞으로 당기지 않으므로, 되돌리려면 WBS에서 날짜를 손으로 고쳐야 합니다.
  • 선후행 관계를 등록·수정·삭제해도 날짜는 바뀌지 않습니다. 날짜를 실제로 옮기는 것은 재계산뿐입니다.
  • 관계를 걸어 둔 뒤 WBS에서 한쪽을 다른 쪽 하위로 옮기면 재계산이 거부됩니다. 메시지에 적힌 관계를 삭제하고 다시 시도하세요.
  • Sprint 레인의 강조는 강조일 뿐입니다. Sprint 기간에서 업무의 실적이나 진척이 파생되지 않습니다.
  • 기준선이 없으면 기준 대비 초과를 판정하지 않습니다. "초과 0건"이 아니라 "판정하지 않음"입니다. 판정이 필요하면 Dashboard → 진척 탭에서 기준선을 먼저 승인하세요.
  • Summary 행에는 기준 일정 막대가 그려지지 않습니다. 기준선은 각 항목이 직접 가진 날짜만 복사하는데 Summary의 날짜는 하위에서 파생되는 값이라 비어 있기 때문입니다. 단계 전체가 기준 대비 얼마나 밀렸는지는 하위 항목들에서 읽어야 합니다.

6. RACI

업무마다 "누가 하고, 누가 책임지고, 누구에게 묻고, 누구에게 알리는가"를 한 표에 적는 화면입니다. 행은 WBS 업무 전체, 열은 프로젝트 구성원입니다.

RACI는 이 시스템에서 권한이 아니라 표시입니다. 로그인이 없으므로 A로 지정된 사람만 무언가를 할 수 있게 되는 일은 없고, 규칙을 어겨도 저장이 막히지 않습니다. 그래서 이 화면의 가치는 "막아 주는 것"이 아니라 비어 있는 칸과 서로 어긋난 칸을 눈에 띄게 만드는 것에 있습니다.

수정과 삭제

목록의 행에서 수정을 누르면 그 자리에서 바로 편집합니다(대화상자가 아닙니다). 삭제는 확인 창을 띄웁니다.

삭제하면 그 사람의 RACI 배정이 함께 사라집니다. 확인 창도 그렇게 알려 줍니다. 다만 확인 창이 말하지 않는 것이 두 가지 더 있습니다 — 그 사람이 소유자로 지정된 RAID 항목과 담당자로 지정된 Backlog 항목은 지워지지 않고 소유자·담당자만 비워집니다. 기록 자체를 잃지 않으려는 설계이지만, 삭제 후 RAID 화면에 "소유자가 없는 미종결 항목" 배너가 새로 뜰 수 있다는 뜻이기도 합니다.

6.2 화면 구성과 역할 배정

표의 모양

  • 행 — 프로젝트의 모든 WBS 항목이 트리 순서로 들어갑니다. Summary(하위가 있는 항목)도 빠지지 않습니다. 행 머리에는 WBS 코드와 업무명이 있고, 업무명은 계층 깊이만큼 들여쓰기됩니다.
  • 열 — 구성원. 열이 많아지면 표가 가로로 스크롤되지만, 업무 열은 왼쪽에 고정되어 따라 움직입니다. 어느 행을 보고 있는지 놓치면 매트릭스를 읽을 수 없기 때문입니다.
  • 칸 — 각 칸에 R A C I 네 개의 작은 버튼이 항상 있습니다.

네 글자의 뜻

글자 이름 뜻 규칙
R Responsible · 실무 담당 실제로 일을 하는 사람 업무마다 최소 한 명
A Accountable · 최종 책임 결과를 책임지는 사람 업무마다 정확히 한 명
C Consulted · 자문 진행 중 의견을 구하는 사람 제한 없음
I Informed · 통보 결과를 통보받는 사람 제한 없음

차트 아래 범례에 같은 설명이 있고, 글자에 마우스를 올리면 이 문장이 툴팁으로 뜹니다.

토글 동작

글자를 누르면 배정되고, 다시 누르면 해제됩니다. 저장 버튼은 없습니다 — 누르는 즉시 서버에 반영되고, 서버는 매트릭스 전체를 다시 내려줍니다. 글자 하나가 그 행의 경고를 해소하거나 새로 만들 수 있는데, 바뀐 칸만 돌려주면 화면이 그것을 알 수 없기 때문입니다.

  • 한 사람이 여러 글자를 겸할 수 있습니다. 유일성은 (업무, 구성원, 역할) 조합으로 잡혀 있어 같은 칸에 R과 A를 함께 켜 두는 것이 정상입니다. 담당자가 곧 책임자인 경우가 흔한데, 한 글자만 허용하면 그 사람이 R을 켜는 순간 A가 사라져 "책임자 없음" 경고가 잘못 뜹니다.
  • 한 업무에 여러 사람이 같은 글자를 가질 수 있습니다. R이 셋인 것은 정상이고, A가 둘인 것은 경고 대상이지만 저장은 됩니다(6.4).
  • 이미 배정된 글자를 다시 배정하려 하면 이미 배정된 역할입니다.로 거부됩니다. 화면에서는 토글이 알아서 해제 쪽으로 가므로 정상 조작으로는 만나기 어렵습니다.
  • Summary 행에도 배정할 수 있습니다. 단계 전체의 최종 책임자를 적는 것은 정상적인 사용이고, 그렇게 적은 글자는 아래로 상속됩니다(6.3).

6.3 상속과 재정의

상위(Summary) 행에 지정한 역할은 그 아래 모든 업무에 적용됩니다. 단계의 책임자를 하위 업무 수십 개에 일일이 다시 적게 하는 것은 표를 채우는 일이지 관리하는 일이 아니기 때문입니다.

아무것도 저장하지 않습니다

상속은 조회할 때 계산됩니다. WBS 코드나 Summary의 일정과 같은 이유입니다 — 상속된 글자를 복사해 저장해 두면, 나중에 그 업무를 다른 단계 아래로 옮겨도 예전 단계의 책임자가 복사본으로 남아 계속 따라다닙니다.

역할별로 상속합니다

자기 행에 R을 적어도 상위의 A는 그대로 내려옵니다. 어떤 글자 하나를 적었다고 그 행이 상위를 통째로 무시하게 만들면, 담당자 이름을 적는 순간 단계의 책임자가 조용히 사라집니다. 상속은 R, A, C, I 각각에 대해 따로 판정합니다.

가장 가까운 상위가 이깁니다

상위 단계와 중간 단계가 같은 역할에 서로 다른 사람을 지정했다면, 가까운 쪽(중간 단계)이 실제로 적용됩니다. 이것을 재정의라고 부릅니다.

주의 — 상속된 흐린 글자를 누르면 해제가 아니라 "이 행에 같은 글자를 새로 배정"이 됩니다. 토글은 "이 행에 내 글자가 있는가"만 보기 때문입니다. 같은 사람에게 같은 역할을 다시 붙이는 것이라 결과는 달라지지 않지만, 그 행이 상위를 재정의한 것으로 취급되어 재정의 배지가 붙고 상속 글자에 취소선이 그입니다(발견한 결함 참고).

6.4 검증 경고

표 위의 노란 배너에 나옵니다. 경고는 막지 않고 알리기만 합니다.

책임자가 둘인 상태는 인수인계 중에 반드시 지나가는 정상적인 저장 상태이고, 매트릭스를 채우다 만 중간 상태에서 저장이 거부되면 "지우고 다시 넣기"를 강요하게 됩니다. 일정 쪽과 같은 기준입니다 — 만족 자체가 불가능한 구조(선후행 순환)는 거부하고, 계획이 서로 안 맞는 것은 표시합니다.

왜 대상이 다른가

  • 누락은 leaf에만. 하위가 있는 항목에 담당자가 없는 것은 공백이 아닙니다 — 일은 하위에 있습니다. Summary까지 함께 세면 누락 하나가 계층 레벨 수만큼 중복 보고됩니다.
  • 누락은 상속까지 본 뒤에. 단계의 A를 물려받은 Work Package는 책임자가 없는 것이 아닙니다. 상속을 무시하고 판정하면 매트릭스에 이미 있는 글자를 다시 적으라고 시키게 됩니다.
  • 중복은 선언한 행에 한 번만. 상위에 A가 둘이면 그 아래 업무 전부가 A 둘을 물려받지만, 실수는 하나입니다. 하위마다 되풀이해 보고하면 실수 하나가 leaf 수만큼 불어납니다. 정리해야 할 곳은 그 글자가 실제로 적힌 행입니다.

구성원이 등록되어 있고 leaf가 하나 이상이면 초록색으로

업무 N건 모두 최종 책임자 한 명과 실무 담당자가 지정되어 있습니다.

라고 적힙니다. "경고 없음"과 "아직 아무것도 안 했음"을 구분하기 위한 문장입니다.

6.5 Backlog 담당자와의 구분

행 머리 아래쪽에 담당 김개발(3), 박개발(1) 같은 회색 줄이 붙는 경우가 있습니다. 이것은 그 Work Package에 귀속된 Backlog 항목의 담당자와 그 사람이 맡은 항목 수입니다.

RACI 역할이 아닙니다. 그래서 열이 아니라 행 머리의 주석으로 그립니다 — 열로 만들면 R·A·C·I 글자와 나란히 서서 다섯 번째 역할처럼 읽힙니다.

RACI 글자 Backlog 담당자
무엇에 대한 답인가 이 업무(Work Package)의 결과를 누가 책임지는가 이 Story·Bug를 지금 누가 들고 있는가
어디서 바꾸는가 이 화면의 글자 토글 Backlog 화면의 항목 편집
서로 영향 없음 없음
보관된 항목 해당 없음 집계에서 빠짐 — 지금 아무도 들고 있지 않은 일이므로

Story의 담당자를 바꿔도 그 업무의 A는 움직이지 않고, A를 배정해도 어떤 Story의 담당자도 바뀌지 않습니다. 두 경로 사이에는 코드가 없습니다.

이 줄을 두는 이유는 표를 읽다가 "이 단계는 누가 실제로 돌리고 있나"를 확인하려고 Backlog 화면으로 넘어가지 않아도 되게 하려는 것입니다. 예를 들어 A는 PM으로 잘 지정돼 있는데 담당이 전부 한 사람이면, 그것은 RACI 규칙 위반은 아니지만 부하가 쏠려 있다는 신호입니다.

6.6 실무 예시

예시 1 — 단계 책임자를 한 번만 적기

1   설계               ← 여기에 A = 박PM
1.1   요구사항 정의      ← R = 김분석
1.2   화면 설계          ← R = 이디자인
1.3   API 설계           ← R = 김개발
  1. 먼저 구성원 네 명(박PM, 김분석, 이디자인, 김개발)을 등록합니다.
  2. 1 설계 행의 박PM 칸에서 A를 누릅니다. 이 한 번으로 1.1·1.2·1.3 세 행의 박PM 칸에 흐린 점선 A가 생깁니다.
  3. 각 하위 행에서 담당자의 R을 누릅니다.
  4. 배너가 사라지고 "업무 3건 모두 …" 초록 문장이 뜹니다.

여기서 하위 세 행의 A는 상속이므로 그 행에서는 지울 수 없습니다. 담당자를 바꿔도(R 재배정) A는 그대로 남습니다.

예시 2 — 한 업무만 책임자가 다를 때

1.3 API 설계만 외부 아키텍트가 책임진다고 합시다.

  1. 1.3 행의 최아키 칸에서 A를 누릅니다.
  2. 같은 행 박PM 칸의 A에 취소선이 그이고, 행 머리에 재정의 배지가 붙습니다.
  3. 1.1·1.2는 그대로 박PM의 A를 상속합니다.

1.3의 A가 둘이 된 것이 아니라 박PM의 A가 이 행에서만 무효가 된 것이므로, "최종 책임자 중복" 경고는 뜨지 않습니다.

예시 3 — 인수인계 중 (경고를 그대로 두는 경우)

박PM에서 정PM으로 넘기는 중이라 1 설계 행에 A를 둘 다 켜 두었습니다.

  • 배너에 최종 책임자 중복 1건 — 1 설계 (박PM, 정PM)이 뜹니다.
  • 저장은 그대로 되고, 아무것도 지워지지 않습니다.
  • 경고는 1 행에만 붙습니다. 아래 세 행은 A 둘을 물려받지만 경고가 되풀이되지 않습니다.
  • 인계가 끝나면 1 행의 박PM A를 눌러 해제합니다. 배너가 사라집니다.

6.7 주의할 점

  • RACI는 권한이 아닙니다. A로 지정되지 않은 사람도 모든 화면을 똑같이 쓸 수 있습니다. 이 표는 합의를 적어 두는 곳이지 접근을 통제하는 곳이 아닙니다.
  • 상속된 흐린 글자를 눌러도 지워지지 않습니다. 오히려 이 행에 같은 글자가 새로 생기면서 재정의 표시가 붙습니다. 지우려면 툴팁에 적힌 상위 행으로 가세요.
  • 구성원을 지우면 그 사람의 RACI 글자가 전부 사라집니다. 되돌리는 기능은 없습니다. 사람이 바뀐 것뿐이라면 삭제 대신 수정으로 이름을 바꾸는 편이 배정을 유지합니다.
  • WBS 항목을 지우면 그 행의 배정도 함께 사라집니다(DB 연쇄). WBS에서 항목을 옮기는 것은 안전하지만, 지우는 것은 매트릭스에도 영향이 있습니다.
  • CSV로 내보낸 RACI에는 상속 글자가 들어가지 않습니다. 각 행에 직접 배정된 글자만 나가므로, 화면에서 흐린 A가 보이던 칸이 Excel에서는 빈칸입니다. 상속을 포함한 그림이 필요하면 화면을 보세요(발견한 결함).
  • 매트릭스가 낡아 보이면 다른 화면에서 WBS나 Backlog를 고친 뒤입니다. RACI 화면으로 다시 들어오면 갱신됩니다(캐시 키에 WBS·Backlog 변경이 들어 있습니다).
  • RACI 화면에는 기준일이 없습니다. 이 화면에는 "오늘"을 기준으로 판정하는 값이 하나도 없기 때문입니다.

7.1 네 가지 종류와 쓰임

네 종류는 한 테이블에 함께 저장됩니다. 제목·상태·소유자·기한 등 대부분의 필드를 공유하고 한 화면에서 함께 읽히기 때문에, 종류마다 표를 나누면 같은 CRUD를 네 벌로 늘리면서 얻는 것이 없습니다.

종류 언제 쓰는가 전형적인 예
위험 (Risk) 아직 일어나지 않았지만 일어나면 계획이 흔들리는 일 "핵심 개발자가 다른 프로젝트에 차출될 수 있음"
가정 (Assumption) 사실이라고 전제하고 계획을 세운 것. 틀리면 위험이 됩니다 "고객사 테스트 서버를 3월에 쓸 수 있다고 전제"
이슈 (Issue) 이미 일어나서 지금 대응이 필요한 일 "인증 모듈 라이선스가 만료되어 빌드가 실패"

종류를 고르면 폼 안에 그 종류의 한 줄 설명이 뜹니다.

RAID의 "의존성"과 간트의 "선후행 관계"는 다릅니다

혼동하기 가장 쉬운 지점입니다.

RAID 항목을 WBS 업무에 연결해도 그 연결은 연관 표시일 뿐 일정 제약이 아닙니다. "법무 검토가 늦으면 3.2가 밀린다"를 일정에 반영하려면, RAID에 적는 것과 별개로 간트에서 선후행 관계를 걸거나 3.2의 날짜를 직접 조정해야 합니다.

종류는 바꿀 수 있습니다

수정 대화상자에서 종류를 바꿀 수 있고, 그것이 정상적인 사용입니다 — 가정이 틀린 것으로 밝혀지면 보통 이슈가 됩니다. 새 항목을 만들지 말고 종류만 바꾸세요. 새로 만들면 닫아야 할 것이 둘이 되고, 언제 등록됐는지도 흐려집니다.

7.3 연결 대상

한 항목을 WBS 업무 · Sprint · Backlog 항목 여러 곳에 붙일 수 있습니다.

같은 위험이 Story 하나, 그 Story가 든 Sprint, 그리고 그 위의 Work Package에 동시에 걸리는 일은 흔합니다. 그럴 때 항목을 세 개 복사하지 마세요 — 닫아야 할 것이 셋이 되고, 하나만 종결하면 나머지 둘이 남아 등록부가 거짓말을 합니다. 원본은 하나로 두고 연결을 세 개 거는 것이 맞습니다.

거는 방법

폼의 연결 대상 상자에서

  1. 왼쪽 셀렉트로 종류(WBS 업무 / Sprint / Backlog)를 고르고,
  2. 오른쪽 셀렉트로 대상을 고른 뒤,
  3. 추가 버튼을 누릅니다. 칩으로 쌓입니다. ×로 뺍니다.
  • 셀렉트를 두 개로 나눈 이유는 세 종류가 다른 질문("어느 업무인가" vs "어느 Story인가")이고, 하나로 합치면 실제 프로젝트에서 수백 줄짜리 목록이 되기 때문입니다.
  • WBS 목록은 트리 순서로 들여쓰기되어 나오고 코드가 함께 보입니다. Sprint는 Sprint 3 (2026-03-02 ~ 2026-03-13)처럼 기간이 붙습니다.
  • 이미 건 대상은 목록에서 빠집니다. 같은 대상을 두 번 걸면 서버가 같은 대상을 두 번 연결할 수 없습니다.로 거부합니다. 한 번 연결된 것과 두 번 연결된 것은 같은 사실이기 때문입니다.
  • 연결이 하나도 없어도 됩니다. 그때는 연결 없음 — 프로젝트 전체에 대한 항목입니다.라고 적힙니다. 프로젝트 전체에 걸린 위험도 정상입니다.
  • 걸 수 있는 것이 아직 없으면 연결할 Sprint이(가) 아직 없습니다. 처럼 알려 줍니다.

Sprint 삭제 끊김 남음

  • 계획이 사라진다고 위험 기록까지 사라지면 안 됩니다. 그래서 삭제는 항목이 아니라 연결만 끊습니다.
  • 보관은 연결을 건드리지 않습니다. 보관은 "접어둔다"이지 "없던 일이다"가 아니고, 복구하면 연결도 함께 돌아와야 하기 때문입니다.

  • 대상이 사라진 흔적이 남아 있으면 (없음)으로 표시되고 회색으로 흐려집니다. 숨기지 않습니다 — 무엇에 걸려 있던 위험인지 알 수 없게 되는 것보다 낫습니다. (정상 경로에서는 삭제 시점에 연결이 끊기므로 잘 나타나지 않습니다.)

7.4 노출도와 기한 판정

두 값 모두 저장하지 않고 조회할 때 계산합니다. "오늘" 또는 다른 입력값을 기준으로 판정하는 값이라 저장하면 곧바로 낡기 때문입니다.

노출도 (exposure)

확률 × 영향으로 계산합니다. 세 단계에 각각 가중치가 있습니다.

등급 가중치
낮음 1
보통 2
높음 3

따라서 노출도는 1~9이고, {1,2,3}의 곱이므로 실제로 나올 수 있는 값은 1, 2, 3, 4, 6, 9 여섯 개뿐입니다.

등급 경계

노출도 등급 나오는 조합 (확률 × 영향)
6 이상 (6, 9) 높음 보통×높음, 높음×보통, 높음×높음
3 ~ 4 (3, 4) 보통 낮음×높음, 높음×낮음, 보통×보통
2 이하 (1, 2) 낮음 낮음×낮음, 낮음×보통, 보통×낮음

경계를 6에 둔 이유는, 실제로 나올 수 있는 값이 여섯 개뿐이라 "적어도 한쪽이 높음이면서 다른 쪽이 보통 이상"인 지점이 6이기 때문입니다. 그 지점부터가 계획이 필요한 위험입니다.

표시 규칙

  • 확률과 영향이 둘 다 있어야 노출도가 나옵니다. 목록에 높음 (6)처럼 등급과 숫자가 함께 뜨고, 마우스를 올리면 확률 높음 × 영향 보통이 툴팁으로 보입니다.
  • 영향만 있으면 영향 보통으로 적고 그 등급의 색을 씁니다. 노출도 숫자는 없습니다.
  • 둘 다 없으면 - 입니다.
  • 종류 제한이 없습니다. 이슈에 확률까지 들어 있으면(예: 위험이었다가 종류만 바꾼 항목) 이슈에도 노출도가 계산돼 보입니다.
  • 종결된 항목의 노출도 배지는 흐려집니다. 지우지는 않습니다 — 무엇이 얼마나 위험했는지가 기록입니다.

기한 초과 (overdue)

세 조건을 모두 만족할 때만 초과입니다.

  1. 기한이 입력되어 있고,
  2. 상태가 종결이 아니고,
  3. 기한이 기준일보다 이전일 것.
  • 기한 당일은 아직 초과가 아닙니다. 그날이 지나야 초과가 됩니다. (기한 < 기준일)
  • 종결된 항목은 기한이 지나도 초과가 아닙니다. 남은 일이 없으므로 늦을 것도 없습니다.
  • 초과 일수는 기한부터 기준일까지의 달력일입니다. 영업일 달력이 없으므로 주말도 셉니다.
  • 기준일("오늘")은 서버가 정해 응답에 함께 실어 보내고, 화면 오른쪽 위 기준일 2026-09-09로 표시됩니다. 클라이언트가 자기 시계를 쓰면 한 응답 안의 행들이 서로 다른 "오늘"로 판정되거나, 오래 열어 둔 탭에서 배너와 표가 어긋납니다.
  • 기한 열에는 2026-03-01 (8일 초과)처럼 적히고 빨갛게 강조됩니다. 기한이 없으면 -입니다.

이 규칙은 WBS의 지연 판정과 정확히 같은 기준입니다.

7.5 필터·정렬·배너

상단 배너 — 필터를 무시하고 전체를 셉니다

표 위에 순서대로 세 줄이 나올 수 있습니다.

줄 내용
종류 요약 위험 3/5 가정 1/2 이슈 2/2 — 미종결 / 전체. 종결된 것은 신경 쓸 대상이 아니라 앞 숫자에서 빠집니다
경고 (노란 배너) 기한 초과 N건 — 제목 (N일)… / 노출도 높음 N건 — 제목… (높음이면서 미종결인 것만)
소유자 없음 소유자가 없는 미종결 항목이 N건 있습니다 — …

세 줄 모두 필터를 무시하고 등록부 전체를 셉니다. "기한 초과 2건"은 프로젝트에 대한 사실인데, 필터를 걸었다고 숫자가 줄면 잘못 읽힙니다. 필터를 따르는 것은 표뿐입니다.

필터

표 위 왼쪽에 있습니다.

컨트롤 값
종류 칩 전체 N · 위험 N · 가정 N · 이슈 N · 의존성 N. 건수가 0인 칩은 비활성
상태 전체 상태 / 미종결만 / 열림 / 대응중 / 종결
정렬 등록순 / 노출도 높은 순 / 기한 임박순
검색 제목·설명·소유자 이름에서 대소문자 없이 부분 일치
  • 칩의 숫자는 필터를 걸기 전 전체 기준입니다. 필터를 좁혀도 칩의 숫자는 변하지 않으므로, 다른 종류에 몇 건이 있는지 보면서 옮겨 다닐 수 있습니다.
  • 미종결만이 실질적인 기본 필터입니다 — 상태 하나를 숨기는 것이 아니라 "볼 필요가 있는 것만" 남깁니다.
  • 필터가 걸려 있으면 표 위에 12건 중 4건 표시 중.이 적히고 필터 해제 버튼이 나타납니다.
  • 조건에 맞는 것이 없으면 조건에 맞는 항목이 없습니다. 필터를 넓혀 보세요.라고 적힙니다. 등록부 자체가 비어 있을 때의 문구와 다릅니다.
  • 필터·정렬은 브라우저 안에서만 처리됩니다. 등록부는 한 화면 분량이고, 이것은 데이터가 아니라 "지금 이 화면"에 대한 질문이라 서버로 보내면 드롭다운을 만질 때마다 왕복이 생깁니다.
  • 필터 설정은 화면을 옮겨도 유지됩니다. 탭을 옮겼다고 조용히 초기화되면 안 되기 때문입니다.

정렬에서 값이 없는 항목

뒤로 갑니다. 기한 없는 위험이 내일 마감인 것보다 급하지 않고, 등급을 매기지 않은 것이 가장 노출된 것도 아니기 때문입니다. 동점은 등록 순(id 순)이라 편집 중에 행이 튀지 않습니다.

7.6 실무 예시

예시 1 — 위험이 이슈로 바뀌는 흐름

① 위험으로 등록 (2월)

필드 값
종류 위험
제목 고객사 테스트 서버 준비가 늦어질 수 있음
상태 열림
확률 보통
영향 높음
소유자 박PM
연결 대상 WBS 3.2 통합 테스트
대응 기한 2026-03-01
대응 방안 사내 임시 서버 확보 검토

→ 노출도 높음 (6). 상단 노란 배너의 노출도 높음에 잡힙니다.

② 실제로 일어남 (3월 5일) — 같은 항목을 수정으로 열어 종류만 이슈로 바꿉니다.

  • 확률 입력란이 사라집니다(이슈는 확률을 묻지 않습니다). 다만 이미 넣은 보통은 그대로 남아 노출도 6이 계속 표시됩니다. 노출도를 지우고 싶다면 종류를 바꾸기 전에 확률을 미지정으로 돌려 두세요.
  • 라벨이 대응 방안 → 해결 방안으로 바뀝니다. 내용을 실제 조치로 고칩니다.
  • 목록에서 위험 구역에서 이슈 구역으로 자리를 옮깁니다.
  • 기한 2026-03-01이 지났고 종결이 아니므로 기한 초과 로 잡히고 배너에 올라갑니다.

③ 해결 — 상태를 종결로 바꿉니다. 기한이 지났어도 더 이상 초과로 세지 않습니다. 제목에 취소선이 그이고 노출도 배지가 흐려지지만 행은 남습니다 — 무엇이 있었고 어떻게 풀었는지가 프로젝트의 기록입니다.

새 항목을 만들지 않은 것이 핵심입니다. 위험과 이슈를 따로 만들면 위험 쪽이 열림으로 남아 영원히 닫히지 않습니다.

예시 2 — 차단된 Story의 원인을 찾기

Board에서 카드 하나가 차단 표시로 멈춰 있습니다.

  1. 카드에 관련 RAID가 함께 표시됩니다. 차단 사유 바로 아래에 이슈 · 인증 라이브러리 취약점 · 김개발처럼 종류·제목·소유자가 붙습니다. "왜 막혔나"의 답이 두 곳에 흩어지면 안 되기 때문입니다.
  2. 여기 뜨는 것은 종결되지 않은 항목 중 그 Backlog 항목에 직접 연결됐거나 그 항목이 귀속된 Work Package에 연결된 것입니다. 실무에서 이슈는 Story보다 Work Package에 걸리는 일이 많아서 둘 다 봅니다.
  3. 아무것도 안 뜬다면 RAID에 아직 등록되지 않은 것입니다. RAID 화면에서 이슈로 등록하고 그 Backlog 항목(또는 Work Package)에 연결하세요. 다음에 Board를 열면 카드에 붙습니다.
  4. 반대 방향도 됩니다 — RAID 화면에서 연결 대상 열을 보면 그 이슈가 어느 Story·Sprint·업무에 걸려 있는지 한 줄로 보입니다.

이 흐름이 성립하려면 연결을 걸어 두어야 합니다. 연결 없는 이슈는 등록부에는 있지만 Board 카드 옆에는 나타나지 않습니다.

예시 3 — 가정을 기한과 함께 적기

"고객사가 3월에 테스트 서버를 준다"는 것은 위험이 아니라 가정입니다. 아직 나쁜 일이 아니라 확인해야 할 전제이기 때문입니다.

  • 종류 가정, 제목 3월 첫 주에 고객 테스트 서버 사용 가능
  • 기한 라벨이 확인 기한 이 되고, 대응 라벨은 확인 방법 이 됩니다 — 2/25 주간회의에서 고객 IT팀에 확인
  • 확률·영향은 묻지 않습니다. 가정은 등급을 매기는 대상이 아니라 확인하거나 깨지는 대상입니다.
  • 확인 기한이 지나도록 열려 있으면 기한 초과 배너에 잡힙니다. 가정에 기한을 넣는 이유가 이것입니다 — 확인하지 않은 전제는 조용히 잊히는 것이 가장 위험합니다.
  • 확인되면 종결, 틀린 것으로 밝혀지면 종류를 위험 또는 이슈로 바꿉니다.

7.7 주의할 점

  • RAID의 의존성은 일정에 영향을 주지 않습니다. 연결은 연관 표시일 뿐입니다. 일정 제약이 필요하면 간트에서 선후행 관계를 따로 거세요.
  • 보관 기능이 없습니다. RAID에는 삭제뿐이고, 삭제하면 연결까지 함께 사라집니다. 끝난 항목은 지우지 말고 종결로 두세요 — 종결된 항목은 흐리게 처리되고 기한 초과에서도 빠지며, 미종결만 필터로 시야에서 치울 수 있습니다.
  • 종류를 바꿔도 확률·영향 값은 남습니다. 폼이 묻지 않을 뿐 지워지지는 않으므로, 노출도를 없애려면 종류를 바꾸기 전에 값을 미지정으로 되돌리세요.
  • 소유자 목록은 프로젝트 구성원입니다. 비어 있으면 폼 아래에 "RACI 화면에서 구성원을 먼저 등록하면 선택할 수 있습니다"라고 안내합니다. 구성원을 지우면 그 항목의 소유자만 비워지고 항목은 남습니다.
  • 연결 대상 목록이 낡아 보이면 다른 화면에서 WBS·Sprint·Backlog를 고친 뒤입니다. RAID 화면에 다시 들어오면 갱신됩니다(캐시 키에 세 리비전과 로컬 날짜가 모두 들어 있습니다).
  • CSV로 내보낼 때는 화면 필터가 반영되지 않습니다. 내보내기는 프로젝트 화면에서 하고, 그 프로젝트의 RAID 전체를 새로 읽어 내보냅니다. 대신 판정값(노출도·기한 초과)과 기준일이 함께 들어갑니다.
  • 삭제 확인 창은 되돌릴 수 없습니다. 삭제된 항목과 그 연결은 복구할 방법이 없습니다.

8. Dashboard

두 탭이 한 쌍입니다. 요약은 다른 화면들의 숫자를 읽어 모아 보여 주기만 하고, 진척은 그 숫자가 나오게 하는 근거를 입력하는 곳입니다.

이 분리는 의도된 것입니다. 요약 탭에는 변경 API가 하나도 없습니다 — 같은 값을 고치는 경로가 둘이면 검증 규칙도 두 벌이 되기 때문입니다. 반대로 진척 탭에서 무언가를 승인하면 요약의 숫자가 곧바로 낡으므로, 요약 탭으로 돌아올 때 자동으로 다시 읽습니다.

화면 위쪽 공통 요소:

설명
프로젝트 셀렉트 다른 화면과 공유합니다
기준일 서버가 정한 "오늘". 여섯 화면의 데이터를 한 요청으로 모아 한 기준일을 붙입니다 — 브라우저가 여섯 번 나눠 부르면 카드마다 다른 오늘이 될 수 있습니다
새로고침 요약 탭에만 있습니다. 진척 탭은 변경할 때마다 응답 전체를 받아 오므로 필요가 없습니다

프로젝트가 하나도 없으면 카드 대신 "먼저 프로젝트를 등록해야 Dashboard 를 볼 수 있습니다"가, Work Package가 하나도 없으면 "WBS에 Work Package가 없습니다"가 뜨고 각각 해당 화면으로 가는 링크가 붙습니다.

8.1 요약 탭

8.1.1 카드 하나하나

대시보드는 아무것도 계산하지 않습니다. 진척·간트·Sprint·Backlog·RACI·RAID 서비스를 한 번씩 불러 배치할 뿐입니다. 그래서 WBS·간트·Dashboard의 진척은 언제나 같은 숫자입니다. 카드가 자기 식으로 계산하면 한 프로젝트에 네 번째 의견이 생깁니다.

목록은 카드마다 최대 5건만 싣습니다. 대시보드는 "어디를 볼지" 정하는 화면이고, 전체 목록은 각 화면에 있기 때문입니다. 다만 모든 항목이 링크라서 숫자에서 원인 항목으로 갈 수 있습니다 — 갈 수 없으면 카드가 막다른 길이 됩니다.

  3. 예상 종료는 "예상 종료를 적지 않은 항목은 계획대로 끝난다"고 보고 계산한 값입니다. 예측의 부재는 "늦지 않는다"가 아니라 "달리 알려진 바 없다"이고, 그 경우 계획이 가장 좋은 추정이기 때문입니다. 그래서 예상 종료가 계획 종료와 같다고 해서 아무도 예측을 하지 않았다는 뜻은 아닙니다 — 둘을 구분하려면 간트에서 예상 종료 표식이 있는 행을 봐야 합니다.

8.1.3 완료 Story Point 추세 읽는 법

막대 하나가 종료된 Sprint 하나이고, 높이는 그 Sprint에서 완료된 Story Point 합계입니다. 가장 높은 막대를 100%로 잡아 상대 높이를 그리고, 값은 막대 아래에 숫자로 적습니다 (칸이 적어 눈금축은 소음이 되기 때문입니다). 오래된 Sprint가 왼쪽입니다.

읽는 규칙:

  • 진행 중인 Sprint는 막대에 넣지 않습니다. 아직 움직이는 숫자라 Sprint 중간에 보면 매번 "하락"으로 읽힙니다. 대신 그래프 아래에 한 줄로 적습니다 — 진행 중 Sprint 8 — 현재 13포인트. 아직 움직이는 숫자라 추세에 넣지 않았습니다.
  • 이월된 항목은 완료한 Sprint 쪽에만 셉니다. 원 Sprint에는 이월로, 다음 Sprint에는 완료로 남으므로 한 항목이 두 막대에 들어가지 않습니다.
  • 종료된 Sprint의 막대는 그 뒤에 무슨 일이 있어도 움직이지 않습니다. 항목을 나중에 재오픈해도 과거 실적은 과거의 사실입니다.
  • 계열이 하나인 이유는 팀이 하나이기 때문입니다. 팀 개념이 생기면 계열이 나뉘어야 하고, 서로 다른 팀의 포인트를 합산해서는 안 됩니다 — 팀마다 포인트 기준이 다르기 때문입니다.
  • 종료된 Sprint의 포인트는 종료 시점에 찍어 둔 값입니다. 나중에 Story Point 추정을 고쳐도 지난 막대는 움직이지 않습니다.
  • Story Point가 비어 있는 항목은 0으로 셉니다. 추정을 안 한 채로 완료가 쌓이면 추세가 실제보다 낮게 보입니다.

8.2.1 진척 계산 방식

Work Package는 자기 실행 방식에 따라, 상위는 하위를 접어 올려 계산합니다. 저장하지 않고 읽을 때마다 다시 계산하므로, 항목을 재오픈하거나 범위를 늘리거나 가중치를 고쳐도 "재계산" 버튼이 필요 없습니다 — 다음 조회가 곧 재계산입니다.

산정 근거 언제 쓰이나 계산식
Agile Work Package · 실행 방식 = Agile 100 × Σ(완료된 Story·Bug의 진척 가중치) ÷ Σ(집계 대상 Story·Bug의 진척 가중치)
Waterfall Work Package · 실행 방식 = Waterfall 100 × Σ(승인된 체크포인트 가중치) ÷ Σ(전체 체크포인트 가중치)
Hybrid Work Package · 실행 방식 = Hybrid α × Agile + (1 − α) × Waterfall. α = Hybrid 비중(%) ÷ 100
수동 입력 Work Package · 실행 방식 미지정 WBS에 입력한 진행률 그대로
가중 집계 상위(Summary) · 직계 자식 중 하나라도 가중치가 있음 Σ(자식 가중치 × 자식 진척) ÷ Σ(자식 가중치)
하위 평균 상위(Summary) · 직계 자식에 가중치가 하나도 없음 자식의 leaf 개수를 가중치로 쓴 평균 (Step 5 이전과 같은 계산)
산정 전 아래 조건 중 하나 값이 null. 0%가 아닙니다

계산에 관한 세부 규칙:

  • 비어 있는 가중치는 1로 봅니다 (Story·Bug의 진척 가중치, 체크포인트 가중치). "가중치를 아직 안 넣었다"는 "비중이 같다"의 흔한 표현이기 때문입니다.
  • 집계 대상은 Story와 Bug뿐입니다. Epic을 그 안의 Story와 함께, Task를 그 Story와 함께 세면 같은 일을 두 번 셉니다. 보관된 항목도 빠집니다.
  • Story Point·진척 가중치·WBS 가중치는 서로 다른 값입니다. 포인트는 팀의 크기 추정, 진척 가중치는 한 Work Package 안 Backlog 항목의 비중, WBS 가중치는 형제 사이의 비중입니다. 같은 단위로 합산하지 마세요.
  • 프로젝트 전체 진척은 최상위 항목들을 접어 올린 값입니다. 모든 leaf를 평평하게 평균 내지 않으므로, 최상위 가지에 가중치를 주면 그것이 곧 "프로젝트에서 그 가지가 차지하는 몫"입니다.
  • 반올림은 화면에서만 합니다. 서버는 반올림하지 않은 값을 보내므로, 상위 값이 이미 반올림된 자식들로 계산되는 오차가 없습니다.

"산정 전"이 0%가 아닌 이유

분모가 없는 것과 분자가 0인 것은 다른 사실입니다. 착수도 하지 않은 프로젝트가 "0% 진행"으로 보이면, 정말 0%인 것(계획이 다 서 있는데 아무도 시작하지 않은 상태)과 구별할 수 없습니다. 그래서 앱 전체가 두 상태를 끝까지 갈라 둡니다 — 막대를 그리지 않고, 숫자 대신 "산정 전"이라고 적고, 상위 평균에서 조용히 빼는 대신 "집계가 불완전하다"고 알립니다.

산정 전이 되는 경우와, 화면이 이유로 적어 주는 한 줄:

상황 화면에 뜨는 이유

Waterfall인데 체크포인트가 하나도 없음 승인 체크포인트가 없습니다.

이 한 줄은 표의 진척 막대에 마우스를 올리면 툴팁으로, 행을 펼치면 본문으로 보입니다.

가중치를 모두 0으로 적으면 0%가 아니라 산정 전이 됩니다. 분모가 0이면 어떤 비율도 나오지 않으므로, 0%로 단정할 근거가 없다고 봅니다.

아무것도 지정하지 않은 프로젝트는 숫자가 변하지 않습니다

두 가지 전환 정책이 기존 프로젝트를 지킵니다.

  • 실행 방식을 지정하지 않은 Work Package → 수동 입력. 입력한 진행률을 그대로 씁니다.
  • 직계 자식에 가중치가 하나도 없는 상위 → 하위 평균. Step 5 이전과 같은 leaf 개수 평균입니다.

그래서 Agile 기능을 전혀 쓰지 않는 프로젝트의 화면 숫자는 예전과 동일합니다. 설계의 가중 계산은 가중치를 넣은 가지 단위로 하나씩 넘어옵니다.

인수는 진척과 직교합니다

인수 상태가 인수 대기이면서 진척이 100% 이상인 Work Package를 "인수 대기"로 셉니다. 실행이 끝난 것과 발주처가 받아 준 것은 다른 사실이라, 진척 100%를 곧바로 완료로 보지 않습니다. 표에서는 이름 옆에 인수 대기 칩이 붙고, 요약 탭에는 별도 카드로 나옵니다.

8.2.2 승인 체크포인트

Waterfall과 Hybrid 진척의 분모입니다. 체크포인트가 하나도 없는 Waterfall Work Package는 0%가 아니라 산정 전입니다 — 아직 잴 자가 없다는 뜻이기 때문입니다.

Work Package별 진척 표에서 행 오른쪽의 체크포인트 n/m 버튼을 누르면 그 행이 펼쳐집니다.

하는 일 방법
추가 펼친 영역 아래 입력줄: 제목(필수) · 가중치(선택) · 완료 조건(선택) → 추가
승인 항목의 승인 → 대화상자에서 승인자 이름 입력(필수)
승인 취소 항목의 승인 취소. 확인창 없이 즉시
삭제 항목의 삭제. 확인창 없이 즉시
  • 가중치를 비우면 균등으로 표시되고 1로 계산됩니다. 체크포인트 4개를 균등하게 두면 하나 승인할 때마다 25%씩 오릅니다.
  • 승인자 이름은 직접 적습니다. 로그인이 없기 때문입니다. 승인은 "누가 했는가"가 핵심이라 이름 없이는 승인할 수 없게 되어 있습니다.
  • 승인을 취소하면 승인자와 승인 시각이 함께 지워집니다. 더 이상 승인하지 않는 사람이 승인자로 남아 있으면 안 되기 때문입니다. "승인했다가 취소했다"는 사실은 변경 이력 (change_logs)에 남습니다 — 다만 그 이력을 보여 주는 화면은 아직 없습니다.
  • 체크포인트는 Work Package에만 둘 수 있습니다. Summary에 두려고 하면 '…'은(는) Summary라 승인 체크포인트를 둘 수 없습니다. 진척은 하위에서 집계됩니다.로 거부됩니다.
  • 가중치를 바꾸면 진척이 움직이므로 변경 이력에 기록됩니다(분모가 달라지기 때문입니다).

펼친 영역에는 Agile 쪽 재료도 함께 보입니다 — 집계 대상 Story·Bug 3/7 완료. 한 화면에서 Waterfall 분모와 Agile 분모를 같이 확인할 수 있습니다.

8.2.3 기준선(Baseline) 승인

계획 진척과 편차는 승인된 기준선에서만 나옵니다. 자동으로 승인되는 경로는 어디에도 없습니다 — 아무도 승인하지 않은 계획은 실적을 견줄 대상이 될 수 없기 때문입니다.

범위 비교 상자 오른쪽의 기준선 승인 버튼 → 대화상자에서 승인자(필수)와 메모(선택).

승인하면 그 시점의 모든 WBS 항목(Summary 포함)을 복사해 보존합니다.

복사되는 것 왜 복사인가
WBS 코드 · 이름 코드는 트리 위치에서 파생되므로 트리가 움직이면 복원할 수 없습니다
구분(Summary/Work Package) · 실행 방식
시작일 · 종료일 계획 진척의 분모
가중치 편차 계산에 기준선 쪽 가중치를 씁니다
완료 기준 그 Work Package의 체크포인트 제목·완료 조건을 /로 이어 붙인 한 덩이

참조가 아니라 복사인 이유는 단순합니다. 참조는 계획이 바뀌면 따라 움직이는데, 기준선은 바로 그것을 하지 않기 위해 존재합니다.

  • 버전은 프로젝트 안에서 1부터 올라갑니다 (v1, v2 …). 승인할 때마다 새 버전이 쌓이고 지난 버전은 지워지지 않습니다. 다만 화면과 계산은 가장 최근 버전 하나만 봅니다 — 여러 버전을 나란히 비교하는 화면은 없습니다.
  • WBS 항목이 하나도 없으면 승인이 거부됩니다 (WBS 항목이 없어 기준선을 승인할 수 없습니다.).
  • 기준선을 지우거나 되돌리는 버튼은 없습니다. 잘못 승인했다면 계획을 바로잡고 다시 승인해 새 버전을 만드는 것이 유일한 방법입니다.
  • 승인 후 배지에 기준선 v2 · 김재학 · 2026-09-01이 표시됩니다.

계획 진척은 이렇게 계산됩니다. 기준선에 든 항목 중 시작일과 종료일이 모두 있는 것만 대상으로, 각 항목의 "기준 기간 중 지난 비율"을 기준선 가중치로 가중 평균합니다.

  • 기준일이 시작일보다 앞이면 0%
  • 그 외에는 (시작일부터 기준일까지의 일수) ÷ (시작일부터 종료일까지의 일수), 종료일 포함, 100%를 넘지 않음
  • 달력일 기준입니다. 영업일·휴일 달력이 없으므로 주말에도 계획 진척이 올라갑니다

이것은 계획 곡선이지 실적이 아닙니다. 시간이 지났다는 것만으로 실제 진척을 채우는 일은 어디에서도 하지 않습니다.

8.2.4 범위 비교 — 편차를 같은 범위에서만 빼는 이유

기준선을 승인하고 나면 계획은 계속 움직입니다. 항목이 추가되고, 빠지고, 가중치가 바뀝니다. 이때 현재 범위의 실제 진척과 기준선 범위의 계획 진척을 그냥 빼면 안 됩니다 — 두 숫자가 서로 다른 프로젝트를 말하고 있기 때문입니다.

그래서 편차는 이렇게 냅니다.

편차 = (기준선에 든 항목만으로 다시 계산한 실제) − (기준선에 든 항목만으로 계산한 계획)

요약 탭의 진척 카드가 (같은 범위 실제 58%)를 편차 옆에 함께 적는 것이 이 값입니다. 헤드라인의 실제 진척(현재 범위 전체)과 다를 수 있고, 달라야 정상입니다.

범위 비교 상자가 그 차이를 설명합니다.

줄 뜻
기준 24개 항목 → 현재 27개 항목 수의 변화 (Summary 포함, 모든 WBS 항목)
추가 3 — 3.4 알림 발송, … 기준선에는 없고 지금 있는 항목
제외 1 — 2.5 레거시 이관 기준선에는 있고 지금 없는 항목(삭제됐거나 범위에서 빠짐)
가중치 변경 2 — 1.2 화면 설계 (3 → 5), … 값이 달라진 항목. 이전 → 현재로 적습니다
기준선 승인 이후 범위와 가중치가 그대로입니다. 셋 다 0건일 때

요약 탭의 기준 일정 카드에도 같은 사실이 한 문장으로 뜹니다 — 기준선 이후 범위가 바뀌었습니다 — 추가 3, 제외 1, 가중치 변경 2. 편차는 기준선에 든 항목만으로 계산했습니다.

진척이 떨어졌을 때 가장 흔한 원인이 여기 있습니다. 일이 되돌아간 것이 아니라 분모가 늘어난 것입니다. 범위 비교의 추가 건수를 먼저 보세요.

8.2.5 보고 스냅샷

진척은 늘 다시 계산됩니다. 그래서 "지금 어디까지 왔나"에는 항상 옳고, "지난달 보고서의 그 숫자"에는 쓸 수 없습니다 — 그 사이에 범위도 가중치도 정책도 움직였기 때문입니다. 스냅샷은 보고한 시점의 숫자를 적어 두는 장치입니다.

메모 입력줄 옆의 현재 진척 저장 버튼 하나가 전부입니다. 메모는 선택입니다.

저장되는 것: 기준일(서버가 정함) · 그때의 기준선 · 그때의 WBS 항목 수 · 가중치 합계 · 프로젝트 전체 지표(실제 · 계획 · 같은 범위 실제 · 편차 · 산정 전 건수 · 집계 불완전 여부 · 인수 대기 · 범위 추가/제외/가중치 변경 건수) · 메모.

목록에는 한 줄로 2026-09-01 · 실제 62% · 계획 71% · 기준선 v2 · 27개 항목 · 9월 1주차 보고 처럼 나옵니다.

  • 항목별 상세는 담지 않습니다. 큰 프로젝트에서 끝없이 커지고, 재현해야 하는 것은 프로젝트 수준의 보고 숫자이기 때문입니다.
  • 산정 전은 스냅샷에서도 null로 남습니다 — 0으로 바꾸지 않습니다.
  • 스냅샷은 수정·삭제할 수 없습니다. 보고한 사실을 나중에 고치면 스냅샷의 존재 이유가 사라집니다.
  • 스냅샷을 저장해도 다른 화면의 숫자는 움직이지 않습니다. 읽기만 하기 때문입니다.

8.3 실무 예시

가상의 프로젝트 "차세대 포털 구축"(Work Package 18개, Sprint 7개 진행)으로 두 가지 흐름을 보입니다.

예시 1 — 월요일 아침 주간 보고 만들기

1. Dashboard → 요약 탭. 오른쪽 위 기준일이 2026-09-07인지 확인합니다. 밤새 탭을 열어 두었다면 여기서 날짜가 넘어간 것을 볼 수 있고, 화면은 이미 새 기준일로 다시 읽은 상태입니다.

2. 진척 카드에서 세 숫자를 받아 적습니다.

62%  가중 집계
계획 진척   71%   (기준선 v2 범위)
편차        계획보다 9%p 뒤짐   (같은 범위 실제 62%)
Work Package  18개 · 산정 전 2개
Waterfall 9  Agile 6  Hybrid 2  미지정 1

산정 전 2개와 미지정 1을 기억해 둡니다 — 보고서에 "62%는 16개 기준"이라고 적어야 할 근거입니다.

3. 일정 카드에서 지연을 확인합니다. 지연 3 · 지연 위험 5 · 임계 4. 지연 상위 3건이 지연 일수 내림차순으로 나열되어 있습니다.

3.2 결제 연동        12일 지연
4.1 성능 시험         6일 지연
2.7 데이터 이관 검증   2일 지연

3.2 결제 연동을 누르면 WBS 화면의 그 행이 펼쳐진 채로 강조됩니다. 거기서 담당과 하위를 확인하고 브라우저 뒤로 가기로 돌아옵니다.

4. 기준 일정 카드에서 v2 · 24개 항목 / 2026-08-10 · 김재학을 확인합니다. 기준 종료일을 넘길 것으로 보이는 업무가 2건 있습니다 경고가 붙어 있다면 그 두 건이 보고서의 "리스케줄 검토 대상"입니다.

5. 실행 카드에서 이번 주 Sprint 상태를 옮겨 적습니다.

Sprint 8   2026-09-01 ~ 2026-09-12
Goal: 결제 모듈 사용자 시나리오 완주
완료 5/11   포인트 13/34   차단 1
  └ 결제 승인 콜백 처리   PG사 회신 대기 · 이수진
      의존성 PG사 테스트 계정 발급   박民수

차단 카드 아래에 관련 RAID 항목과 소유자가 함께 붙어 나오므로, "왜 막혔는가"와 "누가 풀어야 하는가"를 따로 찾을 필요가 없습니다.

6. 데이터 누락 카드를 마지막에 봅니다.

실행 방식 미지정 Work Package        1건
진척을 산정할 수 없는 Work Package    2건
Work Package에 연결되지 않은 Backlog 항목   4건

보고서에 "진척 62%는 산정 가능한 16개 Work Package 기준이며, 2건은 근거 미비로 제외"라고 적습니다. 이 문장이 없으면 62%가 18개 전체에 대한 숫자로 읽힙니다.

7. 진척 탭 → 보고 스냅샷. 메모에 9월 1주차 주간보고를 적고 현재 진척 저장. 다음 주에 "지난주엔 얼마였지"를 물을 때 이 줄이 답합니다.

8. 프로젝트 화면 → 내보내기 → WBS (CSV). 보고서에 붙일 표를 받습니다. CSV에는 지연 상태와 기준일이 함께 들어 있어 며칠 뒤 열어도 무엇 기준인지 알 수 있습니다.

예시 2 — 진척이 이상해 보일 때 원인 찾기

지난주 62%였는데 이번 주 58%로 내려갔습니다. 아무도 일을 되돌리지 않았는데 말입니다.

1. 산정 근거부터 봅니다. 진척 카드 헤드라인 옆의 라벨이 지난주와 같은지 확인합니다. 가중 집계 → 하위 평균으로 바뀌었다면 누군가 가중치를 지운 것이고, 가중 집계가 그대로라면 계산 방식이 바뀐 것은 아닙니다.

2. 데이터 누락 카드의 "산정 전" 건수를 비교합니다. 지난주 2건 → 이번 주 4건이면, 새로 들어온 Work Package 두 개가 아직 근거가 없어 빠진 것입니다. 이때는 헤드라인이 내려간 것이 아니라 다른 모집단을 말하고 있는 것입니다.

3. 진척 탭 → 범위 비교를 봅니다.

기준 24개 항목 → 현재 29개
추가 5 — 3.5 알림 발송, 3.6 알림 이력, 5.1 운영 이관, …

분모가 늘었습니다. 62%였을 때의 24개와 지금의 29개는 다른 프로젝트입니다.

4. 편차는 움직였는지 확인합니다. 편차는 기준선에 든 항목만으로 양쪽을 계산하므로, 범위가 늘어난 것만으로는 변하지 않습니다. 편차가 -9%p에서 그대로라면 원래 하던 일은 계획대로 진행 중이고, 새 범위가 들어와 전체 비율만 희석된 것입니다. 이것이 보고서에 적을 결론입니다.

5. 그래도 특정 Work Package가 의심되면 표를 봅니다. Work Package별 진척 표에서 기준 열이 산정 전인 행을 찾아 체크포인트 n/m 버튼으로 펼칩니다.

  • 체크포인트 0/0 + 체크포인트가 없습니다. Waterfall·Hybrid 진척은 이 목록이 분모이므로, 없으면 산정 전입니다. → 체크포인트를 등록하세요
  • 집계 대상 Story·Bug 0/0 → Agile Work Package인데 Story가 없습니다. Backlog에서 귀속시키세요
  • Hybrid 비중(α)이 정해지지 않았습니다. → WBS 편집에서 α를 정하세요

6. 반대로 진척이 갑자기 뛰었다면 같은 자리에서 제외 건수를 봅니다. 어려운 Work Package를 지우면 분모가 줄어 남은 것들의 비율이 올라갑니다. 화면은 이것을 "진행"이라고 부르지 않습니다 — 제외 2 — …가 그 사실을 그대로 적어 줍니다.

8.4 주의할 점

  • 요약 탭은 읽기 전용입니다. 여기서 고칠 수 있는 것은 없고, 모든 링크는 값을 소유한 화면으로 갑니다.
  • "산정 전"을 0%로 바꿔 읽지 마세요. 이 앱에서 가장 쉽게 저지르는 오독입니다. 진척 62%는 "산정 가능한 항목들에 대한 62%"이며, 산정 전 건수를 함께 말해야 정확합니다.
  • 계획 진척은 시간의 함수가 아니라 승인의 함수입니다. 기준선을 승인하지 않으면 프로젝트가 아무리 오래되어도 계획 진척은 미산정입니다. 이것은 결함이 아니라 정책입니다.
  • 기준선은 최신 하나만 봅니다. v1과 v3를 나란히 비교하는 화면이 없습니다.
  • 기준선을 지우거나 취소할 수 없습니다. 잘못 승인했다면 새 버전을 승인하는 것이 유일한 방법입니다.
  • 체크포인트 삭제·승인 취소에 확인창이 없습니다. 한 번 누르면 바로 반영되고, 그만큼 진척 숫자도 바로 움직입니다.
  • 체크포인트를 수정하는 UI가 없습니다. 제목이나 가중치를 고치려면 지우고 다시 만들어야 하고, 그러면 승인 기록도 함께 사라집니다.
  • 승인자·변경자는 그냥 입력한 문자열입니다. 로그인이 없으므로 권한이 아니라 기록입니다.
  • 진척률 변경 이력을 보는 화면이 없습니다. 데이터(change_logs)는 쌓이고 있지만 열어 볼 곳이 없습니다.
  • 마일스톤 개념이 없습니다. Dashboard가 말하는 날짜는 계획 종료일과 예상 종료일뿐입니다.
  • 속도 추세는 팀이 하나라는 전제 위에 있습니다. 팀이 여럿이 되면 계열을 나눠야 하고, 합산해서는 안 됩니다.
  • Work Package가 0개면 대부분의 카드가 비어 있습니다. WBS를 먼저 채우라는 안내가 뜹니다.

9. 내보내기와 가져오기

프로젝트 화면 한 곳에서만 합니다. 내보내는 단위가 프로젝트이기 때문입니다. 화면마다 버튼을 두면 "전체 JSON"이 여러 벌로 중복되고, 무엇이 내보내지는 단위인지도 흐려집니다.

9.1 무엇을 고를 수 있는가

프로젝트 행의 내보내기 버튼을 누르면 메뉴가 열립니다.

JSON과 CSV는 목적이 반대입니다

JSON에 판정값을 넣지 않는 이유는 그것들이 전부 "오늘" 또는 "다른 행"을 기준으로 계산되는 값이기 때문입니다. 지연 상태·선후행 위반·여유(float)·노출도·기한 초과가 파일에 박히는 순간 거짓이 됩니다. 예외는 WBS 코드 하나로, 사람이 파일을 읽을 때 필요해서 넣되 파생 값입니다.

CSV에는 반대로 판정값을 넣습니다. 그날 화면이 보여 준 것의 스냅샷이기 때문입니다. 그래서 기준일을 열 머리글에 박아 둡니다 — 지연 상태 (기준일 2026-09-07), 기한 초과 (기준일 2026-09-07). 며칠 뒤 파일을 열어도 무엇 기준인지 알 수 있습니다.

CSV에 관한 실무 사항

  • 파일 이름: 프로젝트이름-wbs-2026-09-07.csv 형식. 이름에서 문자·숫자·.·_·-가 아닌 것은 -로 바뀝니다.
  • 한글이 깨지지 않습니다. 파일 앞에 UTF-8 BOM을 붙여 Windows Excel이 시스템 코드페이지로 읽는 것을 막습니다.
  • 줄바꿈은 CRLF입니다(RFC 4180, Excel 기본).
  • RACI CSV 맨 끝에는 빈 줄 하나를 두고 범례가 붙습니다 — RACI: R=RESPONSIBLE, A=ACCOUNTABLE, C=CONSULTED, I=INFORMED. 받는 사람이 글자의 뜻을 알 수 있게 하려는 것이고, 표의 열 구조를 흐트러뜨리지 않도록 빈 줄로 떼어 놓습니다.
  • 화면의 필터를 따르지 않습니다. 프로젝트 화면에서 부르므로 그 프로젝트의 데이터를 새로 읽어 전부 내보냅니다. RAID 화면에서 "위험만" 걸러 놓아도 CSV에는 네 종류가 모두 들어갑니다.
  • 불리언 칸은 Y/N 으로, 빈 값은 빈 칸으로 나갑니다(null이라는 글자가 아니라).

JSON에 관한 실무 사항

  • 평범한 링크로 내려받습니다. 서버가 Content-Disposition: attachment로 내려주므로 별도의 처리가 없고, 개발 프록시와 설치본에서 똑같이 동작합니다. 한글 프로젝트 이름도 그대로 나옵니다.
  • 파일 이름: 프로젝트이름-export-2026-09-07.json
  • 형식 버전(formatVersion)은 6입니다. 파일에 함께 적혀 있습니다.
  • 파일 하나에 프로젝트 하나입니다. 전체를 한 번에 내보내는 기능은 없습니다.

담기는 것: 프로젝트 · 구성원 · WBS 항목(실적·예상 종료일, 가중치, Hybrid α, 인수 상태 포함) · 선후행 관계 · RACI 배정 · RAID 항목과 연결 · Backlog 항목(차단·완료 시각 포함) · Sprint와 배정 이력(종료 결과 포함) · 승인 체크포인트(승인자·승인 시각 포함) · 승인된 기준선 전부와 그 항목 스냅샷 · 보고 스냅샷.

담기지 않는 것: 변경 이력(change_logs), Backlog 귀속 변경 이력, 그리고 위에서 말한 모든 판정값.

9.2 가져오기가 하는 일과 하지 않는 일

프로젝트 화면 오른쪽 위 가져오기 버튼 → 파일 선택. 성공하면 초록 배너에 새 프로젝트 이름이 뜨고, 목록 아래에 새 행이 생깁니다.

하는 일

  • 항상 새 프로젝트를 만듭니다. 기존 프로젝트에 병합하려면 "이 항목이 이름만 바뀐 같은 업무인가"를 행마다 판단해야 하는데, 파일은 그 답을 갖고 있지 않습니다. 공유가 실제로 필요한 것도 "받은 프로젝트를 내 것 옆에 놓고 보는 것"입니다.
  • 이름이 겹치면 뒤에 (가져옴)을 붙입니다. 그것마저 겹치면 (가져옴 2), (가져옴 3) …
  • 모든 id를 다시 매깁니다. 파일의 id는 그것을 만든 설치본의 것이라 여기서는 의미가 없습니다. 상위부터 삽입하며 옛 id → 새 id 맵을 만들고, 선후행·RACI·RAID·Backlog·Sprint의 참조를 그 맵으로 바꿉니다. 파일 순서에 의존하지 않으므로 손으로 편집해 순서가 뒤섞인 파일도 들어옵니다.
  • 승인 상태를 그대로 가져옵니다. 체크포인트 승인, 기준선, 종료된 Sprint의 결과, Board의 차단·완료 시각까지. 승인은 사건이지 현재 데이터의 함수가 아니라서 다시 계산할 수 없고, 초기화해서 넘기면 아무것도 이루지 못한 프로젝트를 건네는 셈이 됩니다.
  • 구분(nodeType)은 파일 값을 믿지 않고 다시 정합니다. 파일에서 자식이 있으면 파일이 WORK_PACKAGE라고 적어도 SUMMARY로 바로잡습니다 — WBS 코드를 다시 계산하는 것과 같은 이유이고, 하위가 있는 Work Package는 편집 규칙이 허용하지 않는 상태라 받는 쪽에서 고칠 수도 없습니다.
  • Backlog의 귀속은 상위에서 물려받습니다. 자식 행에 다른 값이 적혀 있어도 무시합니다 — 이 모델에서 귀속은 언제나 가족의 맨 위에서 오기 때문입니다.
  • 구형 파일을 읽습니다. formatVersion 1~5도 들어옵니다. 없는 절은 빈 절과 같게 다루고, 버전 5 이하의 단일 wbsItemId는 WBS_ITEM 연결 하나가 됩니다.

하지 않는 일

  • 기존 프로젝트에 병합하지 않습니다.
  • 파일보다 높은 형식 버전은 거부합니다 — 이 버전이 읽을 수 없는 형식입니다 (파일 7, 지원 6). 앱을 업데이트하세요. 모르는 필드를 조용히 버리는 것보다 낫다고 보기 때문입니다.
  • 계획의 품질은 검증하지 않습니다. 아래는 경고 없이 그대로 들어옵니다 — 순환 선후행 관계, 상위·하위 사이의 선후행 관계, 미연결 Backlog, Summary에 귀속된 Backlog, 종료된 Sprint에서 이후 재오픈된 항목. 사용자 자신의 데이터이고, 그 문제는 각 화면이 이미 설명해 줍니다. 거부하면 데이터를 아예 못 넣게 됩니다.
  • 부분 가져오기가 없습니다. "WBS만" 같은 선택지는 없고, CSV는 읽지 못합니다.

거부되는 것 — 구조가 성립하지 않을 때

무엇이 문제인지 문장으로 알려 주고 아무것도 만들지 않습니다. 검증이 삽입보다 앞에 있어서, 거부된 파일은 빈 프로젝트조차 남기지 않습니다.

대상 거부 사유

WBS 이름 비어 있음, 상위가 파일에 없음, 자기 자신이 상위, 상위 참조 순환, id 중복

RACI 업무·구성원이 파일에 없음, 역할 비어 있음, 같은 (업무·구성원·역할) 중복

파싱 자체가 실패하면(가장 흔한 실수인 "파일을 잘못 골랐다") 요청 내용을 읽을 수 없습니다. 형식이 올바른 JSON인지 확인하세요.가 뜹니다. 값이 enum 범위를 벗어나면 어떤 필드에 무엇이 들어갈 수 있는지까지 알려 줍니다.

9.3 주의할 점

JSON은 백업이 아닙니다

이름이 "전체"라서 오해하기 쉽지만, 이 파일은 공유 수단이지 백업본이 아닙니다.

  1. 복원이 아니라 복제입니다. 가져오기는 항상 새 프로젝트를 만듭니다. 실수로 지운 프로젝트를 원래 자리로 되돌릴 수는 없습니다 — 옆에 하나 더 만들 수 있을 뿐이고, 다른 화면에서 걸어 둔 링크나 기억하던 id는 전부 달라집니다.
  2. 프로젝트 하나뿐입니다. 저장소 전체를 한 번에 내보내는 기능이 없어서, 프로젝트가 열 개면 파일도 열 개를 손으로 받아야 합니다.
  3. 생성일·수정일이 보존되지 않습니다. 가져온 프로젝트의 생성 시각은 가져온 날입니다.
  4. 변경 이력이 빠집니다. change_logs와 Backlog 귀속 변경 이력은 파일에 담기지 않으므로, "언제 누가 왜 바꿨나"는 넘어가지 않습니다.
  5. 판정값이 없습니다. 이것은 의도한 설계지만, 결과적으로 "그날 화면이 어땠는지"는 복원되지 않습니다.

진짜 백업은 데이터 폴더를 복사하는 것입니다. 데스크톱 설치본의 데이터는 ~/.project-flow/data/ 아래 H2 파일에 있습니다. 앱을 종료한 뒤 그 폴더째 복사해 두세요. 서버 프로필로 쓰고 있다면 PostgreSQL 백업이 그 자리를 대신합니다.

그 밖에

  • 가져온 프로젝트의 실적 데이터는 화면에서 수정하면 사라집니다. 실적 시작·종료일과 예상 종료일은 파일로는 들어오지만 WBS 편집 폼에 입력 칸이 없어, 그 항목을 화면에서 한 번 수정하면 값이 지워집니다. 수정이 필요하면 먼저 JSON으로 내보내 두세요.
  • CSV는 가져올 수 없습니다. Excel에서 고친 표를 되돌려 넣는 경로는 없습니다.
  • CSV 파일 이름의 날짜가 하루 어긋날 수 있습니다 — 발견한 결함 참고.
  • 내보내기 중 오류가 나면 버튼 옆에 작은 빨간 ! 가 붙습니다. 마우스를 올리면 사유가 뜨고, 누르면 사라집니다.
  • JSON 내보내기는 오류를 화면에 보여 주지 않습니다. 링크 이동 방식이라 실패하면 브라우저가 서버 응답(JSON 오류 본문)을 그대로 보여 주게 됩니다.

10. 일정관리 실무 — 이 도구로 프로젝트를 굴리는 법

앞의 장들이 "이 화면에서 무엇을 할 수 있는가"였다면, 이 장은 "프로젝트 관리자로서 언제 무엇을 하는가" 입니다. 가상의 프로젝트 하나를 착수부터 종료까지 끌고 가면서, 각 시점에 어느 화면을 열고 무엇을 보고 무엇을 판단하는지 적었습니다.

성격 앞은 문서·승인 중심(요구분석·설계), 가운데는 반복 개발, 끝은 인수

성격이 구간마다 다른 것이 핵심입니다. 요구분석을 Sprint로 관리하면 "완료 Story 수"가 의미 없고, 개발을 승인 체크포인트로 관리하면 2주마다 승인 문서를 만들어야 합니다. 그래서 이 도구는 실행 방식을 Work Package 단위로 고르게 합니다.

10.1 착수 — 뼈대 세우기 (1주차)

10.1.1 WBS 를 어디까지 쪼갤 것인가

기준은 "이 덩어리 하나에 책임자 한 명을 붙일 수 있는가" 입니다. 붙일 수 있으면 Work Package, 아직 여러 명이 갈라져야 하면 Summary 로 두고 더 쪼갭니다.

예제의 WBS 는 이렇게 됩니다.

1  요구분석            Summary
   1.1 현업 인터뷰      Work Package  · Waterfall · 가중치 1
   1.2 요구사항 명세서   Work Package  · Waterfall · 가중치 2
2  설계                Summary
   2.1 화면 설계        Work Package  · Waterfall · 가중치 2
   2.2 DB 설계          Work Package  · Waterfall · 가중치 2
3  개발                Summary
   3.1 예약 등록        Work Package  · Agile     · 가중치 5
   3.2 예약 조회·취소    Work Package  · Agile     · 가중치 4
   3.3 관리자 기능       Work Package  · Agile     · 가중치 3
4  인수                Summary
   4.1 통합 테스트       Work Package  · Hybrid α=70 · 가중치 3
   4.2 인수 인계        Work Package  · Waterfall · 가중치 1

너무 잘게 쪼개지 마세요. Work Package 가 50개를 넘어가면 가중치를 정하는 일 자체가 프로젝트가 됩니다. 6개월 프로젝트라면 10~20개가 다루기 좋습니다. 더 잘게 쪼갤 필요가 있으면 그건 WBS 가 아니라 Backlog 에서 하세요 — 그게 두 계층을 나눠 둔 이유입니다.

10.1.2 실행 방식 고르기

이럴 때 고를 것 진척이 나오는 조건
산출물이 문서·승인이다 Waterfall 승인 체크포인트를 등록해야 함
기능을 반복해서 붙여 나간다 Agile Story·Bug 를 Backlog 에 등록해야 함
개발도 하고 승인도 받는다 Hybrid 둘 다 + α(Agile 비중) 지정
아직 안 정했다 미지정 진행률을 손으로 입력

"미지정"을 부끄러워하지 마세요. 착수 시점에 뒤쪽 구간의 방식이 안 정해지는 건 정상입니다. 미지정이면 예전처럼 진행률을 손으로 적게 되고, 나중에 정하면 그때부터 자동 집계로 바뀝니다.

Hybrid 의 α 를 정하는 법: "이 Work Package 의 일 중 몇 %가 만드는 일이고 몇 %가 승인받는 일인가". 통합 테스트라면 테스트 수행이 대부분이고 마지막에 승인 한 번이니 α=70 정도입니다. α 를 안 넣으면 그 Work Package 는 계속 "산정 전" 입니다 — 비율을 아무도 정하지 않았는데 도구가 대신 정해 주지 않습니다.

주의 — 지금은 항목을 만들 때 고른 α 와 인수 상태가 저장되지 않습니다(발견한 문제). Hybrid Work Package 는 만든 다음 수정을 한 번 더 열어 α 를 넣어 주세요.

10.1.3 가중치 정하기

가중치는 "이 Work Package 가 프로젝트 전체에서 차지하는 무게" 입니다. 사람일수, 난이도, 중요도 중 무엇으로 잡아도 되지만 한 프로젝트 안에서는 한 기준으로 잡으세요.

가장 다루기 쉬운 방법은 예상 인일(man-day)을 10 으로 나눈 정수입니다. 위 예제의 3.1 예약 등록이 50인일이면 5입니다.

  • 비워 두면 "정하지 않음"이고 0이 아닙니다. 형제 중 하나라도 가중치가 있으면, 없는 형제는 집계에서 빠지고 부모에 불완전 표시가 붙습니다.
  • 아무도 안 정하면 예전처럼 하위 개수로 평균 냅니다(하위 평균). 이것도 정상적인 운영 방식입니다 — 다만 "요구사항 명세서"와 "예약 등록"이 같은 무게가 됩니다.

10.1.4 구성원과 책임 (RACI)

WBS 다음에 RACI 화면 아래에서 구성원부터 등록합니다. 사람이 없으면 매트릭스에 열이 없습니다.

단계(Summary)에 A 를 걸어 두는 것이 요령입니다. 상속되므로 그 아래 Work Package 마다 다시 찍을 필요가 없고, 예외가 있는 곳에서만 재정의하면 됩니다.

1 요구분석    A: PM,  R: PL          ← 여기만 찍으면
  1.1 현업 인터뷰                      ← 상속 (점선 흐린 글자)
  1.2 요구사항 명세서  R: 개발A        ← R 만 재정의, A 는 여전히 PM

배너에 실무 담당자 없음이 남아 있으면 그 업무는 아무도 안 하고 있는 것입니다. 착수 주에 0으로 만들어 두면 이후에 뜨는 경고는 전부 "새로 생긴 공백"이라 의미가 있습니다.

10.1.5 기준선(Baseline) 승인 — 언제 누르나

WBS 와 가중치가 확정되고 착수 승인이 난 직후입니다. 너무 이르면 곧 바뀌고, 너무 늦으면 비교할 기준이 없는 채로 몇 주가 흘러갑니다.

Dashboard → 진척 탭 → 기준선 승인. 지금의 범위·일정·가중치·완료 기준이 통째로 복사됩니다.

승인하기 전까지는 계획 진척이 "미산정"이고 간트에 "기준 일정 미등록"이 뜹니다. 시간이 지났다는 이유만으로 계획 진척을 만들어 내지 않기 때문입니다.

  3. RAID 에서 이번 주에 생긴 위험·이슈를 적고, 해소된 것을 종결합니다.

10.3 지연이 보일 때 — 원인을 찾아 들어가는 순서

증상에서 원인으로 내려가는 길이 화면 링크로 이어져 있습니다. 순서대로 따라가세요.

Dashboard 요약  "지연 3건, 최대 12일"
      │  지연 목록의 업무명 클릭
      ▼
WBS  해당 행이 펼쳐지고 강조됨
      │  ① 진척 칸의 근거 라벨을 본다 → 왜 이 숫자인가
      │  ② 연결 Backlog 칸을 클릭
      ▼
Backlog  그 Work Package 의 Story 목록
      │  완료가 안 된 Story 를 찾는다
      │  Sprint 칩이 붙어 있으면 클릭
      ▼
Board  그 카드의 상태와 차단 사유
      │  차단이면 관련 RAID 와 소유자가 카드에 함께 표시됨
      ▼
RAID  이슈의 대응 방안과 기한
      │
      ▼
RACI  그 업무의 A(최종 책임)에게 가져갈 것

예: "3.1 예약 등록이 12일 지연"

  1. WBS — 진척 40%, 근거는 Agile. 즉 Story 5개 중 2개 완료.
  2. 연결 Backlog 클릭 — 미완료 3개 중 하나가 Sprint 4 칩 + 차단 표시.
  3. Board — 카드에 차단: 외부 SSO 연동 스펙 미확정, 관련 RAID SSO 스펙 지연 (소유자 PL).
  4. RAID — 그 이슈의 기한이 이미 8일 초과. 대응 방안이 비어 있음.
  5. 판단 — 일정 문제가 아니라 외부 의존성 문제입니다. 일정을 미루는 것으로는 안 풀리고, PL 이 상대 조직과 스펙을 확정하는 것이 유일한 경로입니다.

여기서 하지 말아야 할 일: 간트에서 일정 재계산을 눌러 뒤로 밀고 "해결됐다"고 보는 것. 재계산은 날짜를 옮길 뿐 원인을 없애지 않습니다.

지연 배지를 읽을 때의 주의

지연 판정은 화면에 보이는 진척 %가 아니라 항목에 저장된 진행률로 합니다. Agile Work Package 는 Board 에서 Story 를 완료해도 저장된 진행률이 자동으로 오르지 않기 때문에, 진척 칸은 60%인데 지연 배지는 여전히 붙어 있는 상황이 생깁니다.

당분간의 운영 요령은 Agile Work Package 의 진행률을 주 1회 손으로 맞춰 주는 것입니다(금요일 루틴에 넣으세요). 근본 해결은 10.6 참고.

10.5 변경이 생겼을 때

범위가 추가될 때

현업이 "알림 기능도 넣어 달라"고 합니다.

  1. WBS 에 3.4 알림 발송 Work Package 를 추가하고 실행 방식·가중치를 지정합니다.
  2. Dashboard 요약에 즉시 나타나는 것: - 진척이 떨어집니다 (분모가 커졌으므로) - 기준 일정 카드에 범위 변화 — 추가 1 이 뜹니다
  3. 기준선을 다시 승인할지 결정합니다.
기준선 유지 기준선 재승인
편차가 말하는 것 "원래 계획 대비" "변경된 계획 대비"
이럴 때 변경이 작고, 원래 약속 대비 상태를 계속 보고 싶을 때 변경 승인을 정식으로 받았고, 이후는 새 계획으로 관리할 때

둘 다 정당합니다. 중요한 건 보고서에 어느 쪽인지 적는 것입니다. 재승인하면 v2 가 되고, 이전 스냅샷은 그대로 남아 과거 보고와 대조할 수 있습니다.

일정이 밀릴 때

  1. 간트 에서 해당 업무의 종료일을 늘립니다(WBS 편집).
  2. 선후행 관계가 걸려 있으면 일정 재계산으로 뒤 업무들을 함께 밀어냅니다. - 뒤로만 밀립니다. 여유가 생겨도 앞으로 당기지 않으니, 당기려면 직접 고쳐야 합니다.
  3. 기준선이 있으면 기준 종료일 초과 경고가 뜹니다. 이 경고는 계획을 고쳤다고 사라지지 않습니다 — 그게 기준선의 목적입니다.
