# 8. Dashboard

> 두 탭이 한 쌍입니다. **요약**은 다른 화면들의 숫자를 *읽어 모아 보여 주기만* 하고,
> **진척**은 그 숫자가 나오게 하는 *근거를 입력*하는 곳입니다.

이 분리는 의도된 것입니다. 요약 탭에는 변경 API가 하나도 없습니다 — 같은 값을 고치는 경로가
둘이면 검증 규칙도 두 벌이 되기 때문입니다. 반대로 진척 탭에서 무언가를 승인하면 요약의 숫자가
곧바로 낡으므로, **요약 탭으로 돌아올 때 자동으로 다시 읽습니다.**

화면 위쪽 공통 요소:

| | 설명 |
|---|---|
| **프로젝트 셀렉트** | 다른 화면과 공유합니다 |
| **기준일** | 서버가 정한 "오늘". **여섯 화면의 데이터를 한 요청으로 모아 한 기준일을 붙입니다** — 브라우저가 여섯 번 나눠 부르면 카드마다 다른 오늘이 될 수 있습니다 |
| **새로고침** | **요약 탭에만** 있습니다. 진척 탭은 변경할 때마다 응답 전체를 받아 오므로 필요가 없습니다 |

프로젝트가 하나도 없으면 카드 대신 "먼저 프로젝트를 등록해야 Dashboard 를 볼 수 있습니다"가,
Work Package가 하나도 없으면 "WBS에 Work Package가 없습니다"가 뜨고 각각 해당 화면으로 가는
링크가 붙습니다.

## 8.1 요약 탭

### 8.1.1 카드 하나하나

**대시보드는 아무것도 계산하지 않습니다.** 진척·간트·Sprint·Backlog·RACI·RAID 서비스를 한 번씩
불러 배치할 뿐입니다. 그래서 WBS·간트·Dashboard의 진척은 **언제나 같은 숫자**입니다.
카드가 자기 식으로 계산하면 한 프로젝트에 네 번째 의견이 생깁니다.

**목록은 카드마다 최대 5건**만 싣습니다. 대시보드는 "어디를 볼지" 정하는 화면이고, 전체 목록은
각 화면에 있기 때문입니다. 다만 **모든 항목이 링크**라서 숫자에서 원인 항목으로 갈 수 있습니다 —
갈 수 없으면 카드가 막다른 길이 됩니다.

| 카드 | 무엇을 말하는가 | 오른쪽 링크 | 항목을 누르면 |
|---|---|---|---|
| **진척** | 실제 진척(+산정 근거) · 계획 진척(기준선 vN 범위) · 편차 · Work Package 수(+산정 전 n개) · 실행 방식 분포 | 상세 → 진척 탭 | — |
| **일정** | 계획 기간(WBS 날짜 범위) · 예상 종료 · 지연/지연 위험/임계 건수 · **지연 상위 5건**(지연 일수 내림차순) | 간트 → `/gantt` | WBS 화면의 그 행으로 (펼쳐지고 강조) |
| **기준 일정** | 승인 버전·항목 수·승인일·승인자 · **기준 종료 초과 5건** · 기준선 이후 범위 변화 | 기준선 → 진척 탭 | WBS 화면의 그 행으로 |
| **실행** | 진행 중 Sprint의 이름·기간·Goal · 완료 n/m · 포인트 n/m · 차단 건수 · **차단 카드마다 사유·담당·관련 RAID** | Sprint → `/sprint` | 관련 RAID → `/raid` |
| **완료 Story Point 추세** | 종료된 Sprint의 막대 그래프 → [8.1.3](#813-완료-story-point-추세-읽는-법) | Sprint → `/sprint` | — |
| **책임** | 책임자 없음 / 담당자 없음 / 책임자 중복 건수 | RACI → `/raci` | — |
| **위험·이슈** | 기한 초과 · 노출도 높음 · 열린 이슈 (각 5건) | RAID → `/raid` | `/raid` |
| **인수 대기** | 실행 100%이지만 승인이 남은 업무 | — | WBS 화면의 그 행으로 |
| **데이터 누락** | 숫자가 답하지 못하는 부분 → [8.1.2](#812-데이터-누락-카드-읽는-법) | — | 원인이 있는 화면으로 |

**비어 있을 때 카드가 하는 말**도 정보입니다. 카드를 감추지 않고 문장을 남깁니다.

- 일정: `기준일 현재 지연된 업무가 없습니다.`
- 기준 일정: `승인된 기준선이 없습니다. 현재 계획을 기준선으로 보지 않으므로 계획 대비 편차와
  기준 초과는 표시하지 않습니다.`
- 실행: `진행 중인 Sprint가 없습니다.`
- 추세: `종료된 Sprint가 아직 없습니다.`
- 책임: `책임 공백이 없습니다.`
- 위험·이슈: `열린 위험·이슈가 없습니다.`

**인수 대기**와 **데이터 누락** 카드는 예외적으로 건수가 0이면 아예 나타나지 않습니다.

#### 카드를 읽을 때 헷갈리기 쉬운 세 가지

1. **"지연"과 "임계"는 다른 질문입니다.** 지연은 *계획 대비 현실*("오늘 기준으로 밀렸나"),
   임계는 *사슬 위의 위치*("이게 밀리면 프로젝트 종료일이 밀리나")입니다. 임계 건수가
   0이라고 안심할 일이 아니고, 지연 0인데 임계 5건인 것도 정상입니다.
2. **지연·지연 위험 건수는 최하위(leaf) 업무만 셉니다.** Summary는 하위의 지연을 이미
   반영하므로 함께 세면 한 건이 레벨마다 중복됩니다. (임계 건수만은 Summary를 포함합니다.)
3. **예상 종료는 "예상 종료를 적지 않은 항목은 계획대로 끝난다"고 보고 계산한 값**입니다.
   예측의 부재는 "늦지 않는다"가 아니라 "달리 알려진 바 없다"이고, 그 경우 계획이 가장 좋은
   추정이기 때문입니다. 그래서 예상 종료가 계획 종료와 같다고 해서 아무도 예측을 하지 않았다는
   뜻은 아닙니다 — 둘을 구분하려면 간트에서 예상 종료 표식이 있는 행을 봐야 합니다.

### 8.1.2 "데이터 누락" 카드 읽는 법

이 카드는 **위 숫자들이 침묵하고 있는 이유의 목록**입니다. 임의로 채우지 않는 것이 원칙이라,
빠진 값을 0이나 평균으로 대신하지 않고 여기에 건수로 신고합니다. 각주로 두지 않고 별도 카드로
둔 이유는, 각주로 두면 헤드라인만 읽고 지나가기 때문입니다.

다섯 종류가 있고, 각각 원인이 있는 화면으로 이동합니다.

| 표시되는 말 | 무엇을 센 것인가 | 누르면 가는 곳 |
|---|---|---|
| **실행 방식 미지정 Work Package** | `실행 방식`이 비어 있는 Work Package. 이 항목들은 진척이 **입력한 진행률 그대로**(`수동 입력`)입니다 | WBS 화면의 첫 번째 해당 행 |
| **가중치가 없는 Work Package** | `가중치`가 비어 있는 Work Package | 진척 탭 |
| **진척을 산정할 수 없는 Work Package** | 진척이 **산정 전(`null`)** 인 Work Package | 진척 탭 |
| **Work Package에 연결되지 않은 Backlog 항목** | 귀속 Work Package가 없는(보관되지 않은) Backlog 항목 | Backlog 화면 |
| **귀속 Work Package가 유효하지 않은 Backlog 항목** | 귀속 대상이 Summary가 되었거나 사라진 항목 | Backlog 화면 |

읽을 때 주의할 것:

- **"가중치가 없는 Work Package"는 결함 신고가 아니라 결정 대기 알림입니다.** 가중치를 아예 쓰지
  않는 프로젝트에서는 이 건수가 Work Package 전체 수와 같아집니다. 그 상태에서도 진척은 예전과
  똑같이(하위 개수 평균으로) 계산되므로 숫자가 틀린 것이 아닙니다 — "형제 사이의 비중을 아직
  아무도 정하지 않았다"는 사실을 알려줄 뿐입니다.
- **"산정 전"과 "0%"는 다릅니다.** 이 카드에 5건이 있다는 것은 "5개가 0%"가 아니라
  "5개는 셀 근거가 아직 없어서 헤드라인 숫자에서 빠져 있다"는 뜻입니다.
- **건수가 있으면 진척 카드에도 흔적이 남습니다.** 하위 일부가 산정 전이거나 가중치가 없으면
  진척 카드에 `일부 하위가 산정 전이거나 가중치가 없어 이 숫자에 빠져 있습니다. 0%로 대신하지
  않았습니다.`가 함께 붙습니다.
- **"미연결 Backlog"는 초안 단계에서는 정상**입니다. 실행 카드에도 같은 건수가 한 번 더
  나옵니다 — 같은 사실을 두 곳에서 세는 것이 아니라, 실행 카드는 "지금 돌아가는 것"의 맥락에서,
  이 카드는 "숫자의 침묵"의 맥락에서 보여 줍니다.

### 8.1.3 완료 Story Point 추세 읽는 법

막대 하나가 **종료된 Sprint 하나**이고, 높이는 그 Sprint에서 **완료된 Story Point 합계**입니다.
가장 높은 막대를 100%로 잡아 상대 높이를 그리고, 값은 막대 아래에 숫자로 적습니다
(칸이 적어 눈금축은 소음이 되기 때문입니다). 오래된 Sprint가 왼쪽입니다.

읽는 규칙:

- **진행 중인 Sprint는 막대에 넣지 않습니다.** 아직 움직이는 숫자라 Sprint 중간에 보면 매번
  "하락"으로 읽힙니다. 대신 그래프 아래에 한 줄로 적습니다 —
  `진행 중 Sprint 8 — 현재 13포인트. 아직 움직이는 숫자라 추세에 넣지 않았습니다.`
- **이월된 항목은 완료한 Sprint 쪽에만 셉니다.** 원 Sprint에는 `이월`로, 다음 Sprint에는
  `완료`로 남으므로 한 항목이 두 막대에 들어가지 않습니다.
- **종료된 Sprint의 막대는 그 뒤에 무슨 일이 있어도 움직이지 않습니다.** 항목을 나중에
  재오픈해도 과거 실적은 과거의 사실입니다.
- **계열이 하나인 이유는 팀이 하나이기 때문**입니다. 팀 개념이 생기면 계열이 나뉘어야 하고,
  **서로 다른 팀의 포인트를 합산해서는 안 됩니다** — 팀마다 포인트 기준이 다르기 때문입니다.
- **종료된 Sprint의 포인트는 종료 시점에 찍어 둔 값**입니다. 나중에 Story Point 추정을 고쳐도
  지난 막대는 움직이지 않습니다.
- **Story Point가 비어 있는 항목은 0으로 셉니다.** 추정을 안 한 채로 완료가 쌓이면 추세가
  실제보다 낮게 보입니다.

## 8.2 진척 탭

숫자의 **근거를 입력하는** 곳입니다. 위쪽에 프로젝트 전체 지표 4개, 그 아래 범위 비교,
Work Package별 진척 표, 마지막에 보고 스냅샷이 있습니다.

| 지표 타일 | 값이 없을 때 | 뜻 |
|---|---|---|
| **실제 진척** | `산정 전` | 현재 범위 전체에 대한 집계. 아래에 산정 근거(`가중 집계` 등) |
| **계획 진척** | `미산정` | 승인된 기준선 기준. 없으면 미산정 |
| **편차** | `미산정` | 같은 범위·가중치로 비교한 실제 − 계획 (%p) |
| **Work Package** | | 개수와 그중 산정 전 건수 |

상황에 따라 아래 문장들이 함께 뜹니다.

- `승인된 기준선이 없어 계획 진척은 미산정입니다. 시간이 지났다는 것만으로 진척을 채우지 않습니다.`
- `일부 하위가 산정 전이거나 가중치가 없어 집계가 불완전합니다. 위 숫자는 셀 수 있는 부분만을 말합니다.`
- `인수 대기 N건 — 진척 100%이지만 최종 인수가 남았습니다.`
- `산정 전: 3.2 결제 연동, 4.1 성능 시험` — **어떤 항목이 빠졌는지 이름으로 알려 줍니다.**

### 8.2.1 진척 계산 방식

**Work Package는 자기 실행 방식에 따라, 상위는 하위를 접어 올려** 계산합니다.
저장하지 않고 읽을 때마다 다시 계산하므로, 항목을 재오픈하거나 범위를 늘리거나 가중치를 고쳐도
"재계산" 버튼이 필요 없습니다 — **다음 조회가 곧 재계산**입니다.

| 산정 근거 | 언제 쓰이나 | 계산식 |
|---|---|---|
| **Agile** | Work Package · 실행 방식 = Agile | 100 × Σ(**완료된** Story·Bug의 진척 가중치) ÷ Σ(집계 대상 Story·Bug의 진척 가중치) |
| **Waterfall** | Work Package · 실행 방식 = Waterfall | 100 × Σ(**승인된** 체크포인트 가중치) ÷ Σ(전체 체크포인트 가중치) |
| **Hybrid** | Work Package · 실행 방식 = Hybrid | α × Agile + (1 − α) × Waterfall. α = `Hybrid 비중`(%) ÷ 100 |
| **수동 입력** | Work Package · 실행 방식 **미지정** | WBS에 입력한 `진행률` 그대로 |
| **가중 집계** | 상위(Summary) · 직계 자식 중 **하나라도** 가중치가 있음 | Σ(자식 가중치 × 자식 진척) ÷ Σ(자식 가중치) |
| **하위 평균** | 상위(Summary) · 직계 자식에 가중치가 **하나도** 없음 | 자식의 **leaf 개수**를 가중치로 쓴 평균 (Step 5 이전과 같은 계산) |
| **산정 전** | 아래 조건 중 하나 | 값이 `null`. 0%가 **아닙니다** |

계산에 관한 세부 규칙:

- **비어 있는 가중치는 1로 봅니다** (Story·Bug의 진척 가중치, 체크포인트 가중치).
  "가중치를 아직 안 넣었다"는 "비중이 같다"의 흔한 표현이기 때문입니다.
- **집계 대상은 Story와 Bug뿐**입니다. Epic을 그 안의 Story와 함께, Task를 그 Story와 함께 세면
  같은 일을 두 번 셉니다. **보관된 항목도 빠집니다.**
- **Story Point·진척 가중치·WBS 가중치는 서로 다른 값**입니다. 포인트는 팀의 크기 추정,
  진척 가중치는 한 Work Package 안 Backlog 항목의 비중, WBS 가중치는 형제 사이의 비중입니다.
  **같은 단위로 합산하지 마세요.**
- **프로젝트 전체 진척은 최상위 항목들을 접어 올린 값**입니다. 모든 leaf를 평평하게 평균 내지
  않으므로, 최상위 가지에 가중치를 주면 그것이 곧 "프로젝트에서 그 가지가 차지하는 몫"입니다.
- **반올림은 화면에서만** 합니다. 서버는 반올림하지 않은 값을 보내므로, 상위 값이 이미 반올림된
  자식들로 계산되는 오차가 없습니다.

#### "산정 전"이 0%가 아닌 이유

**분모가 없는 것과 분자가 0인 것은 다른 사실입니다.** 착수도 하지 않은 프로젝트가 "0% 진행"으로
보이면, 정말 0%인 것(계획이 다 서 있는데 아무도 시작하지 않은 상태)과 구별할 수 없습니다.
그래서 앱 전체가 두 상태를 끝까지 갈라 둡니다 — 막대를 그리지 않고, 숫자 대신 "산정 전"이라고
적고, 상위 평균에서 **조용히 빼는 대신** "집계가 불완전하다"고 알립니다.

산정 전이 되는 경우와, 화면이 이유로 적어 주는 한 줄:

| 상황 | 화면에 뜨는 이유 |
|---|---|
| Agile인데 집계 대상 Story·Bug가 하나도 없음 | `집계 대상 Story·Bug가 없습니다.` |
| Waterfall인데 체크포인트가 하나도 없음 | `승인 체크포인트가 없습니다.` |
| Hybrid인데 α를 정하지 않음 | `Hybrid 비중(α)이 정해지지 않았습니다.` |
| Hybrid인데 Agile 쪽 재료가 없음 | `Agile 요소에 집계 대상 Story·Bug가 없습니다.` |
| Hybrid인데 승인 쪽 재료가 없음 | `승인 요소에 체크포인트가 없습니다.` |
| Hybrid인데 양쪽 다 없음 | `집계 대상 Story·Bug와 승인 체크포인트가 모두 없습니다.` |
| 구분을 Summary로 바꿨는데 아직 자식이 없음 | `하위 항목이 없는 Summary입니다.` |
| 산정 가능한 하위가 하나도 없는 상위 | `산정 가능한 하위 항목이 없습니다.` |
| 하위 가중치의 합이 0인 상위 | `하위 가중치의 합이 0이거나 산정 가능한 하위가 없습니다.` |

이 한 줄은 표의 **진척 막대에 마우스를 올리면** 툴팁으로, **행을 펼치면** 본문으로 보입니다.

> **가중치를 모두 0으로 적으면 0%가 아니라 산정 전이 됩니다.** 분모가 0이면 어떤 비율도 나오지
> 않으므로, 0%로 단정할 근거가 없다고 봅니다.

#### 아무것도 지정하지 않은 프로젝트는 숫자가 변하지 않습니다

두 가지 전환 정책이 기존 프로젝트를 지킵니다.

- **실행 방식을 지정하지 않은 Work Package** → `수동 입력`. 입력한 진행률을 그대로 씁니다.
- **직계 자식에 가중치가 하나도 없는 상위** → `하위 평균`. Step 5 이전과 같은 leaf 개수 평균입니다.

그래서 Agile 기능을 전혀 쓰지 않는 프로젝트의 화면 숫자는 예전과 동일합니다.
설계의 가중 계산은 가중치를 넣은 **가지 단위로 하나씩** 넘어옵니다.

#### 인수는 진척과 직교합니다

`인수 상태`가 **인수 대기**이면서 진척이 **100% 이상**인 Work Package를 "인수 대기"로 셉니다.
실행이 끝난 것과 발주처가 받아 준 것은 다른 사실이라, 진척 100%를 곧바로 완료로 보지 않습니다.
표에서는 이름 옆에 `인수 대기` 칩이 붙고, 요약 탭에는 별도 카드로 나옵니다.

### 8.2.2 승인 체크포인트

**Waterfall과 Hybrid 진척의 분모**입니다. 체크포인트가 하나도 없는 Waterfall Work Package는
0%가 아니라 산정 전입니다 — 아직 잴 자가 없다는 뜻이기 때문입니다.

**Work Package별 진척 표**에서 행 오른쪽의 `체크포인트 n/m` 버튼을 누르면 그 행이 펼쳐집니다.

| 하는 일 | 방법 |
|---|---|
| **추가** | 펼친 영역 아래 입력줄: 제목(필수) · 가중치(선택) · 완료 조건(선택) → `추가` |
| **승인** | 항목의 `승인` → 대화상자에서 **승인자 이름** 입력(필수) |
| **승인 취소** | 항목의 `승인 취소`. 확인창 없이 즉시 |
| **삭제** | 항목의 `삭제`. 확인창 없이 즉시 |

- **가중치를 비우면 `균등`으로 표시되고 1로 계산**됩니다. 체크포인트 4개를 균등하게 두면
  하나 승인할 때마다 25%씩 오릅니다.
- **승인자 이름은 직접 적습니다.** 로그인이 없기 때문입니다. 승인은 "누가 했는가"가 핵심이라
  이름 없이는 승인할 수 없게 되어 있습니다.
- **승인을 취소하면 승인자와 승인 시각이 함께 지워집니다.** 더 이상 승인하지 않는 사람이
  승인자로 남아 있으면 안 되기 때문입니다. "승인했다가 취소했다"는 사실은 변경 이력
  (`change_logs`)에 남습니다 — 다만 **그 이력을 보여 주는 화면은 아직 없습니다.**
- **체크포인트는 Work Package에만** 둘 수 있습니다. Summary에 두려고 하면
  `'…'은(는) Summary라 승인 체크포인트를 둘 수 없습니다. 진척은 하위에서 집계됩니다.`로 거부됩니다.
- **가중치를 바꾸면 진척이 움직이므로 변경 이력에 기록**됩니다(분모가 달라지기 때문입니다).

> 펼친 영역에는 Agile 쪽 재료도 함께 보입니다 — `집계 대상 Story·Bug 3/7 완료`.
> 한 화면에서 Waterfall 분모와 Agile 분모를 같이 확인할 수 있습니다.

### 8.2.3 기준선(Baseline) 승인

**계획 진척과 편차는 승인된 기준선에서만 나옵니다.** 자동으로 승인되는 경로는 어디에도
없습니다 — 아무도 승인하지 않은 계획은 실적을 견줄 대상이 될 수 없기 때문입니다.

범위 비교 상자 오른쪽의 **기준선 승인** 버튼 → 대화상자에서 **승인자**(필수)와 **메모**(선택).

승인하면 그 시점의 **모든 WBS 항목**(Summary 포함)을 **복사해** 보존합니다.

| 복사되는 것 | 왜 복사인가 |
|---|---|
| WBS 코드 · 이름 | 코드는 트리 위치에서 파생되므로 트리가 움직이면 복원할 수 없습니다 |
| 구분(Summary/Work Package) · 실행 방식 | |
| 시작일 · 종료일 | 계획 진척의 분모 |
| 가중치 | 편차 계산에 기준선 쪽 가중치를 씁니다 |
| 완료 기준 | 그 Work Package의 체크포인트 제목·완료 조건을 `/`로 이어 붙인 한 덩이 |

참조가 아니라 복사인 이유는 단순합니다. **참조는 계획이 바뀌면 따라 움직이는데, 기준선은
바로 그것을 하지 않기 위해 존재합니다.**

- **버전은 프로젝트 안에서 1부터 올라갑니다** (`v1`, `v2` …). 승인할 때마다 새 버전이 쌓이고
  **지난 버전은 지워지지 않습니다.** 다만 화면과 계산은 **가장 최근 버전 하나만** 봅니다 —
  여러 버전을 나란히 비교하는 화면은 없습니다.
- **WBS 항목이 하나도 없으면 승인이 거부**됩니다
  (`WBS 항목이 없어 기준선을 승인할 수 없습니다.`).
- **기준선을 지우거나 되돌리는 버튼은 없습니다.** 잘못 승인했다면 계획을 바로잡고 다시 승인해
  새 버전을 만드는 것이 유일한 방법입니다.
- 승인 후 배지에 `기준선 v2 · 김재학 · 2026-09-01`이 표시됩니다.

**계획 진척은 이렇게 계산됩니다.** 기준선에 든 항목 중 **시작일과 종료일이 모두 있는 것**만
대상으로, 각 항목의 "기준 기간 중 지난 비율"을 기준선 가중치로 가중 평균합니다.

- 기준일이 시작일보다 앞이면 0%
- 그 외에는 `(시작일부터 기준일까지의 일수) ÷ (시작일부터 종료일까지의 일수)`, **종료일 포함**,
  100%를 넘지 않음
- **달력일 기준**입니다. 영업일·휴일 달력이 없으므로 주말에도 계획 진척이 올라갑니다

이것은 **계획 곡선**이지 실적이 아닙니다. 시간이 지났다는 것만으로 실제 진척을 채우는 일은
어디에서도 하지 않습니다.

### 8.2.4 범위 비교 — 편차를 같은 범위에서만 빼는 이유

기준선을 승인하고 나면 계획은 계속 움직입니다. 항목이 추가되고, 빠지고, 가중치가 바뀝니다.
이때 **현재 범위의 실제 진척**과 **기준선 범위의 계획 진척**을 그냥 빼면 안 됩니다 —
**두 숫자가 서로 다른 프로젝트를 말하고 있기 때문**입니다.

그래서 편차는 이렇게 냅니다.

```
편차 = (기준선에 든 항목만으로 다시 계산한 실제) − (기준선에 든 항목만으로 계산한 계획)
```

요약 탭의 진척 카드가 `(같은 범위 실제 58%)`를 편차 옆에 함께 적는 것이 이 값입니다.
헤드라인의 실제 진척(현재 범위 전체)과 **다를 수 있고, 달라야 정상**입니다.

**범위 비교 상자**가 그 차이를 설명합니다.

| 줄 | 뜻 |
|---|---|
| `기준 24개 항목 → 현재 27개` | 항목 수의 변화 (Summary 포함, 모든 WBS 항목) |
| `추가 3 — 3.4 알림 발송, …` | 기준선에는 없고 지금 있는 항목 |
| `제외 1 — 2.5 레거시 이관` | 기준선에는 있고 지금 없는 항목(삭제됐거나 범위에서 빠짐) |
| `가중치 변경 2 — 1.2 화면 설계 (3 → 5), …` | 값이 달라진 항목. 이전 → 현재로 적습니다 |
| `기준선 승인 이후 범위와 가중치가 그대로입니다.` | 셋 다 0건일 때 |

요약 탭의 **기준 일정 카드**에도 같은 사실이 한 문장으로 뜹니다 —
`기준선 이후 범위가 바뀌었습니다 — 추가 3, 제외 1, 가중치 변경 2. 편차는 기준선에 든 항목만으로
계산했습니다.`

> **진척이 떨어졌을 때 가장 흔한 원인이 여기 있습니다.** 일이 되돌아간 것이 아니라 **분모가
> 늘어난** 것입니다. 범위 비교의 `추가` 건수를 먼저 보세요.

### 8.2.5 보고 스냅샷

**진척은 늘 다시 계산됩니다.** 그래서 "지금 어디까지 왔나"에는 항상 옳고, "지난달 보고서의 그
숫자"에는 쓸 수 없습니다 — 그 사이에 범위도 가중치도 정책도 움직였기 때문입니다.
스냅샷은 **보고한 시점의 숫자를 적어 두는** 장치입니다.

메모 입력줄 옆의 **현재 진척 저장** 버튼 하나가 전부입니다. 메모는 선택입니다.

저장되는 것: 기준일(서버가 정함) · 그때의 기준선 · 그때의 WBS 항목 수 · 가중치 합계 ·
프로젝트 전체 지표(실제 · 계획 · 같은 범위 실제 · 편차 · 산정 전 건수 · 집계 불완전 여부 ·
인수 대기 · 범위 추가/제외/가중치 변경 건수) · 메모.

목록에는 한 줄로 `2026-09-01 · 실제 62% · 계획 71% · 기준선 v2 · 27개 항목 · 9월 1주차 보고`
처럼 나옵니다.

- **항목별 상세는 담지 않습니다.** 큰 프로젝트에서 끝없이 커지고, 재현해야 하는 것은
  프로젝트 수준의 보고 숫자이기 때문입니다.
- **산정 전은 스냅샷에서도 `null`로 남습니다** — 0으로 바꾸지 않습니다.
- **스냅샷은 수정·삭제할 수 없습니다.** 보고한 사실을 나중에 고치면 스냅샷의 존재 이유가
  사라집니다.
- 스냅샷을 저장해도 다른 화면의 숫자는 움직이지 않습니다. 읽기만 하기 때문입니다.

## 8.3 실무 예시

가상의 프로젝트 **"차세대 포털 구축"**(Work Package 18개, Sprint 7개 진행)으로 두 가지 흐름을
보입니다.

### 예시 1 — 월요일 아침 주간 보고 만들기

**1. Dashboard → 요약 탭.** 오른쪽 위 기준일이 `2026-09-07`인지 확인합니다. 밤새 탭을 열어
두었다면 여기서 날짜가 넘어간 것을 볼 수 있고, 화면은 이미 새 기준일로 다시 읽은 상태입니다.

**2. 진척 카드에서 세 숫자를 받아 적습니다.**

```
62%  가중 집계
계획 진척   71%   (기준선 v2 범위)
편차        계획보다 9%p 뒤짐   (같은 범위 실제 62%)
Work Package  18개 · 산정 전 2개
Waterfall 9  Agile 6  Hybrid 2  미지정 1
```

`산정 전 2개`와 `미지정 1`을 기억해 둡니다 — 보고서에 "62%는 16개 기준"이라고 적어야 할
근거입니다.

**3. 일정 카드에서 지연을 확인합니다.** `지연 3 · 지연 위험 5 · 임계 4`. 지연 상위 3건이
지연 일수 내림차순으로 나열되어 있습니다.

```
3.2 결제 연동        12일 지연
4.1 성능 시험         6일 지연
2.7 데이터 이관 검증   2일 지연
```

`3.2 결제 연동`을 누르면 **WBS 화면의 그 행이 펼쳐진 채로 강조**됩니다. 거기서 담당과 하위를
확인하고 브라우저 뒤로 가기로 돌아옵니다.

**4. 기준 일정 카드**에서 `v2 · 24개 항목 / 2026-08-10 · 김재학`을 확인합니다.
`기준 종료일을 넘길 것으로 보이는 업무가 2건 있습니다` 경고가 붙어 있다면 그 두 건이
보고서의 "리스케줄 검토 대상"입니다.

**5. 실행 카드**에서 이번 주 Sprint 상태를 옮겨 적습니다.

```
Sprint 8   2026-09-01 ~ 2026-09-12
Goal: 결제 모듈 사용자 시나리오 완주
완료 5/11   포인트 13/34   차단 1
  └ 결제 승인 콜백 처리   PG사 회신 대기 · 이수진
      의존성 PG사 테스트 계정 발급   박民수
```

차단 카드 아래에 **관련 RAID 항목과 소유자가 함께** 붙어 나오므로, "왜 막혔는가"와 "누가
풀어야 하는가"를 따로 찾을 필요가 없습니다.

**6. 데이터 누락 카드**를 마지막에 봅니다.

```
실행 방식 미지정 Work Package        1건
진척을 산정할 수 없는 Work Package    2건
Work Package에 연결되지 않은 Backlog 항목   4건
```

보고서에 "진척 62%는 산정 가능한 16개 Work Package 기준이며, 2건은 근거 미비로 제외"라고
적습니다. 이 문장이 없으면 62%가 18개 전체에 대한 숫자로 읽힙니다.

**7. 진척 탭 → 보고 스냅샷.** 메모에 `9월 1주차 주간보고`를 적고 **현재 진척 저장**.
다음 주에 "지난주엔 얼마였지"를 물을 때 이 줄이 답합니다.

**8. 프로젝트 화면 → 내보내기 → WBS (CSV).** 보고서에 붙일 표를 받습니다. CSV에는 지연 상태와
기준일이 함께 들어 있어 며칠 뒤 열어도 무엇 기준인지 알 수 있습니다.

### 예시 2 — 진척이 이상해 보일 때 원인 찾기

지난주 62%였는데 이번 주 **58%**로 내려갔습니다. 아무도 일을 되돌리지 않았는데 말입니다.

**1. 산정 근거부터 봅니다.** 진척 카드 헤드라인 옆의 라벨이 지난주와 같은지 확인합니다.
`가중 집계` → `하위 평균`으로 바뀌었다면 누군가 가중치를 지운 것이고,
`가중 집계`가 그대로라면 계산 방식이 바뀐 것은 아닙니다.

**2. 데이터 누락 카드의 "산정 전" 건수를 비교합니다.** 지난주 2건 → 이번 주 4건이면,
새로 들어온 Work Package 두 개가 아직 근거가 없어 빠진 것입니다. 이때는 **헤드라인이 내려간
것이 아니라 다른 모집단을 말하고 있는 것**입니다.

**3. 진척 탭 → 범위 비교를 봅니다.**

```
기준 24개 항목 → 현재 29개
추가 5 — 3.5 알림 발송, 3.6 알림 이력, 5.1 운영 이관, …
```

**분모가 늘었습니다.** 62%였을 때의 24개와 지금의 29개는 다른 프로젝트입니다.

**4. 편차는 움직였는지 확인합니다.** 편차는 **기준선에 든 항목만으로** 양쪽을 계산하므로,
범위가 늘어난 것만으로는 변하지 않습니다. 편차가 `-9%p`에서 그대로라면 **원래 하던 일은
계획대로 진행 중이고, 새 범위가 들어와 전체 비율만 희석된 것**입니다.
이것이 보고서에 적을 결론입니다.

**5. 그래도 특정 Work Package가 의심되면 표를 봅니다.** `Work Package별 진척` 표에서
`기준` 열이 `산정 전`인 행을 찾아 `체크포인트 n/m` 버튼으로 펼칩니다.

- `체크포인트 0/0` + `체크포인트가 없습니다. Waterfall·Hybrid 진척은 이 목록이 분모이므로,
  없으면 산정 전입니다.` → 체크포인트를 등록하세요
- `집계 대상 Story·Bug 0/0` → Agile Work Package인데 Story가 없습니다. Backlog에서 귀속시키세요
- `Hybrid 비중(α)이 정해지지 않았습니다.` → WBS 편집에서 α를 정하세요

**6. 반대로 진척이 갑자기 뛰었다면** 같은 자리에서 `제외` 건수를 봅니다. 어려운 Work Package를
지우면 분모가 줄어 남은 것들의 비율이 올라갑니다. 화면은 이것을 "진행"이라고 부르지 않습니다 —
`제외 2 — …`가 그 사실을 그대로 적어 줍니다.

## 8.4 주의할 점

- **요약 탭은 읽기 전용입니다.** 여기서 고칠 수 있는 것은 없고, 모든 링크는 값을 소유한 화면으로
  갑니다.
- **"산정 전"을 0%로 바꿔 읽지 마세요.** 이 앱에서 가장 쉽게 저지르는 오독입니다.
  진척 62%는 "산정 가능한 항목들에 대한 62%"이며, 산정 전 건수를 함께 말해야 정확합니다.
- **계획 진척은 시간의 함수가 아니라 승인의 함수입니다.** 기준선을 승인하지 않으면 프로젝트가
  아무리 오래되어도 계획 진척은 `미산정`입니다. 이것은 결함이 아니라 정책입니다.
- **기준선은 최신 하나만 봅니다.** v1과 v3를 나란히 비교하는 화면이 없습니다.
- **기준선을 지우거나 취소할 수 없습니다.** 잘못 승인했다면 새 버전을 승인하는 것이 유일한
  방법입니다.
- **체크포인트 삭제·승인 취소에 확인창이 없습니다.** 한 번 누르면 바로 반영되고, 그만큼 진척
  숫자도 바로 움직입니다.
- **체크포인트를 수정하는 UI가 없습니다.** 제목이나 가중치를 고치려면 지우고 다시 만들어야 하고,
  그러면 승인 기록도 함께 사라집니다.
- **승인자·변경자는 그냥 입력한 문자열입니다.** 로그인이 없으므로 권한이 아니라 기록입니다.
- **진척률 변경 이력을 보는 화면이 없습니다.** 데이터(`change_logs`)는 쌓이고 있지만 열어 볼
  곳이 없습니다.
- **마일스톤 개념이 없습니다.** Dashboard가 말하는 날짜는 계획 종료일과 예상 종료일뿐입니다.
- **속도 추세는 팀이 하나라는 전제 위에 있습니다.** 팀이 여럿이 되면 계열을 나눠야 하고,
  합산해서는 안 됩니다.
- **Work Package가 0개면 대부분의 카드가 비어 있습니다.** WBS를 먼저 채우라는 안내가 뜹니다.
