# 10. 일정관리 실무 — 이 도구로 프로젝트를 굴리는 법

> 앞의 장들이 "이 화면에서 무엇을 할 수 있는가"였다면, 이 장은 **"프로젝트 관리자로서 언제 무엇을
> 하는가"** 입니다. 가상의 프로젝트 하나를 착수부터 종료까지 끌고 가면서, 각 시점에 어느 화면을 열고
> 무엇을 보고 무엇을 판단하는지 적었습니다.

---

## 10.0 예제 프로젝트

이 장 전체에서 쓸 예제입니다.

| | |
|---|---|
| **이름** | 사내 예약 시스템 구축 |
| **기간** | 2026-03-02 ~ 2026-08-31 (6개월) |
| **인원** | PM 1, PL 1, 개발 3, QA 1 |
| **성격** | 앞은 문서·승인 중심(요구분석·설계), 가운데는 반복 개발, 끝은 인수 |

**성격이 구간마다 다른 것이 핵심입니다.** 요구분석을 Sprint로 관리하면 "완료 Story 수"가 의미 없고,
개발을 승인 체크포인트로 관리하면 2주마다 승인 문서를 만들어야 합니다. 그래서 이 도구는 실행 방식을
**Work Package 단위로** 고르게 합니다.

## 10.1 착수 — 뼈대 세우기 (1주차)

### 10.1.1 WBS 를 어디까지 쪼갤 것인가

**기준은 "이 덩어리 하나에 책임자 한 명을 붙일 수 있는가"** 입니다. 붙일 수 있으면 Work Package,
아직 여러 명이 갈라져야 하면 Summary 로 두고 더 쪼갭니다.

예제의 WBS 는 이렇게 됩니다.

```text
1  요구분석            Summary
   1.1 현업 인터뷰      Work Package  · Waterfall · 가중치 1
   1.2 요구사항 명세서   Work Package  · Waterfall · 가중치 2
2  설계                Summary
   2.1 화면 설계        Work Package  · Waterfall · 가중치 2
   2.2 DB 설계          Work Package  · Waterfall · 가중치 2
3  개발                Summary
   3.1 예약 등록        Work Package  · Agile     · 가중치 5
   3.2 예약 조회·취소    Work Package  · Agile     · 가중치 4
   3.3 관리자 기능       Work Package  · Agile     · 가중치 3
4  인수                Summary
   4.1 통합 테스트       Work Package  · Hybrid α=70 · 가중치 3
   4.2 인수 인계        Work Package  · Waterfall · 가중치 1
```

**너무 잘게 쪼개지 마세요.** Work Package 가 50개를 넘어가면 가중치를 정하는 일 자체가 프로젝트가
됩니다. 6개월 프로젝트라면 10~20개가 다루기 좋습니다. 더 잘게 쪼갤 필요가 있으면 그건 WBS 가 아니라
**Backlog 에서** 하세요 — 그게 두 계층을 나눠 둔 이유입니다.

### 10.1.2 실행 방식 고르기

| 이럴 때 | 고를 것 | 진척이 나오는 조건 |
|---|---|---|
| 산출물이 문서·승인이다 | **Waterfall** | 승인 체크포인트를 등록해야 함 |
| 기능을 반복해서 붙여 나간다 | **Agile** | Story·Bug 를 Backlog 에 등록해야 함 |
| 개발도 하고 승인도 받는다 | **Hybrid** | 둘 다 + α(Agile 비중) 지정 |
| 아직 안 정했다 | **미지정** | 진행률을 손으로 입력 |

**"미지정"을 부끄러워하지 마세요.** 착수 시점에 뒤쪽 구간의 방식이 안 정해지는 건 정상입니다.
미지정이면 예전처럼 진행률을 손으로 적게 되고, 나중에 정하면 그때부터 자동 집계로 바뀝니다.

**Hybrid 의 α 를 정하는 법**: "이 Work Package 의 일 중 몇 %가 만드는 일이고 몇 %가 승인받는
일인가". 통합 테스트라면 테스트 수행이 대부분이고 마지막에 승인 한 번이니 α=70 정도입니다.
**α 를 안 넣으면 그 Work Package 는 계속 "산정 전"** 입니다 — 비율을 아무도 정하지 않았는데
도구가 대신 정해 주지 않습니다.

> Hybrid 는 만들 때 α 를 함께 지정할 수 있습니다. 비워 두면 그 Work Package 는 "산정 전"으로
> 남습니다 — 비율을 아무도 정하지 않았는데 도구가 대신 정해 주지 않습니다.

### 10.1.3 가중치 정하기

**가중치는 "이 Work Package 가 프로젝트 전체에서 차지하는 무게"** 입니다. 사람일수, 난이도, 중요도 중
무엇으로 잡아도 되지만 **한 프로젝트 안에서는 한 기준으로** 잡으세요.

가장 다루기 쉬운 방법은 **예상 인일(man-day)을 10 으로 나눈 정수**입니다. 위 예제의 `3.1 예약 등록`이
50인일이면 5입니다.

- **비워 두면 "정하지 않음"이고 0이 아닙니다.** 형제 중 하나라도 가중치가 있으면, 없는 형제는 집계에서
  빠지고 부모에 `불완전` 표시가 붙습니다.
- **아무도 안 정하면** 예전처럼 하위 개수로 평균 냅니다(`하위 평균`). 이것도 정상적인 운영 방식입니다 —
  다만 "요구사항 명세서"와 "예약 등록"이 같은 무게가 됩니다.

### 10.1.4 구성원과 책임 (RACI)

WBS 다음에 **RACI 화면 아래에서 구성원부터 등록**합니다. 사람이 없으면 매트릭스에 열이 없습니다.

**단계(Summary)에 A 를 걸어 두는 것이 요령입니다.** 상속되므로 그 아래 Work Package 마다 다시 찍을
필요가 없고, 예외가 있는 곳에서만 재정의하면 됩니다.

```text
1 요구분석    A: PM,  R: PL          ← 여기만 찍으면
  1.1 현업 인터뷰                      ← 상속 (점선 흐린 글자)
  1.2 요구사항 명세서  R: 개발A        ← R 만 재정의, A 는 여전히 PM
```

배너에 `실무 담당자 없음`이 남아 있으면 그 업무는 **아무도 안 하고 있는 것**입니다. 착수 주에
0으로 만들어 두면 이후에 뜨는 경고는 전부 "새로 생긴 공백"이라 의미가 있습니다.

### 10.1.5 기준선(Baseline) 승인 — 언제 누르나

**WBS 와 가중치가 확정되고 착수 승인이 난 직후**입니다. 너무 이르면 곧 바뀌고, 너무 늦으면 비교할
기준이 없는 채로 몇 주가 흘러갑니다.

Dashboard → 진척 탭 → **기준선 승인**. 지금의 범위·일정·가중치·완료 기준이 통째로 복사됩니다.

**승인하기 전까지는 계획 진척이 "미산정"이고 간트에 "기준 일정 미등록"이 뜹니다.** 시간이 지났다는
이유만으로 계획 진척을 만들어 내지 않기 때문입니다.

## 10.2 매주 — 무엇을 보고 무엇을 고치나

### 월요일 아침 15분: Dashboard 요약

**위에서 아래로 읽으면서 이상한 것만 눌러 들어갑니다.**

| 보는 것 | 정상 | 이상하면 |
|---|---|---|
| **진척 / 편차** | 편차가 −5%p 이내 | −10%p 넘으면 §10.3 으로 |
| **일정 / 지연 건수** | 0~2건 | 지연 목록의 업무명을 눌러 WBS 로 |
| **기준 일정 / 초과** | 없음 | 초과 목록을 눌러 원인 업무로 |
| **실행 / 차단** | 0건 | 차단 카드의 RAID·담당자를 확인 |
| **위험·이슈 / 기한 초과** | 0건 | RAID 로 가서 기한을 다시 잡거나 종결 |
| **데이터 누락** | 0건 | **여기가 0이 아니면 위 숫자들이 그만큼 침묵하고 있는 것** |

**"데이터 누락"을 먼저 보는 습관을 들이세요.** 진척 40%가 "40% 했다"인지 "40%만 셀 수 있고 나머지는
모른다"인지가 여기서 갈립니다.

### 금요일 오후: 실적 반영

1. **Board** 에서 이번 주에 끝난 카드를 완료로 옮깁니다(확인 대화상자에서 완료 기준 확인).
2. **WBS** 에서 미지정·Waterfall Work Package 의 진행률을 갱신합니다.
   - Waterfall 은 진행률을 직접 적는 게 아니라 **진척 탭에서 체크포인트를 승인**합니다.
3. **RAID** 에서 이번 주에 생긴 위험·이슈를 적고, 해소된 것을 종결합니다.

## 10.3 지연이 보일 때 — 원인을 찾아 들어가는 순서

**증상에서 원인으로 내려가는 길이 화면 링크로 이어져 있습니다.** 순서대로 따라가세요.

```text
Dashboard 요약  "지연 3건, 최대 12일"
      │  지연 목록의 업무명 클릭
      ▼
WBS  해당 행이 펼쳐지고 강조됨
      │  ① 진척 칸의 근거 라벨을 본다 → 왜 이 숫자인가
      │  ② 연결 Backlog 칸을 클릭
      ▼
Backlog  그 Work Package 의 Story 목록
      │  완료가 안 된 Story 를 찾는다
      │  Sprint 칩이 붙어 있으면 클릭
      ▼
Board  그 카드의 상태와 차단 사유
      │  차단이면 관련 RAID 와 소유자가 카드에 함께 표시됨
      ▼
RAID  이슈의 대응 방안과 기한
      │
      ▼
RACI  그 업무의 A(최종 책임)에게 가져갈 것
```

### 예: "3.1 예약 등록이 12일 지연"

1. **WBS** — 진척 40%, 근거는 `Agile`. 즉 Story 5개 중 2개 완료.
2. **연결 Backlog 클릭** — 미완료 3개 중 하나가 `Sprint 4` 칩 + `차단` 표시.
3. **Board** — 카드에 `차단: 외부 SSO 연동 스펙 미확정`, 관련 RAID `SSO 스펙 지연 (소유자 PL)`.
4. **RAID** — 그 이슈의 기한이 이미 8일 초과. 대응 방안이 비어 있음.
5. **판단** — 일정 문제가 아니라 **외부 의존성 문제**입니다. 일정을 미루는 것으로는 안 풀리고,
   PL 이 상대 조직과 스펙을 확정하는 것이 유일한 경로입니다.

**여기서 하지 말아야 할 일**: 간트에서 일정 재계산을 눌러 뒤로 밀고 "해결됐다"고 보는 것. 재계산은
날짜를 옮길 뿐 원인을 없애지 않습니다.

### 지연 배지를 읽을 때의 주의

**지연 판정은 화면에 보이는 진척과 같은 값을 씁니다.** Agile Work Package 라면 Board 에서 Story 를
완료하는 것만으로 지연 판정이 함께 풀립니다 — 진행률을 따로 맞춰 줄 필요가 없습니다.

다만 **산정 전(분모가 없는) 항목**은 계산할 값이 없어 저장된 진행률로 판정합니다. 그 항목의 지연
배지가 이상해 보이면 먼저 Story 나 체크포인트가 등록돼 있는지 보세요.

## 10.4 월간 보고 만들기

**보고 직전에 숫자를 만들지 말고, 보고 시점의 숫자를 박제하세요.**

1. **Dashboard → 진척 탭 → 보고 스냅샷**에 `2026-05 월간보고` 라벨로 저장합니다.
   이후 범위가 바뀌어도 이 스냅샷은 변하지 않습니다.
2. **범위 비교**를 확인합니다. 기준선 이후 추가·제외·가중치 변경이 있으면 보고서에 **그 사실을 먼저**
   적으세요. 진척이 떨어진 이유가 "일을 못 해서"가 아니라 "분모가 커져서"일 수 있습니다.
3. **CSV 내보내기**로 표를 뜹니다(프로젝트 화면 → 행의 내보내기 드롭다운).
   - `WBS` — 진척·지연·실행 방식이 들어간 전체 표
   - `RAID` — 위험·이슈 등록부
   - CSV 는 판정값과 한글 라벨을 포함하고 기준일이 열 머리글에 박혀 있어 **며칠 뒤 열어도 무엇 기준인지
     알 수 있습니다.**

### 보고서에 쓸 문장의 형태

숫자만 옮기지 말고 **분모를 함께** 적으세요.

> ❌ "전체 진척 42%"
> ⭕ "전체 진척 42% (기준선 v1 범위 12개 Work Package 기준, 산정 전 2개 제외)"

> ❌ "지연 3건"
> ⭕ "지연 3건 — 최대 12일(3.1 예약 등록). 원인은 외부 SSO 스펙 미확정이며 RAID#7 로 추적 중,
> 소유자 PL, 대응 기한 5/22"

## 10.5 변경이 생겼을 때

### 범위가 추가될 때

현업이 "알림 기능도 넣어 달라"고 합니다.

1. **WBS** 에 `3.4 알림 발송` Work Package 를 추가하고 실행 방식·가중치를 지정합니다.
2. **Dashboard 요약**에 즉시 나타나는 것:
   - 진척이 **떨어집니다** (분모가 커졌으므로)
   - 기준 일정 카드에 `범위 변화 — 추가 1` 이 뜹니다
3. **기준선을 다시 승인할지 결정합니다.**

| | 기준선 유지 | 기준선 재승인 |
|---|---|---|
| 편차가 말하는 것 | "원래 계획 대비" | "변경된 계획 대비" |
| 이럴 때 | 변경이 작고, 원래 약속 대비 상태를 계속 보고 싶을 때 | 변경 승인을 정식으로 받았고, 이후는 새 계획으로 관리할 때 |

**둘 다 정당합니다.** 중요한 건 보고서에 어느 쪽인지 적는 것입니다. 재승인하면 v2 가 되고, 이전
스냅샷은 그대로 남아 과거 보고와 대조할 수 있습니다.

### 일정이 밀릴 때

1. **간트** 에서 해당 업무의 종료일을 늘립니다(WBS 편집).
2. 선후행 관계가 걸려 있으면 **일정 재계산**으로 뒤 업무들을 함께 밀어냅니다.
   - **뒤로만 밀립니다.** 여유가 생겨도 앞으로 당기지 않으니, 당기려면 직접 고쳐야 합니다.
3. 기준선이 있으면 **기준 종료일 초과** 경고가 뜹니다. 이 경고는 계획을 고쳤다고 사라지지 않습니다 —
   그게 기준선의 목적입니다.

## 10.6 이 도구가 답해 주지 않는 것

운영으로 메워야 하는 부분입니다. 모르고 쓰면 숫자를 잘못 읽게 됩니다.

### 지금 결함이라 우회가 필요한 것

| 문제 | 실무 우회 |
|---|---|
| **기존에 승인한 기준선의 Summary 행** | 예전에 승인한 기준선에는 Summary 날짜가 비어 있습니다. 단계 단위 기준 초과를 보려면 **기준선을 다시 승인**하세요(새로 승인하는 것부터 담깁니다) |

### 설계상 없는 것

| 없는 것 | 운영으로 메우는 법 |
|---|---|
| **영업일·휴일 달력** | 일정이 주말에도 흐릅니다. 기간을 잡을 때 휴일을 미리 감안해 넉넉히 |
| **선후행 FS 외의 관계** | SS/FF 가 필요하면 업무를 쪼개 FS 로 표현하세요 |
| **마일스톤** | 마일스톤에 해당하는 지점을 **기간 1일짜리 Work Package** 로 두면 간트에서 점처럼 보입니다 |
| **로그인·권한** | RACI 는 표시용입니다. 실제 접근 통제는 이 도구 밖에서 |
| **팀 여러 개** | 실행 중 Sprint 가 하나뿐입니다. 팀이 둘 이상이면 **프로젝트를 나누는 것**이 현재로선 유일한 방법 |
| **동시 편집 보호** | 마지막 저장이 이깁니다. 같은 프로젝트를 여럿이 동시에 편집하지 마세요 |
| **진척 변경 이력 화면** | 데이터는 쌓이지만 볼 화면이 없습니다. 이력이 필요하면 **스냅샷을 주기적으로** 남기세요 |

## 10.7 한 장 요약 — 시점별 체크리스트

| 시점 | 할 일 | 화면 |
|---|---|---|
| **착수** | WBS 구성 → 실행 방식·가중치 지정 → 구성원 등록 → RACI 단계에 A·R → **기준선 승인** | WBS → RACI → Dashboard/진척 |
| **Sprint 시작** | Backlog 작성·귀속 → Sprint 만들기 → 항목 배정 → 시작 | Backlog → Sprint |

| **매주 금** | 완료 반영 → Waterfall 체크포인트 승인 → 진행률 보정 → RAID 정리 | Board → Dashboard/진척 → WBS → RAID |

| **범위 변경 시** | WBS 추가 → 기준선 유지/재승인 결정 → 보고서에 명시 | WBS → Dashboard/진척 |
| **종료** | 전체 JSON 내보내기로 보관 | 프로젝트 |
