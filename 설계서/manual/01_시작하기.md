# 1. 시작하기

> 한 줄 요약: 앱을 띄우고, 메뉴 구조를 익히고, 모든 화면에 공통으로 적용되는 규칙 몇 가지를 알아 둡니다.

## 1.1 실행

### 설치본

실행하면 **창이 뜨지 않고** 서버가 백그라운드로 올라온 뒤 브라우저가 자동으로 열립니다. 창이 없는 것이
정상입니다. 브라우저가 안 열리면 직접 `http://localhost:8080` 으로 들어가세요.

포트를 바꾸려면 `~/.project-flow/application.properties` 에 한 줄이면 됩니다.

```properties
server.port=8090
```

브라우저도 바뀐 포트로 열립니다. 이 파일은 데이터와 같은 폴더에 있어 **재설치·업그레이드해도 남습니다.**

### 개발 중

```bash
cd backend  && ./gradlew bootRun    # http://localhost:8080
cd frontend && npm run dev          # http://localhost:5173
```

프론트엔드가 `/api` 요청을 8080으로 넘깁니다. 백엔드 포트를 바꿨다면 `VITE_API_TARGET` 으로 알려 주세요.

### 데이터는 어디에 있나

| 실행 방식 | 저장 위치 |
|---|---|
| 데스크톱 설치본 | `~/.project-flow/data` (로컬 H2 파일) |
| 서버 배포 | PostgreSQL |

**설치본은 각자의 PC에 데이터를 둡니다.** 공유 서버가 없으므로 다른 사람에게 프로젝트를 넘기는 방법은
파일뿐입니다([9장](09_Export_Import.md) 참고).

## 1.2 메뉴 구조

```text
프로젝트 | WBS | Agile | 간트 차트 | RACI | RAID | Dashboard
                 ├─ Backlog                              ├─ 요약
                 ├─ Sprint                               └─ 진척
                 └─ Board
```

- **Agile** 은 자기 화면이 없는 묶음입니다. 누르면 Backlog 로 가고, 그 아래에
  `Backlog · Sprint · Board` 줄이 나타납니다. 이 줄은 Agile 화면 세 개 안에 있을 때만 보입니다.
- **진척** 은 Dashboard 안의 탭입니다. 요약이 숫자를 *보여 주고*, 진척이 그 숫자의 근거를 *입력하는*
  곳이라 한 화면의 두 면으로 두었습니다.
- 오른쪽 위 **시스템 설정** 버튼은 화면 테마를 바꿉니다(시스템 설정 → 라이트 → 다크 순환).

각 화면이 하는 일은 이렇습니다.

| 메뉴 | 무엇을 하는 곳인가 |
|---|---|
| **프로젝트** | 프로젝트를 만들고 고릅니다. 모든 작업의 출발점 |
| **WBS** | **범위**를 계층으로 정의합니다. 다른 모든 화면이 여기를 기준으로 삼습니다 |
| **Agile / Backlog** | 실행할 일(Epic·Story·Bug·Task)을 적고 Work Package 에 귀속시킵니다 |
| **Agile / Sprint** | 실행 주기를 계획하고, 항목을 담고, 시작·종료합니다 |
| **Agile / Board** | 카드를 옮기며 실제로 실행합니다 |
| **간트 차트** | 기준·계획·실적 세 일정과 선후행 관계를 봅니다 |
| **RACI** | 업무별 책임(실무·최종책임·자문·통보)을 정합니다 |
| **RAID** | 위험·가정·이슈·의존성을 기록하고 추적합니다 |
| **Dashboard / 요약** | 위 화면들의 숫자를 한 화면에 모읍니다 |
| **Dashboard / 진척** | 그 숫자의 근거(가중치·체크포인트·기준선)를 입력합니다 |

## 1.3 모든 화면에 공통인 것

### 프로젝트 선택은 하나입니다

화면마다 왼쪽 위에 프로젝트 셀렉트가 있고, **모든 화면이 같은 선택을 공유합니다.** 한 번 고르면
메뉴를 옮겨도 유지되고, 바꾸면 모든 화면이 그 프로젝트로 따라옵니다.

### 기준일은 서버가 정합니다

지연·기한 초과 같은 판정의 "오늘"입니다. 화면 상단에 `기준일 2026-09-09` 처럼 적혀 있습니다.

**브라우저 시계를 쓰지 않는 이유**는, 한 응답 안의 행들이 서로 다른 "오늘"로 판정되거나 오래 열어 둔
탭에서 차트의 오늘 선과 배지가 어긋나는 것을 막기 위해서입니다. 탭을 밤새 열어 둬도 다음 날 자동으로
갱신됩니다.

### 추가·수정은 전부 대화상자입니다

- 폼이 화면에 붙박이로 있지 않고 **대화상자로 뜹니다.** 표를 아래로 밀어내지 않기 위해서입니다.
- **저장이 거부되면 대화상자가 닫히지 않습니다.** 그 안에 이유가 표시되고 입력값은 그대로 남습니다.
  다시 입력할 필요가 없습니다.
- 닫기는 `×` 버튼, `취소` 버튼, `Esc` 키 모두 됩니다.

### 표는 가로로 스크롤합니다

셀 내용을 줄바꿈하지 않습니다. 행 높이가 들쭉날쭉해지면 훑어 읽기 어렵기 때문입니다. 화면보다 넓으면
표 안에서 좌우로 스크롤하세요. 설명·비고처럼 긴 칸은 잘라서 보여주고, 마우스를 올리면 전체가 뜹니다.

### 저장은 즉시 반영됩니다

"전체 저장" 버튼은 없습니다. 대화상자에서 저장하거나 카드를 옮기면 그 순간 서버에 반영됩니다.

### 화면끼리 숫자가 다르면 안 됩니다

진척은 **한 곳에서만 계산**해 WBS·간트·Dashboard 가 같은 값을 읽습니다. 세 화면의 진척이 다르게
보인다면 그건 캐시이거나 결함입니다 — 화면을 다시 들어가 보고, 그래도 다르면 알려 주세요.

## 1.4 처음 시작하는 순서

```text
프로젝트 만들기
      │
      ▼
WBS 구성 ──────────────► 단계는 Summary, 최하위 작업은 Work Package
      │                   Work Package 마다 실행 방식과 가중치
      ▼
구성원 등록 ───────────► RACI 화면 아래에서. 책임을 정하려면 사람이 먼저 있어야 합니다
      │
      ▼
Backlog 작성 ──────────► Story·Bug 를 Work Package 에 귀속
      │
      ▼
기준선 승인 ───────────► Dashboard → 진척 탭. 해야 계획 대비 편차가 나옵니다
      │
      ▼
Sprint 계획·시작 ──────► 항목 배정 → 시작 (동시에 하나만)
      │
      ▼
Board 에서 실행 ───────► 할 일 → 진행 중 → 검토 → 완료
      │
      ▼
진척 자동 집계 ────────► WBS·간트·Dashboard 가 같은 숫자를 봅니다
```

**Waterfall 로 관리할 Work Package** 는 Backlog 대신 **승인 체크포인트**를 등록합니다
([8.2.2](08_Dashboard.md)). 체크포인트가 하나도 없으면 그 Work Package 의 진척은 계속
"산정 전"입니다.

## 1.5 이 도구의 세 가지 원칙

매뉴얼 전체에서 반복되는 태도입니다. 이것만 알아도 화면이 왜 그렇게 동작하는지 대부분 설명됩니다.

**1. 산정 전은 0%가 아닙니다.**
분모가 없으면(Story 가 없는 Agile Work Package, 체크포인트가 없는 Waterfall) 숫자를 만들어 내지 않고
"산정 전"이라고 적습니다. 착수 전 프로젝트가 "0% 진행"으로 보이면 정말 0%인 것과 구별할 수 없기
때문입니다.

**2. 만족할 수 없는 구조는 거부하고, 계획이 안 맞는 것은 표시합니다.**
순환 선후행처럼 유효한 답이 아예 없는 것은 등록 자체를 막습니다. 반면 최종 책임자가 둘이거나 일정이
선행보다 앞서는 것은 **저장은 되고 경고만** 뜹니다 — 인수인계 중에 반드시 지나가는 상태이고, 막으면
"지우고 다시 넣기"를 강요하게 됩니다.

**3. 파생 값은 저장하지 않습니다.**
WBS 코드, Summary 의 일정·진척, 지연 판정, 노출도는 모두 **볼 때 계산**합니다. 저장해 두면 항목을
옮기거나 날짜가 바뀌는 순간 낡은 값이 되기 때문입니다. 그래서 화면을 새로 열면 항상 지금 기준의
숫자가 나옵니다.
