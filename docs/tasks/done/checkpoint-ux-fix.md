# 체크포인트·진척 탭 UX 세 건 정리

대상 체크아웃: `D:\git\ScheduleMgr` (main `2e98203` "WBS 폼에서 가중치 입력을 레벨 무관 없앤다")
모든 줄번호는 그 커밋에서 확인한 값이다.

사용자가 보고한 세 가지다.

1. 진척(Dashboard) 탭에서 아직 가중치를 조정할 수 있다 — 없애 달라
2. 승인이 버튼인지 태그인지 구분이 안 된다
3. 체크포인트를 수정 후 저장하거나 추가할 때마다 창이 닫혀서 불편하다

세 건은 서로 독립이다. 순서대로 해도 되고 나눠 맡아도 되지만, **3번이 가장 값이 크고 가장
작다**(한 파일 한 줄) — 먼저 고치면 2번을 손으로 확인하기도 쉬워진다.

## 1. 진척 탭의 가중치·α 편집 제거 (열은 읽기 전용으로 남긴다)

### 1-1. 해결할 문제

`ProgressPanel.vue`에 Work Package 행별 인라인 편집기가 살아 있다.

| 계층 | 지금 상태 |
|---|---|
| 화면 (진척 탭) | 행 액션에 「가중치」 버튼 → 가중치·α 입력칸으로 바뀌고 [저장]/[취소]가 뜬다 |
| 화면 (WBS 폼) | α는 입력할 수 있고(`WbsForm.vue:185`), **가중치 입력은 `2e98203`에서 없앴다** |
| 컴포저블 | `useProgress.updateBasis`(`useProgress.ts:125-130`) |
| API 클라이언트 | `progressApi.updateBasis`(`progressApi.ts:129-130`), `WorkPackageBasisInput`(`:107`) |
| 백엔드 | `PUT /api/projects/{id}/progress/work-packages/{wbsItemId}/basis` — 정상 동작, 테스트 있음 |
| 문서 | **이미 "고칠 수 없다"고 선언해 뒀다** (아래) |

`설계서/agile_design/results/Hybrid_PM_Operation_Guide.md`에는 커밋되지 않은 수정이 들어 있고,
그 수정이 §2.4에서 이렇게 말한다.

> **이 탭에서는 아무 숫자도 고치지 않습니다.** … Work Package의 가중치·α는 같은 화면의 항목 수정
> 폼에서 고칩니다. 여기서는 그 결과를 **읽기 전용**으로만 보여줍니다 — 진척 탭은 조망 화면이지
> 실행 화면이 아니기 때문입니다.

즉 **문서가 앞서 있고 코드가 따라오지 않은 상태**다. 이 작업은 코드를 문서에 맞추는 것이다.

### 1-2. 결정된 방향

**편집만 없애고 가중치·α 열은 읽기 전용으로 남긴다**(사용자 결정). 옆의 `기준` 열이 그 행의
집계가 `가중치 집계`인지 `하위 평균(LEGACY_ROLLUP)`인지를 말하는데, 가중치 숫자가 보이지 않으면
왜 그 숫자가 나왔는지 설명할 자리가 없어진다. 기존 프로젝트에 남아 있는 값도 확인할 수 있어야
한다.

**문서의 한 문장은 틀렸으니 함께 바로잡는다.** 운영 안내는 "가중치와 α도 WBS 화면의 항목 수정
폼에서 고칩니다"라고 적었지만, α만 맞다. `2e98203`이 WBS 폼의 가중치 입력을 없앴고, 지금 그
자리에는 "이 항목에 저장된 가중치(N)는 지우지 않고 그대로 보관하며 집계에도 계속 쓰입니다.
가중치는 이 폼에서 다루지 않으므로 저장해도 값은 바뀌지 않습니다"라는 안내만 있다
(`WbsForm.vue:259-261`).

**그래서 이 편집기를 지우면 가중치는 어느 화면에서도 입력할 수 없게 된다.** 이것이 의도한
결과다 — `CLAUDE.md`의 "그래서 WBS 폼은 레벨 무관 가중치를 묻지 않습니다(사용자 결정)"와 같은
사유(형제 사이의 상대값인데 원가·공수와 묶이지 않아 적을 근거가 없고, 크기 차이는 이미
`leafCount`가 반영한다)가 이 화면에도 그대로 성립한다. 기존 값은 보관되고 집계에도 계속 쓰인다.

**α는 WBS 폼에 남는다** — Hybrid의 분자·분모 비율은 Work Package의 성격이라 적을 근거가 있고,
지우면 Hybrid를 화면에서 설정할 방법이 사라진다.

**백엔드는 건드리지 않는다.** 엔드포인트와 테스트는 계약으로 남긴다. `CLAUDE.md`가 이 엔드포인트를
"일반 WBS 수정 API와 합치지 마세요"라고 못 박은 이유(진척 탭 표의 `WorkPackageProgress`에는
`startDate`·`endDate`·`progress`·`description`이 없어 `PUT /wbs/{itemId}`를 부르면 그 필드들이
null로 덮인다)는 여전히 유효하고, 좁은 경로가 있다는 사실 자체가 나중에 화면을 되살릴 때의
안전장치다. **프론트의 호출 경로만 지운다** — 부르는 곳이 없는 함수를 남기면 다음 사람이 "여기서
고칠 수 있나?"를 다시 묻게 된다.

## 2. 승인 — 상태는 칩, 동작은 버튼

### 2-1. 해결할 문제

`CheckpointList.vue`에서 **상태 표시와 동작 버튼이 서로의 옷을 입고 있다.**

| 무엇 | 줄 | 지금 모양 | 어떻게 읽히나 |
|---|---|---|---|
| 승인 상태 `.cp-approved` | `:206-208`, `:347-350` | 배경 없는 **`--accent` 색 글자** | 링크·버튼처럼 보인다 |
| 미승인 상태 `.cp-pending` | `:209`, `:352-355` | 배경 없는 `--text-faint` 글자 | 아무것도 아닌 것처럼 보인다 |
| 동작 버튼 `.cp-actions button` | `:365-375` | `--surface` 배경 + 옅은 테두리 + `--text-muted` 글자 | 라벨/태그처럼 보인다 |

더해서 **`.cp-actions button:hover` 규칙이 아예 없다** — "누를 수 있다"는 가장 강한 신호가 빠져
있다. 그리고 같은 열의 「승인 3/5」 배지(`WbsTree.vue:1021-1030` `.cp-badge`)는 pill 모양 *버튼*
이라, 펼친 목록에서 pill이 상태를 뜻하게 되면 모양 규칙이 한 화면 안에서 엇갈린다.

### 2-2. 결정된 방향

**상태는 채운 칩(테두리·hover 없음, `cursor: default`), 동작은 테두리+hover가 있는 버튼.** 주
동작인 「승인」만 옅은 강조 채움(filled tonal)을 깔아 한눈에 눌러야 할 것이 보이게 한다.
라벨도 「승인 완료」(상태) / 「승인」(버튼)으로 갈라 한 단어가 두 뜻으로 쓰이는 것을 없앤다.

```
설계 리뷰  가중치 3  리뷰어 확인  [✓ 승인 완료 · 김OO · 03-02]   ( 승인 취소 )( 수정 )( 삭제 )
                                  ▲ 연한 초록 칩, 누를 수 없음    ▲ 테두리 + hover

개발 완료  가중치 2               [ 미승인 ]        [[ 승인 ]]( 수정 )( 삭제 )
                                  ▲ 회색 칩          ▲ 연한 보라 채움(주 동작)
```

**새 색 토큰을 만들지 않는다.** 필요한 것이 모두 있고 다크 모드도 정의돼 있다 —
`--success-weak`/`--success-text`, `--badge-neutral-bg`/`--badge-neutral-fg`,
`--accent-container`/`--accent-container-fg`, `--state-hover`. `CLAUDE.md`의 "색은 전부
`style.css`의 CSS 변수로만 정의합니다"를 지킨다.

### 2-3. 작업

**`frontend/src/features/progress/CheckpointList.vue`** 한 파일이다. 템플릿과 스코프 스타일만
바뀌고 스크립트는 건드리지 않는다.

템플릿(`:206-209`):

- `.cp-approved`의 텍스트를 「승인 완료 · {approvedBy} · {날짜}」로 바꾼다 (지금은 「승인 · …」)
- `.cp-pending`의 텍스트는 **'미승인' 그대로 둔다**
- 두 `<span>` 모두 그대로 `<span>`이다 — 클릭 핸들러를 붙이지 않는다

스타일:

- `.cp-approved` → `background: var(--success-weak)`, `color: var(--success-text)`,
  `border-radius: 999px`, `padding: 0.05rem 0.4rem`, `cursor: default`, 테두리 없음.
  크기·모서리는 이 저장소의 기존 칩(`BacklogList.vue:266-274`, `ProgressPanel.vue:726-731`)과 같은
  계열로 맞춘다 — 칩 모양을 화면마다 새로 짓지 않는다
- `.cp-pending` → 같은 모양에 `background: var(--badge-neutral-bg)`, `color: var(--badge-neutral-fg)`
- `.cp-actions button`에 `:hover` 추가 — 상태 레이어 방식(겹치는 반투명 층)을 쓰거나
  `background: var(--state-hover)`를 얹는다. `CLAUDE.md`의 "상태 레이어는 배경색 교체가 아니라
  겹치는 반투명 층"을 따른다
- 「승인」 버튼에만 클래스를 하나 주고(`class="primary"` 등) `background: var(--accent-container)`,
  `color: var(--accent-container-fg)`, `border-color: transparent`. 「승인 취소」·「수정」·「삭제」는
  지금의 테두리 모양을 유지한다
- `WbsTree.vue`의 `.cp-badge`(`:1021-1030`)에 `:hover`를 더해 "이건 버튼"임을 분명히 한다. 모양·색은
  바꾸지 않는다 — `:1016-1019`의 주석이 왜 이 모양인지 설명하고 있으니 그 결정은 그대로 둔다

**깨지면 안 되는 것 — 기존 테스트가 고정하고 있다** (`CheckpointList.spec.ts`):

- `.cp-pending` 의 텍스트는 정확히 `'미승인'`이어야 한다 (`:138-142`)
- 버튼 라벨 목록에 `'승인'`과 `'승인 취소'`가 **정확히 그 문자열로** 있어야 한다 (`:213-222`)
- `.cp-approved`의 텍스트는 승인자와 날짜를 `toContain`으로만 검사하므로 「승인 완료」 접두는 안전하다
  (`:144-153`)
- `editable: false`에서는 `button`이 **0개**여야 한다 (`:115-122`) — 칩을 `<button>`으로 만들지 마라

**새 테스트 하나** — `editable: true`에서 `.cp-approved`·`.cp-pending`이 `<button>`이 아님을
고정한다. "상태는 표시이고 동작이 아니다"가 이 작업의 요지이고, 다음에 누가 칩에 클릭을 달면
`editable: false`의 버튼 0개 테스트에서야 드러나 원인이 멀어진다.

색·모양은 테스트로 잡을 수 없으니 **수동 확인이 곧 검증이다**(아래 4장).

## 3. 저장·추가할 때마다 창이 닫힌다 — 원인은 `CheckpointList`가 아니다

### 3-1. 해결할 문제

`CheckpointList`는 이미 옳다. "추가 후에는 폼을 열어 두고 제목 칸으로 포커스를 되돌린다"가
컴포넌트 테스트로 고정돼 있다(`CheckpointList.spec.ts:250-278`). **테스트는 통과하는데 화면에서는
닫힌다.** 한 계층 위에서 컴포넌트가 통째로 파괴되기 때문이다.

| 단계 | 어디 |
|---|---|
| 1. 체크포인트 추가·수정·승인·삭제 → `markWbsChanged()` + `data.value` 교체 | `useProgress.ts:74-87` |
| 2. WbsView의 `watch(progressData, …)` → `ensureLoaded(id)` | `WbsView.vue:101-104` |
| 3. WBS 리비전이 올라갔으니 캐시 키가 달라져 실제 재요청 → `loading.value = true` | `useWbs.ts:41` |
| 4. `<p v-if="loading">` / `<WbsTree v-else>` → **WbsTree 언마운트** | `WbsView.vue:273-275` |
| 5. `checkpointsOpen`(`WbsTree.vue:104`)과 그 안 `CheckpointList`의 `formOpen`·`draft`·`editingId`·포커스가 전부 소멸 | — |
| 6. 응답이 오면 다시 마운트 — 모든 행이 접힌 상태 | — |

2번 `watch`는 필요해서 있는 것이다(주석이 왜인지 적어 뒀다): 체크포인트를 승인하면 트리 행의
진척(%)과 「승인 N/M」 배지가 낡는데, `markWbsChanged()`만으로는 *열려 있는* 이 화면이 다시 읽지
않는다. **이 watch를 지워서 고치지 마라** — 숫자가 낡는 문제가 돌아온다.

### 3-2. 결정된 방향

**이미 행이 있으면 갱신 중에도 트리를 감추지 않는다.** `WbsView.vue:273-275` 한 곳만 바꾼다.

```
before:  <p v-if="loading">불러오는 중...</p>
         <WbsTree v-else … />

after:   <p v-if="loading && tree.length === 0">불러오는 중...</p>
         <WbsTree v-else … />
```

- 행 key가 `row.node.id`로 안정적이고(`WbsTree.vue:461`) 트리 변경 시 `checkpointsOpen`을 건드리는
  코드가 없으므로, 트리를 살려 두기만 하면 펼침 상태·폼·포커스가 그대로 남는다
- **첫 로드에는 여전히 "불러오는 중"이 나와야 한다.** 조건에서 `tree.length === 0`을 빼면 빈 트리
  상태에서 `WbsTree`의 빈 화면 문구("등록된 WBS 항목이 없습니다. 위 ＋ 최상위 항목 추가로…",
  `WbsTree.vue:436-438`)가 먼저 번쩍인다 — 항목이 없다는 말과 아직 안 왔다는 말은 다르다
- 체크포인트 목록 자체는 `progressData`에서 **즉시** 갱신된다(`mutate`가 응답을 바로 `data.value`에
  넣는다). 트리 행의 진척·배지만 재요청 한 번 뒤에 따라온다 — 사람이 보는 순서로는 자연스럽다
- 갱신 중임을 알리는 별도 표시는 두지 않는다(사용자 결정). 레이아웃이 흔들리고, 정작 방금 바꾼
  체크포인트 목록은 이미 최신이다

**판정을 순수 함수로 뺀다.** `frontend/src/features/wbs/treeVisibility.ts`에 이런 모양의 함수와
spec을 둔다.

```ts
/** 첫 로드에만 트리를 감춘다 — 갱신 중에 감추면 펼친 체크포인트와 그 폼이 함께 사라진다. */
export function showsLoadingInsteadOfTree(loading: boolean, rowCount: number): boolean
```

이 저장소의 관습이다(`rowSelection.ts`·`assignFilter.ts`·`checkpointForm.ts`가 모두 그렇게
생겼다). 조건이 한 줄이라 사족처럼 보이지만, **이 한 줄을 되돌리면 3번 버그가 그대로 돌아오고
컴포넌트 테스트로는 드러나지 않는다** — `WbsView`는 라우터와 컴포저블 네 개를 mock해야 마운트되는
화면이라 뷰 레벨 테스트가 없다(그래서 애초에 이 버그가 테스트를 통과한 채 남아 있었다). 함수
이름과 spec의 문장이 이유를 붙들어 둔다.

`CLAUDE.md`의 "컴포넌트 테스트는 '렌더링·상호작용'을 덮고, 순수 함수 테스트는 '판정'을 덮습니다"에
맞는 쓰임이다.

### 3-3. 덤과 범위

같이 좋아지는 것: 항목 추가·수정·이동·삭제, 파일 가져오기, 일정 재계산 뒤에도 화면이 "불러오는
중"으로 깜빡이지 않는다. 스크롤 위치와 선택된 행도 유지된다.

## 4. 확인 방법

```bash
cd frontend
npm test            # 기존 테스트 전체 + 새 treeVisibility.spec.ts + CheckpointList 새 테스트
npm run build       # vue-tsc — updateBasis 제거로 남은 참조가 있으면 여기서 잡힌다
```

백엔드는 바뀌지 않으므로 `./gradlew test`는 필요 없다. 다만 진척 탭에서 편집을 없앤 것이 서버
동작을 바꾸지 않았다는 확인으로 한 번 돌려도 무해하다.

수동 확인 — `npm run dev` + 백엔드 `bootRun`, Waterfall 또는 Hybrid Work Package가 있는 프로젝트로:

1. **WBS 화면**에서 Work Package 행의 「승인 N/M」 배지를 눌러 펼친다
2. 체크포인트를 **연달아 3건 추가** → 매번 폼이 열린 채 남고, 커서가 제목 칸으로 돌아오고,
   **행이 접히지 않는다**. 위 목록에 새 행이 하나씩 쌓인다
3. 한 건을 **수정 후 저장** → 폼만 닫히고 **행은 그대로 펼쳐져 있다**(예전에는 여기서 접혔다)
4. **승인** → 승인자 입력이 접히고 상태 칩이 「승인 완료 · 이름 · 날짜」로 바뀌며, 행은 펼쳐진 채다.
   그 자리에서 다음 체크포인트를 바로 승인할 수 있고 승인자 이름이 미리 채워진다
5. **삭제** → 행이 펼쳐진 채 목록에서만 사라진다
6. 위 2~5 동안 트리 행의 진척(%)과 「승인 N/M」 배지가 한 박자 뒤에 따라 갱신된다
7. 화면을 새로 고쳐 **첫 로드**를 본다 → "불러오는 중"이 나오고, "등록된 WBS 항목이 없습니다"가
   번쩍이지 않는다
8. 승인 칩과 버튼을 **라이트·다크 양쪽에서** 본다 — 칩은 커서가 화살표이고 hover에 반응하지 않고,
   버튼은 커서가 손가락이고 hover에 반응한다. 「승인」이 나머지 버튼보다 눈에 먼저 들어온다
9. **진척 탭**(`/dashboard?tab=progress`) → 가중치·α 열에 숫자가 보이고 **「가중치」 버튼이 없다**.
   행을 더블클릭하면 체크포인트가 펼쳐지고(읽기 전용 목록), 「WBS에서 편집」 링크가 그 행으로 간다
10. 진척 탭의 **기준선 승인**과 **보고 스냅샷 저장**은 그대로 동작한다(이번 삭제 범위 밖이다)
11. **커밋 조회 모드**로 들어가 두 화면을 본다 — 진척 탭에 쓰기 버튼이 없고(기준선 승인·스냅샷이
    잠긴다), WBS 트리의 체크포인트는 `editable: false`로 버튼 없이 보인다

| 백엔드 전체 (`PUT .../basis` 포함) | 계약이고 테스트가 붙어 있다. 프론트가 부르지 않을 뿐이다 |

| 체크포인트의 가중치 입력 | Waterfall·Hybrid 진척의 분모다. 이번 범위 밖(사용자 결정) |

| `WbsTree.vue`의 `.cp-badge` 모양·색 | `:1016-1019`의 주석이 왜 pill인지 설명한다. `:hover`만 더한다 |
| `stores/scheduleCache.ts` 리비전 구조 | 무효화는 지금이 맞다. 문제는 무효화가 아니라 그때 화면을 감췄던 것이다 |

## 6. 이번에 하지 않는 것 (후속 후보)

- **`ProgressPanel` 컴포넌트 테스트 신설.** 이 파일에는 선례가 없고 `useProgress`와 `RouterLink`를
  mock해야 한다. 이번 변경은 삭제가 대부분이라 `vue-tsc`와 수동 확인으로 충분하다
- **`WbsView` 뷰 레벨 테스트.** 3번 버그를 실제로 잡을 수 있는 유일한 테스트지만 라우터 + 컴포저블
  네 개를 mock해야 한다. 대신 판정을 순수 함수로 빼서 규칙만 고정한다
- **`checkpointsOpen`을 모듈 스코프로 올리기.** `lastApprover`처럼 하면 화면을 옮겼다 돌아와도
  펼침이 유지되지만, 이번 불만은 "저장할 때마다 닫힌다"이고 화면을 떠나는 것은 사람의 의도적
  행위다. 범위를 좁게 둔다
- **다른 화면의 갱신 중 깜빡임.** 위 표의 이유로 이번에는 손대지 않는다. 같은 증상이 보고되면
  같은 방식으로 고친다
- **가중치를 다시 입력할 자리.** 원가·공수와 묶여 적을 근거가 생기면 그때 설계한다. 그전까지
  `wbs_items.weight`는 보관·집계에만 쓰이는 값이다
