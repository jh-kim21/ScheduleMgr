# WBS 트리 — 열별 값 필터

대상 체크아웃: `D:\git\ScheduleMgr` (main `091d4a6` "체크포인트·진척 탭의 UX 세 곳을 고친다")

> **선행 작업이 둘 있다.** `wbs-tree-toolbar` → `wbs-tree-columns` 순으로 끝내고 커밋한 뒤
> 시작한다. 필터는 열 모델(`wbsColumns.ts`)에 필터 종류를 더하고, 필터 행은 보이는 열만 그린다.
> 아래 `WbsTree.vue` 줄번호는 `091d4a6` 기준이라 **선행 작업 뒤에는 달라진다** — 선택자·심볼
> 이름으로 찾을 것. `wbsTree.ts`·`raidFilter.ts` 쪽 줄번호는 두 작업이 건드리지 않으므로 그대로
> 유효하다.

---

## 1. 해결할 문제

WBS 트리에서 "Waterfall인 Work Package만", "김OO이 담당인 업무만", "Web 분야만" 훑을 방법이 없다.
완료된 지시서가 이것을 후속으로 남겨 뒀다 — `done/wbs-tree-improvements.md` 6-5: *"Tag로 필터·집계.
열에 표시만 하고 끝낸다."*

지금은 화면 전체 검색도, 열별 필터도 없다. 행이 수십 개인 프로젝트에서 눈으로 훑는 것이 유일한
방법이다.

**RAID 로그가 같은 문제를 이미 풀어 뒀다** — `features/raid/raidFilter.ts`가 순수 함수로 판정하고
클라이언트에서 필터한다. CLAUDE.md가 그 이유를 적어 뒀다: *"이건 데이터가 아니라 '지금 이 화면'에
대한 질문이라 서버로 보내면 드롭다운마다 왕복이 생기고 조합마다 캐시 키가 필요해진다."* 같은
판단이 여기에도 그대로 적용된다.

다만 **RAID는 평면 목록이고 WBS는 트리다.** 그 차이가 이 작업의 어려운 부분 전부다.

## 2. 결정된 방향

### 2-1. 일치 행 + 조상을 문맥으로 남긴다. 하위는 포함하지 않는다

일치 행만 남기면 `1.2.1`이 어느 가지에 속한 일인지 알 수 없다 — WBS로 읽히지 않는다. 그래서
일치 행의 **조상을 문맥으로** 남기고 흐리게 표시한다(문맥 행임을 표시하지 않으면 그 조상도
조건에 맞는 것처럼 읽힌다).

**일치 행의 하위는 끌고 오지 않는다.** 필터의 질문은 "이 조건에 맞는 업무가 어디 있나"이고,
하위까지 포함하면 조건에 맞지 않는 행이 결과에 섞인다. 실행 방식으로 필터할 때 특히 나쁘다 —
Summary는 전환 전 실행 방식을 **보관**하므로(CLAUDE.md 실행 방식 규칙) 보관값으로 일치한 Summary가
가지 전체를 끌고 온다.

### 2-2. 필터가 걸린 동안 드래그 이동을 잠근다 — 이게 가장 중요하다

`wbsTree.ts:3-8`의 `WbsRow`는 `node`와 함께 **`siblings`·`index`**를 들고 있고, 그 `index`가 곧
서버로 보내는 드롭 위치의 근거다(`resolveDropPosition`, `:38-50`). 트리를 잘라 낸 뒤 그대로
`flattenTree`를 돌리면 `index`가 **필터된 형제 목록 기준**이 되어, 사용자가 본 자리와 다른 곳으로
항목이 이동한다. 서버는 이 요청을 거부할 수 없다 — 유효한 위치이기 때문이다. **조용히 잘못된
결과가 저장된다.**

원래 `index`를 유지하도록 만들 수도 있지만(필터는 렌더에서만 걸고 `siblings`는 원본 배열을
유지), 그러면 사용자가 화면에서 붙어 보이는 두 행 사이에 놓았는데 실제로는 그 사이에 숨은 형제가
여럿 있는 상태가 된다. 결과가 정의는 되지만 놀랍다.

**필터가 하나라도 걸려 있으면 드래그를 끄고, 왜 껐는지 알린다.** 필터를 풀면 돌아온다.

### 2-3. 필터가 걸린 동안은 접힘(`collapsed`)을 무시한다

조상이 접혀 있으면 일치 행이 화면에 없다. 필터 중에는 접힘을 무시하고 전부 펼쳐 그린다 —
**`collapsed`를 비우지 말 것.** `flattenTree`에 빈 `Set`을 넘기기만 하면 되고, 그러면 필터를 풀
때 사용자가 접어 둔 상태가 그대로 돌아온다.

### 2-4. 선택지는 현재 트리의 값에서 뽑는다

담당자·분야 필터의 후보를 마스터 목록(`useWbsTags`, 구성원 API)에서 가져오지 않는다. 지금 트리에
실려 온 값에서 뽑으면 **새 prop도 새 요청도 없고**, 아무 행도 쓰지 않는 분야가 목록에 뜨지도
않는다(필터로서는 그게 맞다).

### 2-5. 필터는 저장하지 않는다

열 구성은 `localStorage`에 남기지만(`wbs-tree-columns` 지시서 2-5) **필터는 남기지 않는다.** 이건
설정이 아니라 지금 이 화면에 대한 질문이다(RAID 필터와 같은 이유). 남아 있으면 다음에 화면을 연
사용자가 행이 사라진 이유를 모른다.

### 2-6. 팝업 없이 머리글 아래 필터 행 하나

각 열 머리글 아래에 그 열 타입에 맞는 컨트롤을 한 줄로 둔다. 표를 보면서 조건을 바꾸는 것이
필터의 사용법이라 대화상자가 맞지 않고, 열마다 팝오버를 띄우는 것은 비용만 크다(`ExportMenu.vue`가
461줄인 이유 — `wbs-tree-columns` 지시서 2-4).

필터 행은 **토글로 켜고 끈다**(툴바의 [필터] 버튼). 기본은 꺼짐 — 이 화면의 주된 행위는 트리를
읽는 것이다(RAID 입력 패널이 기본으로 접혀 있는 것과 같은 규칙).

## 3. 작업

### 3-1. `wbsColumns.ts`에 필터 종류를 더한다 (선행 작업의 파일)

```ts
export type WbsFilterKind = 'none' | 'text' | 'enum' | 'names' | 'tags'
// WbsColumn 에 filter: WbsFilterKind 추가
```

| 열 | 종류 | 무엇으로 |
|---|---|---|
| WBS | `text` | `code` 앞자리 일치 (`1.2`를 넣으면 `1.2`, `1.2.1`이 남는다) |
| 업무명 | `text` | `name` 부분 일치(대소문자 무시) + `description`도 본다 |
| 시작일·종료일 | `none` | 기간 필터는 이번에 하지 않는다(6장) |
| 실행 방식 | `enum` | `executionMode` (`WATERFALL`/`AGILE`/`HYBRID`/미지정). **Summary의 보관값은 일치로 보지 않는다** — `nodeType === 'WORK_PACKAGE'`인 행만 본다(2-1의 이유) |
| 연결 Backlog | `enum` | `있음` / `없음` |
| 진척 | `enum` | `산정 전` / `0%` / `1~99%` / `100%` / `불완전` / `인수 대기`. 숫자 범위 입력을 두지 않는 이유는 6장 |
| 체크포인트 | `enum` | `없음` / `일부 승인` / `전부 승인` |
| 담당자 | `names` | `responsible`의 이름(상속 포함). `미지정`도 하나의 선택지다 |
| 분야 | `tags` | 태그 id. Summary의 하위 요약(`rolledUp`)은 일치로 보지 않는다 — 자기 분야가 아니다 |

### 3-2. `frontend/src/features/wbs/wbsTreeFilter.ts` (새 파일)

판정을 전부 여기 둔다. 순수 함수이므로 `vitest`로 고정한다(`raidFilter.ts`와 같은 자리·같은 이유).

```ts
export interface WbsFilterState {
  code: string
  name: string
  mode: string[]        // 빈 배열 = 조건 없음
  backlog: string | null
  progress: string[]
  checkpoint: string[]
  owners: string[]      // 이름. '미지정' 포함
  tagIds: number[]
}

export const EMPTY_FILTER: WbsFilterState
export function hasActiveFilter(state: WbsFilterState): boolean

export interface FilteredTree {
  /** 일치 행 + 그 조상만 남은 트리. 구조는 원본과 같다(children 배열이 잘려 있을 뿐). */
  nodes: WbsNode[]
  /** 조건에 실제로 맞은 행. 나머지는 문맥이다. */
  matchIds: Set<number>
}

/** 조건이 하나도 없으면 원본을 그대로 돌려준다(새 배열을 만들지 않는다). */
export function filterTree(nodes: WbsNode[], state: WbsFilterState): FilteredTree

/** 필터 행의 선택지 — 지금 트리에 있는 값만. */
export function filterOptions(nodes: WbsNode[]): {
  owners: string[]                       // 정렬됨, '미지정' 포함 여부도 데이터가 정한다
  tags: { id: number; name: string }[]
}
```

- **조건 여럿은 AND**다. 서로 다른 열의 조건이 OR면 필터를 좁힐 수 없다.
- 한 열 안의 여러 값(실행 방식 두 개 고르기)은 OR다.
- `matchIds`가 필요한 이유: 화면이 문맥 행을 흐리게 그려야 한다. 이것 없이 트리만 돌려주면
  일치 행과 문맥 행을 구분할 수 없다.

spec `wbsTreeFilter.spec.ts`:

- 조건 없음 → **같은 배열 참조**를 돌려준다(불필요한 재렌더를 막는다)
- 손자 하나가 일치하면 부모·조부모가 남고 `matchIds`에는 손자만 있다
- 일치한 Summary의 **하위는 남지 않는다** (2-1을 고정한다)
- 두 열의 조건이 AND로 걸린다
- 한 열의 두 값이 OR로 걸린다
- 업무명 필터가 대소문자를 무시하고 `description`도 본다
- WBS 코드 필터가 `1.2`로 `1.2`·`1.2.1`을 남기고 `1.20`은... **경계를 정해 테스트로 고정한다**
  (앞자리 일치이므로 `1.2`는 `1.20`도 문자열로는 일치한다. 코드 구분자(`.`)를 기준으로 토막을
  비교할지 여기서 정하고 그대로 적는다)
- 실행 방식 필터에서 **보관값을 가진 Summary는 일치하지 않는다**
- 분야 필터에서 **하위 요약(`rolledUp`)만 가진 Summary는 일치하지 않는다**
- 담당자 필터에서 상속받은 담당자도 일치한다(화면이 그 이름을 보여주므로)

### 3-3. `frontend/src/features/wbs/WbsTree.vue`

**(a) 필터를 적용해 행을 만든다.** 지금은 `rows = computed(() => flattenTree(props.tree, collapsed.value))`
(`091d4a6` 기준 `:57-58`)다.

```ts
const filter = ref<WbsFilterState>(EMPTY_FILTER)
const filtering = computed(() => hasActiveFilter(filter.value))
const filtered = computed(() => filterTree(props.tree, filter.value))
// 필터 중에는 접힘을 무시한다(2-3). collapsed 를 비우지 않는다.
const rows = computed(() =>
  flattenTree(filtered.value.nodes, filtering.value ? EMPTY_SET : collapsed.value),
)
```

`EMPTY_SET`은 모듈 스코프 상수 하나로 둔다(매번 `new Set()`을 만들면 `rows`가 필요 없이 다시
계산된다).

**(b) 드래그를 잠근다.** 2-2가 이 작업의 핵심이다.

| 자리 (`091d4a6` 기준) | 할 일 |
|---|---|
| `:467` `:draggable="!readOnly"` | `!readOnly && !filtering` |
| `:330` 부근 `onDragStart` | 맨 앞에서 `if (filtering.value) return` — 속성만 믿지 않는다 |
| `:697-705` `root-dropzone` | `v-if="!readOnly && !filtering"` |
| `:707-710` `legend` | 필터 중에는 "필터가 걸려 있는 동안에는 순서를 바꿀 수 없습니다. 이동은 필터를 해제한 뒤에 하세요."로 바꾼다 |
| `tbody tr { cursor: grab }`(`:736-738`) | 필터 중에는 `default`로 — 끌 수 있어 보이면 안 된다 |

**(c) 필터 행을 그린다.** `<thead>`의 머리글 행 다음에 `<tr class="filter-row">`. 보이는 열만
그린다(선행 작업의 `shows(key)`를 그대로 쓴다). 머리글이 고정된 상태(선행 작업)에서는 필터 행도
함께 고정해야 한다 — `position: sticky`의 `top`을 머리글 높이만큼 줘야 하고, 그 높이를 상수로
박으면 글꼴이 바뀔 때 어긋난다. 머리글 행의 실제 높이를 재서 CSS 변수로 넘기거나, 두 행을 같은
`<thead>` 안에 두고 각각 `top: 0`/`top: var(--head-h)`로 둔다.

- `text` 열: `<input type="search">`. **디바운스를 두지 않는다** — 클라이언트 필터라 즉시 반영이
  비용이 아니고, 디바운스는 "내가 방금 친 게 반영됐나"를 헷갈리게 한다
- `enum`·`names`·`tags` 열: 다중 선택. 새 컴포넌트를 만들지 말고 `<select multiple>` 또는 이
  저장소에 이미 있는 칩 토글 방식(`RaidView.vue:438-455`의 `.chip.active`) 중 하나를 고른다.
  **팝오버는 만들지 않는다**
- 조건이 걸린 열의 머리글에 표시를 남긴다(필터 행을 접었을 때 "왜 행이 적지?"를 알 수 있어야
  한다)

**(d) 툴바에 [필터] 토글과 상태 배너.** 선행 작업이 만든 툴바에 붙인다.

```
[하위 추가][수정][삭제]   [열 설정][필터 ●]   선택: 1.2 설계
필터 적용 중 — 일치 12건, 문맥 5행   [필터 해제]
```

- `[필터 해제]`는 `filter.value = EMPTY_FILTER` 하나다
- **일치 건수는 leaf만 세지 않는다** — 지연 배너(`WbsView.vue`)가 leaf만 세는 것은 Summary가
  하위의 지연을 이미 반영하기 때문인데, 필터 일치는 그 행 자체의 사실이라 Summary도 하나로 센다

**(e) 문맥 행을 흐리게.** `matchIds`에 없는 행에 클래스를 주고 `color: var(--text-faint)`
계열로 내린다. **행을 비활성으로 만들지는 않는다** — 문맥 행도 고르고 편집할 수 있어야 한다
(조상을 고치러 왔을 수 있다).

**(f) 선택과 키보드는 그대로 둔다.** 선택된 행이 필터로 사라지면 `resolveVisibleSelection`
(`:222-232`)이 이미 조상을 따라 올라가 처리한다. `watch(() => props.tree, …)`의 선택 무효화
(`:194-201`)는 **원본 트리**를 보므로 필터로 선택이 지워지지 않는다 — 맞는 동작이다(필터를 풀면
그 선택이 돌아온다).

### 3-4. `frontend/src/views/WbsView.vue`

**지연 경고줄은 필터를 따르지 않는다.** `attention`/`delayedCount`/`atRiskCount`(`:112-124`)는
`tree`(원본)에서 세고 있다 — **그대로 둔다.** "지연 업무 3건"은 프로젝트에 대한 사실이고, 필터를
걸어 숫자가 줄면 잘못 읽힌다(CLAUDE.md RAID 규칙: *"상단 배너는 필터를 무시하고 전체를 셉니다"*).

필터는 `WbsTree` 안에만 있으므로 이 파일은 **아무것도 바뀌지 않을 수 있다.** 바꿔야 할 것이
생기면 그건 필터 상태가 뷰로 새어 나간 것이니 다시 볼 것.

### 3-5. 컴포넌트 테스트 `WbsTreeFilter.spec.ts` (새 파일)

- [필터]를 누르면 필터 행이 나타나고, 다시 누르면 사라진다
- 업무명 칸에 글자를 치면 행 수가 줄고 조상이 남는다
- 문맥 행에 클래스가 붙고 일치 행에는 붙지 않는다
- **필터가 걸리면 `tr[draggable="true"]`가 하나도 없고 드롭존이 사라진다** (2-2를 고정한다)
- 필터를 풀면 드래그가 돌아온다
- 접어 둔 조상 아래의 일치 행이 필터 중에는 보이고, 필터를 풀면 다시 접힌 상태로 돌아온다 (2-3)
- 실행 방식 필터를 걸어도 머리글 수와 서랍 `colspan`이 어긋나지 않는다

## 4. 건드리지 않는 것

| 무엇 | 이유 |
|---|---|
| `wbsTree.ts`의 `flattenTree`·`resolveDropPosition`·`WbsRow` | 필터는 잘린 트리를 넘기기만 한다. `index`의 뜻을 바꾸면 이동이 조용히 틀린다(2-2) |
| `collapsed` | 필터 중에 무시할 뿐 비우지 않는다. 필터를 풀면 접힘이 돌아와야 한다 |
| `WbsView.vue:112-124` 지연 집계 | 배너는 프로젝트 전체를 센다. 필터를 따르면 잘못 읽힌다 |
| `watch(() => props.tree, …)` 선택 무효화 | 원본 트리를 본다. 필터로 선택이 지워져선 안 된다 |
| 서버·API·캐시 리비전 | 필터는 화면의 질문이다. 요청이 늘지 않는다 |
| 마스터 목록 API(`useWbsTags`, 구성원) | 선택지는 트리 값에서 뽑는다(2-4). 새 prop을 만들지 말 것 |
| `localStorage` | 필터는 저장하지 않는다(2-5) |

## 5. 확인 방법

```bash
cd frontend
npm test
npm run build
```

수동 확인:

1. [필터] → 머리글 아래에 한 줄이 열린다. 세로로 스크롤해도 머리글과 필터 행이 함께 남는다
2. 업무명에 `설계`를 친다 → 일치 행과 **그 상위 경로**가 남고, 상위는 흐리게 보인다
3. 일치한 Summary의 하위가 딸려 오지 않는다
4. 실행 방식 = Waterfall → Work Package만 일치한다. 예전에 Waterfall이었다가 Summary로 바꾼 행이
   일치하지 **않는다**(보관값)
5. 담당자에서 한 명을 고른다 → 상속으로 표시된 행도 일치한다
6. 분야에서 하나를 고른다 → 자기 분야로 가진 행만 일치하고, 하위 요약만 가진 Summary는 아니다
7. 두 열에 동시에 조건을 건다 → 둘 다 만족하는 행만 남는다
8. **필터가 걸린 상태에서 행을 끌어 본다 → 끌리지 않고, 드롭존이 없고, 설명문이 이유를 말한다**
9. [필터 해제] → 드래그가 돌아오고, 접어 뒀던 가지가 다시 접혀 있다
10. 필터를 걸어 선택된 행이 사라지게 한다 → 방향키가 여전히 동작한다(가장 가까운 보이는 조상에서
    움직인다). 필터를 풀면 원래 선택이 돌아와 있다
11. 상단의 "지연 업무 N건"이 **필터와 무관하게** 그대로다
12. 필터가 걸린 상태에서 체크포인트를 펼친다 → 서랍이 표를 깨뜨리지 않는다
13. 필터가 걸린 상태에서 열을 숨긴다 → 숨긴 열의 필터 조건이 어떻게 되는지 확인한다.
    **정해야 할 것**: 숨긴 열의 조건을 유지할지(보이지 않는데 행이 걸러진다) 해제할지.
    권하는 쪽은 **유지하고 배너에 알리는 것** — 조용히 해제하면 사용자가 모르게 결과가 넓어진다
14. 새로 고친다 → 필터가 비어 있다(저장하지 않는다). 열 구성은 그대로다
15. 커밋 조회 모드 → 필터는 동작한다(읽기다). 드래그는 어차피 잠겨 있다
