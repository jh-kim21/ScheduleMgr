# 프로젝트 커밋 히스토리 — 구현 지시서

> 이 문서는 구현을 맡을 에이전트/개발자에게 주는 작업 지시서입니다. 이 프로젝트를 처음 보는
> 사람도 이 문서만으로 작업할 수 있도록, 기존 구조와 따라야 할 패턴을 함께 적었습니다.
> 작업 전에 [CLAUDE.md](../CLAUDE.md)를 먼저 읽으세요 — 이 앱의 설계 원칙이 정리되어 있습니다.

## 1. 무엇을 만드나

프로젝트의 **특정 시점 전체 상태를 "커밋"으로 저장**하고, 나중에 그 시점의 화면을 모든 메뉴에서
그대로 다시 볼 수 있게 한다. git 커밋과 같은 감각으로, 사람이 명시적으로 찍는다.

할 수 있어야 하는 것:

1. 현재 시점을 커밋으로 저장 (메시지 + 작성자)
2. 커밋 목록 조회, 임의 커밋 삭제
3. **그 시점 화면을 전 메뉴에서 읽기 전용으로 조회** (WBS·간트·RACI·RAID·Backlog·Sprint·Board·대시보드·진척)
4. 그 시점 기준 보고 데이터 추출 (JSON 다운로드, 화면별 CSV)
5. 커밋에서 **새 프로젝트 생성**(복원)

**범위 밖** (이번에 만들지 않는다): 브랜치, 머지, 커밋 간 diff, 현재 프로젝트 덮어쓰기 복원.

## 2. 왜 이렇게 만드나 — 핵심 설계 판단

### 2.1 판정값을 "저장"한다 (재계산하지 않는다)

이 앱의 JSON 내보내기(`ExportService`)는 **의도적으로 판정값(지연 상태·선후행 위반·float·노출도·
기한 초과)을 담지 않습니다.** "오늘" 또는 다른 행을 기준으로 계산되는 값이라, 파일에 박히면
거짓이 되기 때문입니다.

**커밋은 반대로 갑니다.** 계산된 값까지 전부 저장합니다. 용도가 다르기 때문입니다.

| | 용도 | 판정값 |
|---|---|---|
| 내보내기(export) | 다시 **살아있는 프로젝트로** 읽어들이기 | 담지 않음 (새 맥락에서 거짓이 됨) |
| 커밋(commit) | 그 순간을 **박제해서 보기** | **담음** (그때의 사실이므로 정확함) |

재계산 방식을 택하면 **계산 로직이 바뀔 때 과거 보고 숫자가 따라 바뀝니다.** 다음 달에
`DelayCalculator`의 버그를 고치면, 3월 커밋을 열었을 때 3월에 실제로 보고했던 숫자와 다른 값이
나옵니다. 감사·보고 용도에서는 이게 치명적입니다.

이 판단에는 **선례가 있습니다.** `progress_snapshots` 테이블(V19)이 이미 계산된 지표(`metrics`)를
그대로 박아 저장하고, 주석에 이렇게 적혀 있습니다 —
*"Baseline이 지워지면 스냅샷은 남고 참조만 비워야 한다. 보고했던 사실 자체는 사라지면 안 된다."*

### 2.2 기준선(baseline)과 역할이 다르다

혼동하기 쉬우니 명확히 구분한다.

| | 무엇인가 | 계산에 쓰이나 |
|---|---|---|
| **기준선(baseline)** | 승인된 *약속*. 계획 진척·편차의 비교 기준 | **쓰임** |
| **커밋(commit)** | 그때의 *기록*. 보기만 함 | **안 쓰임** |

둘을 합치면 "기록을 남기려고 기준선을 다시 찍는" 오남용이 생깁니다. 기준선 재승인은 지연 신호를
리셋하는 무거운 행위이므로, 기록 목적으로 쓰이면 안 됩니다.

### 2.3 이미 정해진 결정 (바꾸지 말 것)

| 항목 | 결정 | 이유 |
|---|---|---|
| 압축 | **하지 않는다** | DB에서 내용을 직접 확인할 수 있어야 함 |
| 용량 한도 | **프로젝트별 1GB** | 초과 시 커밋 차단 후 사용자가 골라 삭제 |
| 자동 삭제 | **하지 않는다** | 무엇을 버릴지는 사람이 고른다 |
| 자동 커밋 | **하지 않는다** | 모든 변경마다 찍으면 목록이 노이즈가 됨 |
| 커밋 수정 | **불가** | 불변. 삭제만 가능 |
| 커밋 삭제 | **제약 없음** | 최신 커밋도 삭제 가능 |
| 복원 | **새 프로젝트 생성** | 덮어쓰기는 id 매핑·진행 중 Sprint 충돌 때문에 만들지 않음 |

## 3. 반드시 피해야 할 함정

작업 중 실제로 걸릴 것들입니다. 먼저 읽으세요.

### 3.1 `CLOB` 쓰지 말 것 → `TEXT`

압축을 하지 않으므로 큰 JSON 문자열을 그대로 저장하는데, **PostgreSQL에는 `CLOB` 타입이
없습니다.** 같은 마이그레이션이 H2(`desktop`)와 PostgreSQL(`server`) 양쪽에서 돌아야 하므로
**`TEXT`** 를 쓰세요. H2는 `TEXT`를 `CHARACTER LARGE OBJECT`의 별칭으로 받습니다.

### 3.2 `@Lob String` 쓰지 말 것

Hibernate 6(Spring Boot 3.5)에서 `@Lob`이 붙은 `String`은 PostgreSQL에서 `oid`(large object)로
매핑되어 깨집니다. 엔티티는 이렇게 작성하세요.

```java
@JdbcTypeCode(SqlTypes.LONGVARCHAR)   // @Lob 쓰지 말 것
@Column(nullable = false)
private String rawPayload;
```

### 3.3 버전 채번에 `count + 1` 쓰지 말 것 → `MAX(version) + 1`

기존 `ProgressBasisService.approveBaseline`(:173)은 이렇게 합니다.

```java
int nextVersion = baselineRepository.findByProjectId(projectId).size() + 1;
```

**기준선은 삭제가 없어서** 이게 안전했습니다. 커밋은 삭제가 되므로 이 패턴을 복사하면 깨집니다 —
`[v1, v2, v3]`에서 v2를 지우면 `size()`가 2가 되어 다음 커밋이 v3으로 채번되고
`UNIQUE (project_id, version)`에 걸립니다.

```java
int nextVersion = commitRepository.findMaxVersion(projectId) + 1;
```

**삭제된 번호는 재사용하지 않습니다.** v2를 지우면 목록은 `v1, v3, v4`가 되고, 그 빈 번호가
"중간에 뭔가 지워졌다"를 드러내므로 오히려 낫습니다.

### 3.4 새 도메인 예외는 `GlobalExceptionHandler`에 함께 등록할 것

CLAUDE.md에 기록된 실제 사고입니다 — *"Step 4에서 빠뜨려 Sprint의 모든 거부가 500으로 나갔고,
서비스 단위 테스트로는 드러나지 않았습니다."* 용량 초과·커밋 없음 등 새로 만드는 예외를
[`GlobalExceptionHandler`](../backend/src/main/java/com/projectflow/presentation/GlobalExceptionHandler.java)에
반드시 등록하고, **컨트롤러 레벨 테스트로 상태 코드를 확인**하세요.

### 3.5 기준일이 화면마다 갈리지 않게 할 것

`LocalDate.now()`가 네 군데에 흩어져 있습니다.

```
backend/src/main/java/com/projectflow/application/WbsService.java:84
backend/src/main/java/com/projectflow/application/GanttService.java:156
backend/src/main/java/com/projectflow/application/ProgressService.java:96
backend/src/main/java/com/projectflow/application/RaidService.java:178
```

커밋은 이 서비스들을 연달아 호출하므로, **자정 직전에 커밋하면 화면마다 기준일이 갈릴 수
있습니다.** 커밋 시 기준일을 한 번 정해 모든 호출에 같은 값을 쓰도록 경로를 만드세요.
(그 아래 계산기들 — `DelayCalculator.assess(...)` 등 — 은 이미 `referenceDate`를 파라미터로 받으므로
서비스 시그니처만 손대면 됩니다.)

### 3.6 조회 서비스를 개조하지 말 것

커밋 저장은 **기존 조회 API를 그대로 호출해 응답을 담기만** 합니다.
[`DashboardService`](../backend/src/main/java/com/projectflow/application/DashboardService.java)가
"아무것도 계산하지 않고 다른 서비스를 한 번씩 불러 배치할 뿐"인 것과 같은 패턴입니다.
데이터 출처를 갈아끼우는 개조(리포지토리 대신 payload를 읽게 만들기)는 **필요 없습니다.**

## 4. 백엔드 설계

### 4.1 마이그레이션 `V22__create_project_commits_table.sql`

현재 최신은 V21입니다. V22로 추가하세요.

```sql
CREATE TABLE project_commits (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    project_id BIGINT NOT NULL,
    -- MAX(version)+1로 채번한다. 삭제된 번호는 재사용하지 않는다.
    version INT NOT NULL,
    -- 이 커밋의 모든 판정값이 기준으로 삼은 날짜. 서버가 정한다.
    as_of DATE NOT NULL,
    committed_at TIMESTAMP NOT NULL,
    -- 로그인이 없으므로 자유 입력 텍스트다 (baselines.approved_by와 같은 한계).
    committed_by VARCHAR(100),
    message VARCHAR(1000),
    -- 화면에 필드가 추가되면 옛 커밋에는 그 값이 없다. 화면이 "구형 커밋"임을 말할 수 있어야 한다.
    format_version INT NOT NULL,
    -- 용량 집계용. 매번 LENGTH()로 TEXT를 훑지 않기 위해 저장해 둔다.
    payload_bytes BIGINT NOT NULL,
    -- 저장된 상태만. export 형식 그대로이며 복원(새 프로젝트 생성)에 쓴다.
    raw_payload TEXT NOT NULL,
    -- 판정값까지 포함한 화면 응답 모음. 시점 조회에 쓴다. 계산 로직이 바뀌어도 이 값은 불변이다.
    computed_payload TEXT NOT NULL,

    CONSTRAINT fk_commit_project FOREIGN KEY (project_id)
        REFERENCES projects (id) ON DELETE CASCADE,
    CONSTRAINT uq_commit_version UNIQUE (project_id, version)
);

CREATE INDEX idx_commit_project ON project_commits (project_id);
```

**H2와 PostgreSQL 양쪽에서 실제로 돌려 보세요.** CLAUDE.md의 "다음 단계"에 *"PostgreSQL에서
마이그레이션 전체를 한 번 돌려 보기"* 가 미완 과제로 남아 있습니다. 이 기능은 처음부터 양쪽에서
검증하고 가야 합니다.

### 4.2 API

| 메서드 | 경로 | 설명 |
|---|---|---|
| `POST` | `/api/projects/{projectId}/commits` | 현재 시점 커밋 (`committedBy`, `message`) |
| `GET` | `/api/projects/{projectId}/commits` | 목록 (payload 제외, 메타 + 용량 사용률) |
| `GET` | `/api/projects/{projectId}/commits/{version}` | 그 시점 전체 데이터 (`computed_payload`) |
| `DELETE` | `/api/projects/{projectId}/commits/{version}` | 삭제 |
| `GET` | `/api/projects/{projectId}/commits/{version}/export` | 그 시점 JSON 다운로드 (attachment) |
| `POST` | `/api/projects/commits/{commitId}/restore` | 그 커밋으로 **새 프로젝트** 생성 |

> 기존 `/api/projects/{id}/progress/snapshots`(보고 스냅샷)와 **다른 기능입니다.** 경로와 화면
> 용어에서 혼동되지 않게 하세요.

### 4.3 `ProjectCommitService` — 캡처

```
as_of            ← 한 번만 정해 아래 모든 호출에 같은 값 사용
raw_payload      ← ExportService 의 내보내기 결과
computed_payload ← 아래 조회 응답을 모은 JSON
```

`computed_payload`에 담을 응답 (전 화면 재현에 필요):

| 응답 | 재현할 화면 |
|---|---|
| `/wbs` | WBS |
| `/gantt` | 간트 |
| `/members`, `/raci` | RACI |
| `/raid` | RAID |
| `/backlog` | Backlog |
| `/sprints` | Sprint · Board |
| `/progress`, `/progress/checkpoints`, `/progress/snapshots` | 대시보드 진척 탭 |
| `/dashboard` | 대시보드 요약 |

`/dashboard`가 다른 응답의 내용을 일부 중복해서 담지만, **충실한 재현을 위해 그대로 저장합니다.**

### 4.4 용량 게이트 (프로젝트별 1GB)

```
커밋 요청
   ↓
SUM(payload_bytes) WHERE project_id = ?
   ↓
├ ~80%      → 그대로 커밋
├ 80~100%   → 커밋하되 응답에 경고 플래그 → 화면이 "용량 84% 사용 중" 배너 표시
└ 100% 초과 → 409 거부 + 기존 커밋 목록(버전·시점·용량) 동봉
                 ↓
            화면이 삭제 대화상자 표시 → 사용자가 골라 삭제 → 재시도
```

- 한도는 설정값 `project-flow.commit.max-bytes-per-project` (기본 1GB). 서버 배포에서 조정
  가능해야 하므로 하드코딩하지 마세요.
- **자동 삭제는 하지 않습니다.**
- 참고 용량 감각: 압축을 안 하므로 커밋 하나가 대략 2~5MB. 1GB면 프로젝트당 200~500개 수준.

### 4.5 복원 (새 프로젝트 생성)

`raw_payload`를 기존
[`ImportService`](../backend/src/main/java/com/projectflow/application/ImportService.java)에 그대로
넘깁니다. 가져오기가 이미 *"항상 새 프로젝트를 만들고 모든 id를 재매핑"* 하므로 추가 로직이 거의
없습니다.

- 이름 표기: `원본명 (v3 복원)` — 기존 `(가져옴)` 접미사 규칙과 같은 취지
- **현재 프로젝트를 덮어쓰는 복원은 만들지 마세요.**

## 5. 프론트엔드 설계

### 5.1 커밋 목록·저장 UI

- 위치: **프로젝트 화면** [`ProjectsView.vue`](../frontend/src/views/ProjectsView.vue)
  — 내보내기/가져오기가 이미 거기 있고, 저장 단위가 프로젝트라 일관됩니다.
- 목록 항목: 버전 · 시점(`as_of`) · 메시지 · 작성자 · 용량
- 상단에 용량 게이지: `84% (860MB / 1GB)`
- 행별 액션: **보기** / **JSON 내보내기** / **새 프로젝트로 복원** / **삭제**
- `＋ 현재 시점 커밋` 버튼 → 메시지·작성자 입력

**따라야 할 화면 규칙** (CLAUDE.md "화면 레이아웃 규칙"):
- 모든 추가·수정 폼은 [`ModalDialog`](../frontend/src/components/ModalDialog.vue) 안에 둔다
- 폼에 패널 크롬(테두리·패딩)을 두지 않는다 — 대화상자가 갖는다
- 저장 거부 메시지는 대화상자 안에 보여주고(`:error`), **성공했을 때만 닫는다**
- 표는 `.table-scroll`로 감싸고 `th, td`에 `white-space: nowrap`

### 5.2 읽기 전용 시점 조회 (전 화면)

**이 항목이 프론트엔드 작업량의 대부분입니다.**

- `frontend/src/stores/commitView.ts` 신설 — `activeCommit`을 **모듈 스코프**에 둔다
  (기존 `useProjects`/`useWbs`가 화면 간 상태를 공유하는 것과 같은 패턴. 뷰마다 새 `ref`를 만들면
  화면을 옮길 때마다 상태가 초기화된다.)
- 활성화되면 **api 클라이언트가 커밋 엔드포인트로 분기**한다. `computed_payload`가 라이브 응답과
  **같은 shape**이므로 화면 컴포넌트 자체는 거의 수정할 필요가 없다.
- **전 화면 고정 배너**: `2026-03-01 시점 (v3) · "1차 검수 완료" — 읽기 전용` + 나가기 버튼
- **쓰기 진입점을 빠짐없이 차단**한다. 대상:

  | 화면 | 막아야 할 것 |
  |---|---|
  | WBS | 추가·수정·삭제, 드래그 이동, 파일 가져오기 |
  | 간트 | 선후행 추가·수정·삭제, 일정 재계산 |
  | RACI | 역할 토글, 구성원 추가·수정·삭제 |
  | RAID | 항목 추가·수정·삭제 |
  | Backlog | 항목 추가·수정·삭제, 보관 |
  | Sprint | 생성·수정·삭제, 시작·종료, 배정·제거 |
  | Board | 카드 드래그앤드롭, 상태·차단 변경 |
  | 진척 탭 | 체크포인트 추가·수정·승인, 기준선 승인, 스냅샷 저장 |
  | 프로젝트 | 수정·삭제, 가져오기 |

- **캐시**: 커밋은 불변이므로 캐시 키가 `(commitId)` 하나면 충분하다. 기존
  [`stores/scheduleCache.ts`](../frontend/src/stores/scheduleCache.ts)의 리비전·로컬 날짜 조합은
  필요 없다.

### 5.3 보고용 추출

CSV 생성이 이미 조회 응답을 받아 만드는 구조이므로
([`shared/exportRows.ts`](../frontend/src/shared/exportRows.ts),
[`shared/csv.ts`](../frontend/src/shared/csv.ts)), **커밋 응답을 같은 함수에 넣으면 그대로
동작합니다.**

- 열 머리글의 기준일에 커밋의 `as_of`를 박을 것 (며칠 기준 보고서인지 드러나야 함)
- CSV 앞의 UTF-8 BOM(`'﻿'`)은 그대로 유지 — 없으면 Windows Excel에서 한글이 깨집니다

## 7. 완료 기준 / 테스트

**백엔드**
- [ ] 커밋 저장 후 `computed_payload`의 각 화면 응답이 저장 시점의 라이브 응답과 **일치**한다
- [ ] **삭제 후 채번**: `[v1,v2,v3]`에서 v2를 삭제하고 커밋하면 **v4**가 된다 (v3 아님)
- [ ] 최신 커밋도 삭제된다
- [ ] 용량 80% 초과 시 경고 플래그가 응답에 실린다
- [ ] 용량 100% 초과 시 409로 거부되고, 응답에 기존 커밋 목록이 담긴다
- [ ] 커밋 수정 API가 존재하지 않는다
- [ ] 복원이 새 프로젝트를 만들고, WBS·의존성·RACI·RAID·Backlog·Sprint 참조가 모두 재매핑된다
- [ ] 프로젝트를 삭제하면 그 커밋도 함께 삭제된다 (CASCADE)
- [ ] 마이그레이션이 **H2와 PostgreSQL 양쪽에서** 성공한다
- [ ] 새 예외들이 400/409로 나간다 (500이 아님)

**프론트엔드**
- [ ] 커밋 조회 모드에서 **9개 화면 전부**가 그 시점 데이터로 렌더링된다
- [ ] 5.2 표의 쓰기 진입점이 **모두** 비활성화된다
- [ ] 배너가 전 화면에 표시되고, 나가면 라이브 데이터로 돌아온다
- [ ] 커밋 시점 기준 CSV가 추출되고 기준일 열 머리글에 `as_of`가 박힌다
- [ ] 구형 `format_version` 커밋을 열면 없는 항목에 대해 화면이 "이 커밋에는 없는 정보"임을 알린다

**수동 확인**
- [ ] 커밋 → 데이터를 크게 바꿈 → 커밋 조회 시 예전 숫자가 그대로 나온다
- [ ] 자정 직전에 커밋해도 화면들의 기준일이 갈리지 않는다
