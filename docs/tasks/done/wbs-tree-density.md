# WBS 트리 — 한 화면에 보이는 행 수를 늘린다

대상 체크아웃: `D:\git\ScheduleMgr` (main `f91d4d5` "고정 열 오프셋을 선언값이 아니라 실제 렌더 폭에서 잰다")
모든 줄번호는 그 커밋에서 확인한 값이다.

사용자 요구: **"WBS 화면에서 볼 수 있는 Row 갯수가 너무 적다."**

---

## 1. 해결할 문제

화면 높이 900px(1080p + 브라우저 크롬) 기준으로 CSS에서 계산한 세로 예산이다. rem은 16px로
환산했고 **브라우저 실측이 아니라 추정치**다 — 비율을 보는 데는 충분하지만, 작업 전에 실제
화면에서 한 번 확인하고 시작하면 좋다.

| 어디 | 무엇 | 높이 |
|---|---|---|
| 표 **위** | 앱 헤더(`App.vue` `.app-header` `padding: 1.25rem` 상하) | ~72px |
| | WBS 제목 + [가져오기][최상위 추가] (`WbsView.vue:295-300` `margin-bottom: 1rem`) | ~48px |
| | 프로젝트 선택 (`WbsView.vue:336-343` `margin-bottom: 1.25rem`) | ~50px |
| | 지연 경고줄 (있을 때, `WbsView.vue:357-367`) | ~45px |
| | 툴바 — 버튼 9개 (`WbsTree.vue:1838-1843`) | ~45px |
| 패널 **안** | 고정 머리글 | ~35px |
| | 필터 행 (열었을 때) | ~40px |
| | **드롭존** (`WbsTree.vue:1957-1966`: `margin-top: 0.75rem` + `padding: 0.7rem` + 점선) | **~54px** |
| | **설명문 2줄** (`WbsTree.vue:1980-1985` `margin-top: 0.75rem`) | **~46px** |
| | `BOTTOM_GAP` (`WbsTree.vue`의 상수) | 16px |

행에 남는 높이 ≈ **489px**. 한 행은 `0.9rem` 글자(~20px) + `padding: 0.5rem` 상하(16px) +
테두리(`border-bottom: 1px` + `border-top: 2px`) ≈ **39px**(`WbsTree.vue:1277-1286`)이니
**약 12행**이다. 필터 행까지 열면 11행.

**표를 위한 공간보다 표를 둘러싼 것이 더 많이 먹고 있다** — 패널 *안*에서만 100px(2.5행)이
행이 아닌 것에 간다.

## 2. 결정된 방향

세 가지를 한다(사용자 결정). 합치면 **12행 → 약 19행(+58%)**이고 **레이아웃 구조를 건드리지
않는다.**

| # | 무엇 | 얻는 것 |
|---|---|---|
| A | 행 밀도 `보통 / 좁게` 옵션 | +4행 |
| B | **드롭존을 없앤다** | +1.4행 |
| C | 설명문을 `?` 토글로 접는다 | +1.2행 |

**하지 않기로 한 것과 이유**

- **페이지 크롬(제목·버튼·프로젝트 선택)을 한 줄로 합치기** — 항상 +1.3행이지만 `WbsView`
  레이아웃을 고쳐야 하고, 좁은 화면에서 그 한 줄이 다시 여러 줄로 접히면 이득이 사라진다.
  이번 셋으로 충분한지 먼저 본다.
- **전체화면 토글** — +5~6행으로 가장 크지만, 접힌 동안 프로젝트를 바꾸려면 다시 펴야 하는 등
  상태가 하나 더 생긴다. 셋을 적용한 뒤에도 부족하면 그때 만든다.
- **앱 셸을 고정 높이 flex로** — 근본적이다(지금 `maxHeight`는 마운트·리사이즈 때만 재므로
  **페이지를 아래로 스크롤해도 패널이 자라지 않는다**). 다만 `App.vue`와 모든 화면에 영향이
  가므로 별건이다.

### 2-B. 드롭존을 없애도 기능이 줄지 않는다 — 확인했다

`onDrop`이 `before`/`after` 배치에서 **`parentId: row.node.parentId`**를 쓴다
(`WbsTree.vue:662-666`). 그래서 **최상위 행의 위/아래 가장자리에 놓는 것만으로 이미 최상위로
옮겨진다.** 드롭존이 유일하게 하던 일은 "최상위 목록의 맨 끝에 붙이기"(`onDropRoot`가
`position: props.tree.length`, `:679-686`)인데, 그건 마지막 최상위 행의 아래 가장자리에 놓는
것과 같은 결과다.

여기에 `932284c`가 넣은 **[내어쓰기](Alt+←)**가 있어 최상위까지 단계적으로 올리는 버튼·키보드
경로도 이미 있다. 즉 경로가 셋에서 둘로 줄 뿐이다.

**잃는 것은 발견성 하나다** — "여기로 끌어다 놓으면 최상위 항목이 됩니다"라는 문장이 사라진다.
그래서 **C의 설명문이 그 안내를 대신 받아야 한다**(아래 3-C). 이것을 빠뜨리면 "최상위로 어떻게
올리지?"에 답하는 자리가 화면에서 없어진다.

## 3. 작업

### 3-A. 행 밀도 (`보통 / 좁게`)

**`frontend/src/features/wbs/wbsColumns.ts`**

- `WbsColumnPrefs`(`:65-68`)에 `density: WbsDensity` 추가. `export type WbsDensity = 'normal' | 'dense'`
- `defaultPrefs()`(`:70-72`)는 `'normal'`
- `normalizePrefs`(`:98-)`에 갈래 추가. `PIN_LEVELS`(`:57`)와 같은 방식으로 `DENSITIES` Set을 두고
  **모르는 값은 `'normal'`로 떨군다** — `localStorage` 값은 신뢰할 수 없다(이 파일의 기존 주석과
  같은 이유)

**`frontend/src/features/wbs/wbsColumnPrefs.ts`** — 손댈 것이 거의 없다. `STORAGE_KEY`(`:9`)는
그대로 쓰고(`project-flow.wbs-columns`) 새 키를 만들지 않는다. 밀도는 열 구성과 같은 성격의
"이 사람이 이 표를 어떻게 보고 싶은가"이고, 키를 둘로 나누면 `normalizePrefs`가 두 벌이 된다.

**`frontend/src/features/wbs/WbsColumnSettings.vue`** — `.pin-list`(`:61-101`)의 라디오 세 개와
**같은 모양으로** `보통 / 좁게` 라디오 두 개를 더한다. `onPin`(`:31-33`)과 같은 꼴의 `onDensity`를
두고 `setColumnPrefs({ ...columnPrefs.value, density })`. [기본값으로](`:102`)가 밀도까지
되돌리는 것은 `resetColumnPrefs`가 `defaultPrefs()`를 쓰므로 자동이다.

라벨에 효과를 적는다("좁게 — 한 화면에 3~4행 더"). 무엇이 달라지는지 안 적으면 눌러 보기 전에는
알 수 없다.

**`frontend/src/features/wbs/WbsTree.vue`**

표에 클래스를 하나 더 건다. `:pin-name`·`filtering`을 거는 바로 그 자리다.

```
:class="{ 'pin-name': columnPrefs.pin === 'name', filtering, dense: columnPrefs.density === 'dense' }"
```

```css
.wbs-tree.dense th,
.wbs-tree.dense td {
  padding: 0.3rem 0.5rem;
  font-size: 0.85rem;
}
```

**함정 셋 — 빠뜨리면 다른 것이 깨진다**

1. **`border-top: 2px solid transparent`(`:1282`)를 줄이지 말 것.** 드롭 표시(`.drop-before`/
   `.drop-after`)가 쓰는 자리다. 줄이면 드래그 중 행이 2px씩 튀고, 아예 없애면 드롭 위치가
   보이지 않는다. 밀도는 `padding`과 `font-size`만 건드린다.
2. **밀도가 바뀌면 머리글 높이와 고정 열 폭이 함께 바뀐다.** `--head-h`(필터 행의 `top`)와 고정
   열의 `left` 오프셋을 다시 재야 한다. **이미 걸려 있다** — `watch(columnPrefs, () => nextTick(measure))`
   (`:323`)가 `f91d4d5`에서 들어왔고, `measure()`(`:291-`)가 `measurePins()`(`:265-`)를 부른다.
   **`nextTick`이 필수인 이유도 같다**(클래스가 DOM에 반영된 뒤에 재야 한다). 이 watch를 건드리지
   말고, 밀도 전환 뒤 고정 열이 어긋나지 않는지 수동으로 확인한다(5장 3항).
3. **`.dense`를 `th, td` 규칙 자체에 합치지 말 것.** 지금 규칙(`:1277-1286`)은 `padding` 외에
   테두리·`white-space`·정렬을 함께 들고 있다. 밀도용 선언만 따로 얹어야 나중에 밀도를 지울 때
   나머지가 남는다.

### 3-B. 드롭존 제거

**`frontend/src/features/wbs/WbsTree.vue`** — 지울 것:

| 줄 | 무엇 |
|---|---|
| `:1252-1260` | `<div class="root-dropzone">` 블록 전체 |
| `:672-677` | `onDragOverRoot` |
| `:679-686` | `onDropRoot` |
| `:1957-1978` | `.root-dropzone` / `.root-dropzone.active` CSS |
| `:339` | `dropTarget`의 타입에서 `'root'` 제거 → `{ id: number; placement: DropPlacement }` |

`rowClass`(`:777-`)의 `target?.id === row.node.id` 비교는 숫자만 남아 오히려 단순해진다 — **비교
자체는 그대로 둔다.**

`dropTarget`을 `null`로 되돌리는 자리(`:603`, `:638`)와 행 위에서 세우는 자리(`:643`)는 그대로다.

### 3-C. 설명문을 `?` 토글로 접고, 내용을 현재에 맞게 고친다

**지금 설명문은 이미 낡았다.** `:1262-1265`는 드래그만 설명하고, `932284c`가 넣은 툴바 이동 버튼
넷과 Alt+화살표를 언급하지 않는다. 드롭존까지 사라지므로 **지우는 것이 아니라 고쳐서 옮기는
작업**이다.

- 툴바(`:1838-`) 오른쪽 끝에 `?` 토글 버튼을 둔다. `aria-expanded`를 주고 기본은 접힘
- 펼치면 지금 설명문이 있던 자리(패널 맨 아래)에 그대로 나타난다 — 자리를 옮기면 `flex: none`
  아이템 구성이 바뀌어 5장의 확인 항목이 달라진다
- 내용에 **세 가지**를 담는다:
  - 드래그: 가운데에 놓으면 하위, 위/아래 가장자리에 놓으면 같은 계층에서 순서
  - **최상위로 옮기기**: [내어쓰기](Alt+←), 또는 최상위 행의 위/아래 가장자리에 놓기 ← **드롭존이
    하던 안내를 여기서 받는다(2-B)**
  - 키보드: 위로·아래로·들여쓰기·내어쓰기 = Alt+↑/↓/→/←

**필터 중 문구는 토글과 무관하게 항상 보인다.** `legendText`(`:771-775`)와 `:1266`의 `v-else`는
"필터가 걸려 있는 동안에는 순서를 바꿀 수 없습니다"를 띄우는데, 이건 도움말이 아니라 **왜 드래그가
안 되는지에 대한 답**이다. 접히면 사용자가 이유를 알 수 없다. `v-if="!filtering"` 쪽만 토글에
걸고, `v-else` 쪽은 그대로 둔다.

### 3-D. 테스트

**`frontend/src/features/wbs/WbsTreeFilterRow.spec.ts:138-170`** — 이 테스트가 `.root-dropzone`의
존재/부재로 "필터 중 드래그 잠금"을 검증한다(`:145`, `:153`, `:170` 세 곳). 드롭존이 사라지므로
단정을 **`tr[draggable="true"]`가 0개인지로 옮긴다.** `:145`/`:170`의 "필터 전에는 드래그
가능하다"도 같은 방식으로 남긴다.

**단정을 지우지 말고 옮길 것** — 필터 중 드래그 잠금은 조용히 잘못된 이동이 저장되는 것을 막는
장치다(`wbs-tree-filter` 2-2).

**`wbsColumns.spec.ts`** — `normalizePrefs`가 모르는 `density`를 `'normal'`로 떨구는지, 기본값이
`'normal'`인지 두 개를 더한다(`pin`에 대해 이미 있는 테스트와 같은 모양).

**새 컴포넌트 테스트** (`WbsTreeColumns.spec.ts` 또는 밀도용 새 파일):

- `density: 'dense'`면 표에 `.dense` 클래스가 붙고 `'normal'`이면 안 붙는다
- `WbsColumnSettings`에서 `좁게`를 고르면 `setColumnPrefs`가 `density: 'dense'`로 불린다
- `?` 토글: 기본은 설명문이 없고, 누르면 나타난다
- **필터가 걸리면 토글과 무관하게 필터 문구가 보인다** (3-C의 결정을 고정한다)

`padding`·행 높이는 CSS라 테스트로 잡을 수 없다 — 수동 확인이 검증이다.

## 4. 건드리지 않는 것

| 무엇 | 이유 |
|---|---|
| `border-top: 2px solid transparent`(`:1282`) | 드롭 표시 자리다. 줄이면 드래그 중 행이 튄다 |
| `watch(columnPrefs, …)`(`:323`)·`measure()`·`measurePins()` | `f91d4d5`가 방금 만든 자리이고, 밀도 전환의 재측정까지 이미 덮는다 |
| `onDrop`의 `before`/`after` 분기(`:662-666`) | 최상위 이동이 여기에 달려 있다. 드롭존을 지우고 나면 **이 경로가 드래그로 최상위에 놓는 유일한 길이다** |
| `dropTarget`을 세우고 지우는 자리(`:603`·`:638`·`:643`) | 행 위 드롭 표시는 그대로다 |
| `legendText`(`:771-775`)와 `:1266`의 `v-else` | 도움말이 아니라 "왜 드래그가 안 되는지"에 대한 답이다. 토글에 걸지 않는다 |
| `BOTTOM_GAP`·`Math.max(320, …)` 하한 | 좁은 창에서 패널이 사라지지 않게 하는 장치다 |
| `App.vue`·`WbsView.vue` 레이아웃 | 이번 범위 밖(2장) |
| `wbsColumnPrefs.ts`의 `STORAGE_KEY` | 밀도를 같은 키에 함께 넣는다. 새 키를 만들지 않는다 |
| 다른 화면의 표 | 밀도는 WBS 트리에만 둔다. 다른 표에서 필요해지면 그때 옮긴다 |

## 5. 확인 방법

```bash
cd frontend
npm test
npm run build
```

수동 확인 — **행이 30개 이상이고 지연 경고줄이 뜨는 프로젝트**로:

1. 시작 상태에서 보이는 행 수를 센다(기준값, 대략 12행일 것이다)
2. `열 설정 → 좁게` → **행 수가 3~4행 늘고** 글자가 읽을 수 있는 크기로 남는다
3. **그 상태로 `고정: WBS + 업무명`을 켠다** → 고정된 두 열이 딱 붙어 있고 틈이 없다.
   순서를 바꿔(고정 먼저, 밀도 나중) 해도 같다 — 어긋나면 `:323`의 재측정이 밀도 변경을 놓친 것이다
4. 좁게 상태에서 **필터 행을 열고 닫는다** → 필터 행이 머리글 바로 아래에 붙는다(`--head-h`가
   밀도를 반영했는지 보는 것이다)
5. **드롭존이 화면에 없다.** 패널 아래가 표로 끝난다
6. 하위 항목을 드래그해 **최상위 행의 위 가장자리**에 놓는다 → 최상위로 올라간다
7. 같은 항목을 **마지막 최상위 행의 아래 가장자리**에 놓는다 → 최상위 맨 끝에 붙는다(예전 드롭존의
   동작)
8. 드래그 중 **드롭 위치 표시(위/아래/가운데)가 여전히 보인다** — 좁게 상태에서도
9. 툴바 [내어쓰기](또는 Alt+←)를 반복해 최상위까지 올린다
10. `?`를 누른다 → 설명문이 나타나고 **최상위로 옮기는 방법과 Alt+화살표가 적혀 있다**. 다시
    누르면 접힌다
11. **필터를 걸면** `?`가 접혀 있어도 "필터가 걸려 있는 동안에는 순서를 바꿀 수 없습니다"가 보인다
12. 새로 고친다 → 밀도가 그대로다. 프로젝트를 바꿔도 그대로다
13. `열 설정 → 기본값으로` → 밀도가 `보통`으로 돌아온다
14. 라이트·다크 양쪽에서 좁게 상태를 본다 — 행 구분선과 선택 배경이 여전히 읽힌다
15. 커밋 조회 모드 → 드롭존이 없어도(원래 `!readOnly`로 숨었다) 화면이 정상이고, `?`와 밀도는
    동작한다(읽기다)
16. 창 높이를 절반으로 줄인다 → 패널 하한(320px)이 걸려도 표가 보인다
